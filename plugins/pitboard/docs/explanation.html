How PitBoard works

Where PitBoard's numbers come from, how fresh they are, and how it computes Pace, Budget, and the rest. For the list of readings and thresholds, see the reference.

Where the numbers come from

PitBoard computes nothing it cannot read. Claude Code reports usage to plugins with each reply, and PitBoard adds what PaceLine's limits file and the session's transcript hold.

Reading Source
ContextThe token counts of each model request in the main conversation. After a compaction, the compaction's own size until /context can estimate the whole window, then that estimate until the next request.
Auto-compact, the compaction point, the compaction window and who set it/context's breakdown, read at session start, after each turn, and after each compaction.
Five-hour and weekly limits, API costClaude Code, once per turn, merged with the limits file when it exists.
Readings other sessions saw, the history behind Pace, model-scoped limitsPaceLine's limits file and its history, for the signed-in account only.
Cache countdown, Hit for the last turnThe session's own requests. The countdown runs from the start of the last one.
Session hits, the TTLThe session transcript since the last compaction.
Model, effort, Claude Code version, turns, session timeClaude Code. Until a request reports the effort, it comes from modelSettings or effortLevel in the settings. /effort in this session shows at once.
AdvisoradvisorModel in settings.json. /advisor in this session shows at once.
Branchgit branch --show-current in the start directory.

/clear, and a resume inside a running session, drop the previous conversation's context, cache, and session readings at once. The limits stay, because they belong to the account. Subagents' requests and compactions leave the row alone; it describes the main conversation.

Where the row sits

The row sits where each surface lets a plugin draw:

  • In the CLI, under the prompt input, below Claude Code's own mode and hint line. ⓘ and a pitboard button end it.
  • In Desktop, above the prompt input. Desktop offers a plugin no place under the input: it does not draw the hint line that holds the CLI row. Its footer under the input, between the mode selector and the model name, has room for a short label only, and holds a pitboard button.

Either pitboard button opens the same pane as /pitboard. Claude Code counts the click as your request, so the pane opens in a terminal of any width; a pane a plugin opens on its own waits for 144 columns.

How fresh the numbers are

Event What PitBoard refreshes
Each model requestContext, the cache countdown, Hit, effort
Each completed turnLimits, cost, model, branch, the /context breakdown, the limits file, the transcript
Every 20 secondsThe limits file and advisorModel in settings.json
Every secondThe clock behind countdowns, Pace, and time to reset

A limit reading moves only while some session makes requests, because Claude Code reports limits after each one. With every session idle, the five-hour and weekly readings stand still, unless PaceLine's usage-watch is on. An idle session sees a reading from another session up to about 20 seconds after PaceLine has written it to the file. A model switch, or an auto-compact change in /config, shows after the next completed turn.

The Desktop row redraws only when what it shows changes. A card's paces and times are taken at the start of the minute, so a card can lag by up to a minute.

How the row combines the file with its own session

PitBoard groups readings by window, by the reset time rounded to the minute:

  • A later window wins, even with a lower reading.
  • Within one window the higher reading wins, since a lower one can only be an older observation. On a tie the file's reading wins.
  • A file reading observed more than 5 minutes ahead of the clock, or with a window that ends later than its length allows (5 hours or 7 days, plus 5 minutes), counts as absent.
  • A window whose reset has passed reads 0%. The weekly window moves its reset forward by a week; the five-hour window has no known reset until a reading from the next window arrives.

Model-scoped limits

The model-scoped weekly limits, such as Fable, exist only in the limits file. PaceLine's usage-watch writes them with each exact reading of the account's usage, tagged "source": "usage-endpoint". PitBoard shows them while both hold:

  • The newest exact five-hour or weekly reading in the file is at most 15 minutes old.
  • The week they were read in has not reset.

With usage-watch off, the file has no model-scoped limits and the row shows none.

The formulas

Pace

Pace is how fast a limit is spent now, in percent per hour. PitBoard keeps a reading only when the percentage changes, so each reading holds until the next one. Pace runs from the value held at the start of a look-back span to the value now, and a flat stretch counts as time at zero. Pace is never negative.

Limit Look-back Minimum span before Pace shows
Five-hourThe last 90 minutes10 minutes of readings in this window
WeeklyThe last 6 hours1 hour of readings in this window

The weekly percentage moves in whole points, so its Pace needs a longer look-back. When the window started inside the look-back, Pace runs from the window's first reading. Until the minimum span has passed, Pace reads n/a (needs 10 min) or n/a (needs 1 h).

Budget, At reset, Runs out

Budget   = (100 - used %) / hours to reset
At reset = used % + Pace x hours to reset
Runs out = now + (100 - used %) / Pace hours
  • Budget is the pace that spends exactly what is left by the reset.
  • At reset is where the current Pace leaves the five-hour window at its reset.
  • Runs out replaces At reset when the limit reaches 100% before the reset.

The even-pace tick, Week elapsed, Spare and Overspent

The tick on a limit's bar stands at the share of the window gone: 1 - time to reset / window length, with a window of 5 hours or 7 days. For the week, the card calls this share Week elapsed.

Spare or Overspent (points) = used % - Week elapsed %
in hours of budget          = |points| / 100 x 168 h

Below even pace, the card says Spare; past it, Overspent. A week spends 100% over 168 hours, so a day of budget is 100/7, about 14.3 points.

Try the formulas

With scripts on, the sliders below run PitBoard's own code on a limit and show what its card reads. They give the numbers the formulas above give.

For example, at 40% Used with 3 hours to reset, a Pace of 10%/h gives a Budget of 20%/h and an At reset of about 70%, and a Pace of 20%/h gives an At reset of about 100%. The Pace slider stops at the fastest Pace the readings behind it can show: the used share spent over the minimum span, 10 minutes for the five-hour limit and 1 hour for the week, and never above 40%/h for the five-hour limit or 5%/h for the week. While a window has run for less than that minimum span (5 hours to reset on the five-hour limit, 168 hours on the week), PitBoard has no Pace to show and the card reads n/a. Clock times are in your time zone, counted from the moment you opened the page.

Context and cache

  • Ctx is the context's tokens divided by the compaction point while auto-compact is on, or by the full window while it is off, capped at 100%.
  • Turns left divides what is left before compaction by the average growth of up to the last five turns that grew the context. It needs at least two of them. A drop in the context is a compaction and starts the series over.
  • The cache countdown is the start of the last request plus the TTL, one hour or five minutes, less a 5-second margin. Until a cache write shows the TTL, PitBoard assumes five minutes. The hooks report how many tokens a request wrote to the cache but not their TTL, so after a request that writes the cache while the TTL is unknown, PitBoard reads the transcript again every 2 seconds, up to five times.
  • If cold uses the price ratio of a cache write to a cache read. A write costs 1.25 times the input price with a five-minute TTL and 2 times with a one-hour TTL. A read costs 0.05 times on Opus 5.5 and Sonnet 5.5, 0.025 times on Fable 5.1 and Mythos 5.1, and 0.1 times on other models (Anthropic's prices, prompt caching, read 2026-10-15). With a one-hour TTL a cold turn therefore costs about 40 times a warm one on Opus 5.5 and Sonnet 5.5, and 80 times on Fable 5.1 and Mythos 5.1; with five minutes, 25 and 50 times. On another model PitBoard divides by the 0.1 read price and marks the result ≥: at least 20 or 12.5 times.
  • Hit is cache reads divided by reads plus writes.
  • /compact sends a separate request with the same prefix as the conversation. While the cache is warm it reads that prefix from the cache; after a break longer than the TTL it processes the whole history as uncached input, so it costs the most when an old session is resumed (Claude Code, prompt caching, read 2026-10-15).
  • Claude Code can compact a long idle conversation shortly before its one-hour cache expires, and the next message then sends a summary. By default it does so in an interactive terminal session when the context is at or above a threshold, 200,000 tokens unless CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS sets it (the minimum is 100,000), about 54 minutes after the last request (Claude Code, settings reference, read 2026-10-15). While that is expected, the row shows ᶻ after the ↻ mark in the terminal, and a drawn pair of z letters, the usual sleep sign, in Desktop. The setting idleCompaction (Claude Code v2.1.290 or later; an earlier version ignores it), the variable DISABLE_AUTO_COMPACT and turning auto-compact off turn it off. PitBoard checks the setting, the variable, auto-compact, the one-hour TTL and the context size. It cannot see the feature flag Claude Code also consults, and it does not check the surface. The mark therefore shows that idle compaction is expected.
  • The Idle compact row of the Ctx card reads on · from 200k when every condition PitBoard can see holds (the figure is the threshold), on · below 200k (156k) when idle compaction is on but the context, here 156k, is under the threshold, off when the setting, the variable or auto-compact turns it off, and n/a when the cache is not on a one-hour TTL or the TTL is not known yet. The mark shows only for on.

Why the row can differ from /usage

  • /usage shows the account's figures at the moment you run it. The row shows the newest reading Claude Code reported to a session, or PaceLine recorded, and moves only when one arrives.
  • Within one window the row keeps the higher of its own reading and the file's.
  • The file holds the readings of each account apart. PitBoard finds the signed-in account in Claude Code's .claude.json and draws that account's partition only, so a /login to another account changes the figures within about 20 seconds. When PitBoard cannot tell the account, or the only readings have no account, it draws what the file has and shows Account unknown on the limit cards.
  • The row rounds percentages to whole numbers.
  • A Desktop card takes its paces and times at the start of the minute.
  • Desktop's own context ring counts the full window. Ctx counts toward the compaction point while auto-compact is on, so it reads higher.

Colours

A colour means the same on every surface: the CLI row and detail line, the Desktop row and cards, and the /pitboard pane.

Colour Meaning
None (grey)Nothing to do. Good values stay grey too.
AmberWatch: worth a glance.
RedAct: changes what to do next.
Blue (teal in the terminal)A cold cache: lost, and no longer urgent.
GreenA state that is on and fine: auto-compact on.

Model and effort colours name a model or an effort level and carry no state. In the CLI detail line, the model name, the advisor's model and the effort level take a theme colour by hue; the CLI row colours the advisor's model the same way, and the pane colours the model name beside Session. Desktop colours only the advisor's model name, in the row's Advisor group, with fixed hex; its model and effort sit in Desktop's own footer, which PitBoard does not colour. An advisor model of no known family is drawn in sand italics in Desktop, and an inactive advisor is dimmed and struck through in Desktop and in the terminal.

A model name is matched against these families without regard to case, and the first family in table order wins. A name that matches none of them takes the last row.

The terminal row, its detail line and the /pitboard pane draw in Claude Code's theme colours, so they follow a light or a dark theme: values in the theme's text, names, separators and rules in inactive, watch in warning, act in error, a cold cache in planMode (teal), and auto-compact on in success. Every text colour reaches a 4.5:1 contrast on Claude Code's light and dark themes, except on the light theme Sonnet and effort high (suggestion, 4.4:1) and Fable (bashBorder, 3.7:1). The Desktop row and cards keep their own fixed colours.

The five-hour limit turns red when its Pace is above its Budget. Budget is the pace that lasts exactly to the reset, so a higher Pace reaches 100% before the reset: the same condition as Runs out. The row also turns red from 90% used and amber from 70%.

The weekly limit and the model-scoped limits take their colour on the row from the percentage used only: amber from 80%, red from 95%. Inside the Week card, Pace above Budget is amber, and Overspent is amber, red past a day of budget.
