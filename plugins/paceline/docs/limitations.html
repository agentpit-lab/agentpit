PaceLine limitations

What PaceLine cannot do, grouped by where you meet it. Each entry says what you see and what still works, with a link to the page that explains the workaround. For how the numbers are made, see How PaceLine works. Type the /paceline: commands in a session; run the paceline commands in a session's Bash tool, or ask the agent to run them.

Accounts and logins

Limit readings need a claude.ai subscription login

pace, usage-watch, and the limits writer work only with a claude.ai login on a plan with usage limits, such as Pro or Max. A session that signs in with an API key, or reaches Claude through a gateway, carries no five-hour or weekly readings, and Claude Code gives usage-watch no login for its request. A session whose requests carry no limit readings gives pace no data. Sessions through Amazon Bedrock or Google Vertex AI are not tested; without limit readings they give no data either.

/paceline:pace status stops with no usage data yet, no pace: line comes before an Agent launch, and /paceline:usage-watch status shows last attempt: never.

context-watch and cache-watch do not use limit readings. See Keep usage current while idle.

Two accounts in one configuration directory keep their limits apart, with gaps

PaceLine tags each reading with a one-way key of the account that is signed in, and keeps the readings of each account in a partition of its own in rate-limits.json. Pace, the night queue, and PitBoard read only the partition of the account signed in now. After a /login to another account in the same configuration directory, the old account's figures stay in the file and come back when you sign in to it again. A partition whose readings are all older than 7 days is dropped, except the newest one, which stays however old and shows as stale. A Claude Code Desktop session passes its account to its process in the variables CLAUDE_CODE_ACCOUNT_UUID and CLAUDE_CODE_ORGANIZATION_UUID. When both are set and the account variable is a UUID, the key comes from them and holds for the life of the process. After a /login or /logout in that session, the PaceLine hooks and PitBoard in it treat the account as account unknown until it restarts; paceline status and the gates run from that session still read the variables and report the account the session started with. Otherwise the key comes from oauthAccount in Claude Code's own .claude.json, which names the account of the last /login in a terminal; see Files.

Some gaps remain:

  • A /login in another open session can misfile readings for a while. Every open session shares the .claude.json file, and a session tags a reading with the account the file names at the moment it writes. A session that writes just before it sees the change of account tags a reading of the old account with the new account's key, and it stands in the new partition until an exact reading or the next window replaces it.
  • A session still on PaceLine 0.2.5 does not tag its readings and merges them into a top level that mixes accounts. A merge by a newer session rebuilds the top level from the partitions, and a 0.2.5 merge can mix it again. The mix lasts until every open session has restarted on the new version.
  • A reader that knows nothing of accounts, such as an older PitBoard, sees only the top level, which mirrors the newest partition. It shows the account that wrote last, whichever account is signed in.
  • A reading with no account field, from an older PaceLine or another writer, goes to the partition unknown. Pace and PitBoard use it when the signed-in account has no partition of its own, and mark the figures as account unknown.
  • A Desktop session that its host starts with its own credential, rather than with the two variables alone, and macOS and Linux are not verified live. The variables are not part of Claude Code's documented interface, so a later version may drop them; PaceLine then reads .claude.json. The behaviour of oauthAccount there is read from Claude Code's files, not from a sign-in on those systems. Where the file names no account, the state is account unknown.

after a /login, /paceline:pace status shows the new account's figures, or no usage data yet for the signed-in account until its first reading arrives. When PaceLine cannot tell the account, status ends with account unknown (<reason>) and the pace: line adds account unknown. See Status says account unknown.

a Desktop session on one account and a terminal session on the other need no second directory: each tags and reads its own account. In a plain terminal, paceline status shows the terminal login's figures and ends with other account <8 digits> active; --account <8 digits> when another account has a reading under 30 minutes old; paceline status --account <key> shows that account's. A second configuration directory per account, as the next entry describes, keeps the files of two accounts apart altogether. See Use two accounts on one machine.

Each configuration directory keeps its own state

The state directory sits under the Claude Code configuration directory: $CLAUDE_CONFIG_DIR, else ~/.claude. Two configuration directories on one machine have two state directories.

each has its own pace switch, profile, plans, reservations, night queue, usage-watch switch, and usage-watch schedule. Turning pace on in one does not turn it on in the other.

to share one state directory, set PACELINE_STATE_DIR to the same path for both. Each session then resolves its own account from its own configuration directory's .claude.json, so the readings of the two accounts go to separate partitions of one limits file, and each session reads its own. See the reference for how <state> is found.

Surfaces and session kinds

Requirements: Claude Code 2.1.287 and Python 3.9

PaceLine needs Claude Code 2.1.287 or later, and Python 3.9 or later on PATH as python3 or python.

on an older Python, the hooks do nothing and write a hook.python line to <state>/debug.log, and paceline stops with a message that names the version.

see A hook reports a Python problem.

cache-watch does nothing in non-interactive runs

cache-watch keeps no cache in claude -p runs. Its wake is a background Stop hook, and Claude Code kills a background hook that is still running when a -p run ends. Ending the session also removes the session's cache-watch state. Sessions of the Agent SDK are not tested.

the run ends after its turn, and no wake comes.

cache-watch in an interactive session, in the CLI or in Desktop. See Hold the cache while away.

A hard limit refuses a launch in non-interactive runs

At a hard limit, or over the agent cap while the five-hour window burns toward its threshold, the hook before an Agent or Workflow launch asks you to confirm. In a claude -p run nobody can answer, and Claude Code denies such a request. This entry is from Claude Code's documentation, not tested here.

an Agent or Workflow launch at a hard limit, or over the agent cap in the burn state, fails in the run. With a cap of 0, every launch fails.

below the hard limits, and within the agent cap, the pace: line is advice only and the launch goes ahead. A night queue checks paceline auto before each item, and auto waits or stops at the same limits, and waits when the burn leaves no room for an agent. See The confirmation at a hard limit.

context-watch

context-watch leaves subagent compactions alone and gives no warnings with auto-compaction off

context-watch leaves subagent compactions alone: it writes a snapshot only for the main conversation. With auto-compaction off, the context line, if you turned it on, measures against the context window, and no warnings come.

no snapshot for a subagent's compaction, and no warning at 85% or 95% while auto-compaction is off.

the line, if you turned it on, and a snapshot at each compaction of the main conversation. See Recover after a compaction.

Where an organization manages Claude Code, context-watch does not run

On a Team or Enterprise login, and on a machine with managed settings, Claude Code seats its built-in sec-default guard. The guard keeps the prompt, tool-batch, session-start and compaction events from the hooks module of a plugin you install, and context-watch runs on those events. A fix is planned for a later version.

no context line, no warnings at the set levels, no snapshot at a compaction, and no note after it to read one.

pace, usage-watch and cache-watch. Naming paceline@agentpit in managed appendPlugins does not lift the guard while you install PaceLine yourself from the public agentpit marketplace: a plugin you install is not the organization's plugin, so the guard still skips its hooks (tested with PaceLine on a Team organization). An administrator can seat PaceLine as the organization's plugin, which the guard does not skip, with three managed keys: extraKnownMarketplaces with a directory marketplace at an absolute path, whose marketplace.json lists each plugin by a relative ./plugins/<name> source so that it loads in place; enabledPlugins with "paceline@<marketplace>": true; and appendPlugins naming paceline@<marketplace>. claude plugin list then shows Scope: managed. Where the organization has server-managed settings, the keys go into the admin console: under the default managedSourcesBehavior of first-wins, a local managed-settings.json adds nothing. That relaxes the organization's security settings, so it fits a small team whose owner can decide that, and hardly a large organization.

cache-watch

cache-watch keeps only one-hour cache entries

cache-watch holds the one-hour prompt cache. A session whose main thread writes five-minute cache entries is refused.

on prints not started: this session writes five-minute cache entries; cache-watch keeps only one-hour entries.

the main thread's TTL is Claude Code's setting for the session. See Hold the cache while away.

cache-watch keeps only the main thread's cache

cache-watch keeps only the main thread's cache. It reads the session's own transcript and skips subagent rows; subagents write their rows to separate files. A wake refreshes the main thread's cache and never a subagent's.

a finished subagent that you resume after its cache expired starts cold, whatever its TTL.

the main conversation stays warm while cache-watch is on.

A five-minute main thread is refused even with one-hour subagents

Only the main thread's cache entries decide. A session whose main thread writes five-minute entries is refused even when its subagents write one-hour entries.

on prints not started: this session writes five-minute cache entries.

the main thread's TTL is Claude Code's setting for the session; subagent TTL settings do not change the decision. See Hold the cache while away.

cache-watch needs a cache entry first

cache-watch starts only after the main thread has written a cache entry, which tells it the TTL.

on in a session with no cache entry yet prints not started: this session has no one-hour cache entry yet.

take one turn in the session, then run on again.

A computer that sleeps past the cache's expiry loses the cache

The wake runs in a hook process on this computer. A computer that sleeps past the cache's expiry misses the wake. cache-watch then turns itself off for the session, and your next message brings a one-line notice.

after the computer wakes, your next turn writes the whole context to the cache again, and the agent tells you in one line that the cache expired before the wake and cache-watch is off. /paceline:cache-watch status shows off (cache expired before the wake).

run /paceline:cache-watch on to watch the session again, or keep the computer awake while you are away, as Run a night queue describes in its first step.

Each wake counts against the five-hour limit

Each wake is one turn: it reads the context from the cache and sends a one-line push. The read costs far less than the rewrite of the whole context that the first turn after the cache's expiry would make (at least 20 times less by Anthropic's API prices), but the turn still counts against the five-hour limit. How much a cache read weighs in subscription limits is not published.

at most max (5) wake turns per absence, with the default settings.

lower --max, or raise --lead, with /paceline:cache-watch config. See Hold the cache while away.

The push reaches a phone only with Remote Control

The wake sends its one-line message as a push only when the session has the push tool: with Remote Control on and "Push when Claude decides" enabled in /config.

without them, no push on your phone.

without the push tool, the wake posts the line in the session as a reply instead.

cache-watch stops itself when the main thread switches to five-minute entries

When the main thread starts writing five-minute cache entries while cache-watch is on, watching stops.

one wake tells you in one line that cache-watch stopped, and /paceline:cache-watch status shows off (five-minute cache).

once the main thread writes one-hour entries again, run on again.

cache-watch shows times in the machine's time zone

The Cache kept until line and the times in status use the machine's time zone.

they can differ from pace's times when the profile counts in another zone.

pace's commands keep the profile's zone.

Idle compaction can run after cache-watch's last wake

In a terminal session whose context is at or above the idle compaction threshold, Claude Code is expected to compact the conversation about 54 minutes after the last request (Claude Code, settings reference, read 2026-10-15). cache-watch wakes the session no later than 52.5 minutes after the last request, and each wake, as a new request, restarts Claude Code's idle count. When the wakes run out, cache-watch turns itself off and Claude Code can compact about 54 minutes after the last wake. The threshold is 200,000 tokens unless CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS sets it, and idle compaction also needs Claude Code to fetch feature flags from Anthropic, so a given session may differ.

/paceline:cache-watch status shows off (no reply after N wakes). If Claude Code compacted the session in the meantime, the next message in the session sends a summary instead of the full history.

run /paceline:cache-watch on to watch the session again, or raise the number of wakes with --max. Setting idleCompaction to false keeps Claude Code v2.1.290 or later from compacting while idle; on an earlier version, setting autoCompactEnabled to false does.

cache-watch depends on Claude Code's private transcript format

cache-watch reads the session transcript, a private file of Claude Code, for the main thread's cache writes and their TTL.

if the format changes, on can report no one-hour cache entry, or wakes can stop.

the rest of PaceLine does not read the transcript.

pace

The pace line counts a model's own limit only when the model is set where Claude Code starts

The hook before a launch passes no model to pace. It counts a model-scoped weekly limit only when PACELINE_MODEL or ANTHROPIC_MODEL is set where Claude Code starts.

the pace: line can advise a model whose own weekly limit is spent.

paceline status --model <id> shows the model-scoped limit. See The budget per hour.

The pace line is skipped when pace takes longer than 3 seconds

The hook before a launch gives paceline status 3 seconds. When pace takes longer than 3 seconds, the hook adds nothing.

no pace: line and no confirmation for that launch; the launch goes ahead. A hook.pre_agent line with "failure":true goes to <state>/debug.log.

the next launch tries again. Run paceline doctor to find a slow step.

Reservations of a cut-off session wait for the next pace call

At session end, a hook records the end and releases the session's reservations in its own process. Claude Code gives all SessionEnd hooks 1.5 seconds together by default, and a plugin's own timeout does not raise it, according to Claude Code's documentation. When that budget cuts the release off, or another paceline call holds the state lock, the next pace call releases them: the pace: line before a launch, paceline auto, or a session start. Only a hook stopped before it records the end leaves them until their process is gone or their lease ends.

the reservations of an ended session stay active until the next pace call. When the hook was stopped before it recorded the end, the night queue counts them as outstanding until the lease ends (30 minutes, or 240 minutes for a subagent) or pace finds the owning process gone.

CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS, set where Claude Code starts, raises the budget for all SessionEnd hooks. paceline reserve list shows the active reservations, and paceline reserve prune drops the ones whose process is gone. See Reservations.

Unknown memory turns off the memory checks

When pace cannot measure free memory, the memory checks do not apply.

/paceline:pace status says host memory unknown.

see The recommendation.

The five-hour burn rate needs 10 minutes of readings

pace measures the five-hour burn rate from the readings of the current window, looking back 90 minutes. The base reading must lie at least 10 minutes back; until then there is no rate. A window that has just reset, and a machine with no history yet, start without one.

paceline status --json shows "burn": null under five_hour, no burn reason ends the status line, and the Agent and Workflow hook asks for no burn confirmation, however fast the percentage rises.

the hard limits, the budget per hour, and the agent count work without the burn rule, and the burn rule starts once 10 minutes of readings exist. See The five-hour burn rate.

Launch reservations rest on the order of Claude Code's hooks

The Agent and Workflow hook holds a launch reservation so that the launches of one assistant message count each other against the agent cap. Each SubagentStart of a session takes over the oldest launch reservation of that session, whichever launch it belongs to. The design assumes that Claude Code runs the PreToolUse hooks of one message before any SubagentStart of it. Claude Code does not document that order.

an agent whose start carries no session ID gets no reservation of its own: its launch reservation counts it for 60 seconds, and then nothing counts it. When the starts of a Workflow, or any start while other launches of the same session are pending, take over the oldest reservation, a pending launch can lose its reservation before its own agent starts, and that agent stays out of the count until it starts. A launch that you decline in a prompt keeps its reservation for 60 seconds.

the gate still asks or advises on the active reservations, and a launch reservation ends on its own after 60 seconds. See Reservations.

A prompt through the Agent SDK leaves the away marker

The hooks module clears the away marker only on a prompt typed in the terminal or in Claude Code Desktop, sent through Remote Control, or sent from Slack. Claude Code marks a prompt from claude -p or the Agent SDK with the same origin as a prompt that Claude Code Desktop sends on its own, such as the first prompt of a session that another session starts, so the module leaves the marker on both. If you work only through claude -p or the Agent SDK, your prompts never clear the marker.

paceline away status still shows away: on since <time> after you send a prompt through claude -p, and a launch at a hard limit is denied instead of asked.

run paceline away off when you are back, or send one message in the terminal, in Claude Code Desktop or through Remote Control. See The away marker.

The away marker has no expiry

The away marker stays set until you send a message in any session or run paceline away off. It has no timeout, and one file serves every session. A marker set before you leave and never followed by a message stays on, and so do the denials it causes. Without the marker, a launch that would ask waits for your answer.

paceline away status shows away: on since <time>, however long ago, and every launch that would ask is denied with a note that you are away.

paceline away off, or any message of yours, clears it. See The away marker.

Without the tzdata package, few time zones

Without the tzdata package, Python may have no zone data, and pace knows only UTC and a few built-in European zones.

the profile stays UTC.

see The time zone is wrong.

usage-watch

usage-watch is off by default

usage-watch is off until you run /paceline:usage-watch on.

without it, no model-scoped limits, and data only as of the last turn of a session on this machine.

everything in Data pace cannot see about readings without usage-watch. See Keep usage current while idle.

usage-watch reads an endpoint outside the published API

usage-watch reads https://api.anthropic.com/api/oauth/usage, an endpoint outside Anthropic's published API reference. Its address, answer format, or availability can change without notice. PaceLine reaches it only through Claude Code, with the session's own login; PaceLine never sees a token.

if the endpoint changes, /paceline:usage-watch status shows last error: HTTP <status> or unexpected response, and usage-watch waits 10 minutes after any error other than HTTP 429. PitBoard's model-scoped limits disappear 15 minutes after the last good reading, and pace's model-scoped rules stop applying.

the limits writer, the five-hour and weekly readings from each session's own turns, pace's budget and recommendation, the night queue (with the data ageing while sessions are idle), and PitBoard's five-hour and weekly readings. See usage-watch shows nothing.

usage-watch needs an open session

usage-watch runs inside an open session with PaceLine.

while every session is closed, nothing is read.

keep one session open, busy or idle. See Keep usage current while idle.

A sleeping computer pauses usage-watch

usage-watch runs in the session process, so it pauses while the computer sleeps.

no readings while the computer sleeps. When that lasts longer than 30 minutes, the data turns STALE: the hard limits are skipped and the night queue waits. Readings resume within about 10 seconds of waking.

keep the computer awake, as Run a night queue describes in its first step.

CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC blocks usage-watch

While CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC is set, Claude Code refuses usage-watch's request.

/paceline:usage-watch status shows last error: network error, and usage-watch asks again every 10 minutes.

the readings from each session's own turns. See Keep usage current while idle.

Data pace cannot see

Without usage-watch, only the five-hour and weekly windows

Without usage-watch, only the five-hour and weekly windows: the session readings PaceLine records hold only those two. A model's own weekly limit is not seen, and --model has no effect. Without usage-watch, the data is as of the last turn of any session on this machine.

the figures lag /usage, and no model-scoped limits show.

turn on usage-watch. See Why the numbers can lag /usage.

Measured costs and the forecast need care

The measured cost of a reservation or queue item is a change in account-wide weekly usage, so parallel work inflates it. A reservation that overlapped another is marked overlapped, and paceline calibrate leaves it out. The forecast and paceline calibrate need history: 3 hours of the last day for the forecast, and calibration_min_days (14) days for calibration.

no forecast, or no calibration proposal, until the history is there.

the budget and the recommendation need no history. See The forecast.
