PaceLine reference

Commands, exit codes, profile keys, environment variables, files, and the formats other programs read and write. The tables come from the plugin's code: python .ci/docs_facts.py build writes its facts, and python .ci/pages.py build writes the tables from them. The notes under each table are hand-written.

In this page, <state> is the state directory: $PACELINE_STATE_DIR, else <config>/state/paceline, where <config> is $CLAUDE_CONFIG_DIR, else ~/.claude.

Inside a session, the paceline command is on the PATH of the Bash tool. Elsewhere, run <plugin dir>/bin/paceline.cmd on Windows, or python <plugin dir>/scripts/paceline.py.

Common options

Every command except away and usage-watch accepts these options:

  • --json: print the full result as JSON.
  • --model ID: the current model ID. It selects a model-scoped weekly bucket when the limits file has one. Default: $PACELINE_MODEL, else $ANTHROPIC_MODEL.
  • --session ID: the Claude Code session ID. It also picks the session's account from <state>/session-accounts/. Default: $CLAUDE_SESSION_ID, else $CLAUDE_CODE_SESSION_ID.
  • --no-merge: use the limits file as it is, without merging the inbox first.
  • --now TIME: an ISO 8601 time to use as the clock, for what-if runs and tests. Default: $PACELINE_NOW, else the real time.
  • --state-dir DIR: the state directory for this command.

Status and switches

  • paceline status prints one line, for example:

    7d 34% reset 2026-10-03 03:00+00:00 | budget 1.45%/h (working-hours norm 1.03) | 5h 23%/95 | night 15.2% | data 1 min old

    The fields, in order: the plain weekly usage and the local reset time; the budget per hour against the norm of the current part (working-hours norm or off-hours norm); forecast unused, when there is enough history; five-hour usage against the five-hour stop; the night allowance; the age of the data, with STALE in front when it is older than 30 minutes. Further fields appear only when they apply: account unknown (<reason>), when the figures cannot be told to be the signed-in account's (the reasons are untagged, no-file, unreadable, no-account, no-credential, and no-state-key; while the session's account is pending, or is not known for the reason desktop or logged-out, status shows no figures and stops with no usage data yet), other account <8 digits> active; --account <8 digits>, one entry for each other account with a reading under 30 minutes old, shown only when the key came from .claude.json, that is, outside a session and with neither PACELINE_ACCOUNT_KEY nor --account, host memory unknown (only while the memory guard is on), pace hooks off (paceline on), a WARNING that the rest of the week is near the capacity of the hours left, and the reasons for a block. The line names no model and no number of agents; the model-scoped weekly buckets are in paceline status --json under weekly.scoped. The explanation says how each number is computed. With --json, data.account is {"state": "known" | "unknown", "key": <the signed-in account's key or null>, "reason": <code or null>}; key is the one-way key of the inbox, never an identifier of the account. data.other_accounts, a list of the full keys behind the other account field, is present only when that field is shown. paceline status --account KEY reports the partition whose key starts with KEY, 4 to 16 hex digits of a key in rate-limits.json; no match or several matches exit with code 2 and list the candidate keys. --account belongs to status alone; the gates always use the account of the session.

  • paceline queue ... and paceline auto ... moved to the Stint plugin: they print where they went on stderr and exit with status 2. paceline advice is the answer Stint obeys.
  • paceline on and paceline off write the pace switch, <state>/pace.json.
  • paceline profile prints the profile; show is the default. paceline profile set KEY VALUE changes one key with checks (see Profile keys). paceline profile check prints timezone follows this machine: <zone> in machine mode, and otherwise compares the profile's fixed time zone with this machine's and prints a hint when they differ; with --json it adds mode (machine or fixed) and effective, the zone in use.
  • paceline status --json shows the burn rule under five_hour.burn (rate_per_hour_pct, budget_per_hour_pct, budget_share, threshold_pct, threshold_at, threshold_at_local, base_at, span_min, and limited; null while no rate is measured), recommendation (blocked and reasons), and the away marker under away (on, set_at, session). reserve gives, at the top level and in paceline plan --json, the weekly reserve: pct, name, release (the release weekday; null is the last day before the reset), release_at, release_at_local, release_day, release_text and reset_text (the local weekday, day and clock, for example Fri 30 09:00), label (the reserve as the texts name it, for example reserve "tests" 8 %), released, kept_to_reset (true when no release falls inside the week, so the reserve is kept to the reset), opens_clock (the local clock the reserve opens at, for example 09:00; null when it is off, released or kept to the reset), kept_pct (what is kept now), stop_at_pct (100 less pct), used_pct (the plain weekly usage the stop compares), over (true before the release while the usage is at or past the stop line), and text, the line status and plan print. At 0 % the release fields and stop_at_pct are null. When the reserve cannot be computed, the object holds only error, over (false), kept_pct (0) and text (reserve unknown: the stop is off), and the figures around it are unaffected. budget_part names the part the budget comes from (kind, day, start, end, share_pct, spent_pct, part_hours, hours_left, unplanned, and stored, true when the part's entry is in the plan file). night describes tonight's off-hours part: date, start, end, hours, current, mark, weight, share_pct, fixed, window_capacity_pct, host_capacity_pct, last_before_reset, and allowance_pct. paceline status --launch-key KEY also holds a short-lived launch hold under that key; the Agent and Workflow hook passes the tool call ID. status --json also carries advice (see The advice format), budget_part.next_planned (start, start_local, day and kind of the first later part with weight above 0, or null), and stops.five_hour.reset (the ISO instant beside reset_local).

The advice command

paceline advice [--json] [--session ID] [--model M] [--no-merge] answers one question at any hour: may unattended work start, how much may it spend and with how many agents. It runs the status path without a launch key (it fixes the current part like status does), takes no hold, and builds the answer the format of The advice format describes.

  • The line is advice: START | budget 1.30% | agents <=3 (followed by | <text> for each limit reason), advice: WAIT until <local time> | <texts> (advice: WAIT | <texts> when no instant is known) or advice: STOP | <texts>, where <texts> are the reasons' texts joined by ; . With --json the command prints the advice object.
  • The exit code is 0 for start, 10 for wait and 11 for stop; an error exits 1 as everywhere.
  • While the account is known, the command also writes the advice to <state>/advice-<key>.json (the account key of the limits file), replacing the file; with no known account it writes nothing. A failed write is traced and never changes the answer.
  • Without the week's figures (no usage reading yet, or a week that cannot be read) the answer is built from the same short status status gives then, and is wait or stop with the reason's text.
  • The plan gate of attended launches, the pro rata comparison in limit mode, is not part of the advice; see What unattended work may spend.

Settings

  • paceline settings [--json] prints every PaceLine setting and switch with its value: the three switches (pace, usage-watch, away), the profile keys, the time zone mode, and the files behind them, and a last line that says where context-watch and cache-watch went. It also shows, from the week plan of the session's account, the working hours and the three reserve values (reserve_pct, reserve_release, reserve_name), which are not profile keys. A * marks a value that differs from its default. It only reads: it never runs a simulation. With --json each value has value and default , and the result adds switches; moved, which names the plugin (pitcrew) of context-watch and cache-watch; timezone (mode, stored, effective, detected, usable, hint); plan, with work_hours, reserve_pct, reserve_release and reserve_name (each value, default, range, and a note when the account is not known or the plan file cannot be read); and files, where plan is the plan file, or null while the session's account is not known.

The week plan

  • paceline plan [--json] prints the week from the current part to the reset. A day has two parts, its working hours (☼) and the off-hours after them (☾). Each day is one line with the mark of each part (off, light, normal, heavy, or a number), the part's share of what is left in percent, and a bar scaled to twice the even pace; ▲ marks a day above that scale. The current part carries ◀ now and spent X of Y (pro rata Z), and estimated when its starting usage was read after the start. A part the week cuts shows its hours, for example ☼ 09:00-14:00 (5 h). Below the days come the reserve line (for example reserve 8 % kept, opens Fri 30 09:00, the text status also shows; the release day's row ends with · reserve opens 09:00 while the reserve is kept), the even pace, the bar top, what is unplanned and when it expires, and not reachable in N windows for a share the part's five-hour windows cannot deliver. The warning shows only once the window ratio is calibrated: run paceline calibrate, then paceline profile set five_hour_to_week_pct VALUE; while the ratio is still its default 10.0, unreachable_windows is null and no warning shows. --json prints one object: mode, effective_mode, inform_until, work_hours, week, used_pct, reserve (see paceline status --json), left_pct, even_pct_per_day, bar_scale_pct, unplanned_pct and expires_at (both null unless the rest of the week is unplanned), current, days (from today's date), and week_days (every date of the week, ended parts included). Each part carries kind, start, end, hours, cut, mark, weight, state (ended, current, or later), share_pct, fixed, unplanned, estimated, spent_pct, allowed_pct, over, reach_pct, and unreachable_windows.
  • paceline plan set DAY [--work V] [--off-hours V] marks a day; give at least one option. DAY is today, tomorrow, mon to sun (the next such day, today included), or YYYY-MM-DD, and it must own a part of the current week, else the command exits 2. V is off (or day-off), light (0.5), normal (1), heavy (1.5), or a number from 0 to 2 in steps of 0.25. A mark for a part that has ended or lies outside the week is stored, and the command says it changes nothing in this week's plan. A mark that gives the part that is running another mark splits it at that moment: the part ends now and keeps its share and spending, and the rest starts now with a share from what is left of the week by its new mark. While the away marker is on, the part is not split: the mark is stored for later parts and the command says so.
  • paceline plan reset [DAY] removes the marks of one day, or of every day.
  • paceline plan template [show | set WEEKDAY [--work V] [--off-hours V] | reset [WEEKDAY]] shows, sets, or clears the marks every week starts from; a day without marks of its own takes its weekday's. Without a mark, working hours are normal and off-hours are off, so unattended work has no allowance until the off-hours are marked.
  • paceline mode [inform|limit] [--until-part-end] shows or sets the mode. inform is the default; limit makes a launch ask first when the current part is planned and its spending is more than 1 point above its share pro rata by now (pace plan: ...); the first question of a part names paceline mode inform --until-part-end. A hard limit asks in both modes, and an unplanned part never asks. While the away marker is set, a question is a denial. mode inform --until-part-end is accepted only in limit: it keeps limit stored but reads as inform until the current part ends. In inform it exits 2 with already in inform mode.
  • paceline profile set work_hours HH:MM-HH:MM sets the working hours of the plan file, in the profile's time zone. Minutes are multiples of 15, the start is before the end within one day, and both the working hours and the rest of the day last at least an hour; a refused value exits 2. The new hours apply from the end of the part that is running. work_hours is not a profile key.
  • paceline status --json carries plan: mode, effective_mode, inform_until, part (kind, day, start, end, end_local, share_pct, spent_pct, allowed_pct, over, unplanned, estimated), and first_prompt. Only status --launch-key can return first_prompt true, once for each part in limit mode. When the plan file cannot be read, plan is null and plan_error says why.
  • paceline plan offer [--refuse] [--hold | --confirm] is the command behind the off-hours offer. On the operator's own prompt in an off-hours part that is unplanned (its mark is the default and it has no share), with pace on, PaceLine adds one line for the model, once for each part across sessions: it asks whether to plan the part (light, normal, or heavy) and names paceline plan set DAY --off-hours V. A part whose mark the operator set, by a dated mark or by the weekday template, is not offered. --refuse records a no for the part, and no offer follows until the part ends. The record is <state>/plan-offer-<account>.json, and paceline off removes it. The command prints nothing when no offer is due, skips the inbox merge, and waits at most half a second for the lock. The prompt hook runs it with --hold, which records the offer as pending, and then with --confirm, which records it as offered once the hook has the line; a pending record ends the offers of its part for 30 seconds, so a run that was cut off before the line was shown is offered again.

Every command above that reads or changes the plan first fixes the current part's share, once, at the part's start, from the usage at that start; a later command in the same part writes nothing. Setting the marks or the template for the running part splits it at once (see plan set). Setting work_hours, the time zone, or a reserve key fixes the running part first, so the change applies from the next part. Exit codes: 1 for a plan file that is not valid JSON or a missing weekly reading, 2 for a refused value or day. The old plan add, list, find, modify, cancel, confirm, and tomorrow commands are gone, and a profile's old declared plans are dropped without conversion.

The weekly reserve

  • paceline reserve [PCT] [--release DAY] [--name TEXT] [--json] shows or sets the weekly reserve of the session's account. Bare, it prints the reserve's text, for example reserve 8 % kept, opens Fri 30 09:00, and with --json the reserve object of paceline status --json. Without a weekly reading it prints the stored values and release instant unknown: no usage data yet, and release_at is null. In a week with no release candidate (a daylight-saving change can leave the release day without a working start) the release instant is the reset and the reserve never opens that week: the text reads reserve 8 % kept to the reset Sat 31 05:00.
  • PCT is a whole number from 0 to 50; 0 turns the reserve off and keeps the release day and the name for a later reserve 8. --release DAY is mon to sun, or last for the last day before the reset; the release is a weekday kept from week to week, so today, tomorrow and dates are refused. --name TEXT is 1 to 32 printable characters, and --name "" clears it. A value that breaks a rule exits 2 and writes nothing.
  • A write fixes the running part first, like the plan commands, and prints the change and its effect: reserve: 8 % -> 10 %, the new reserve text, week used 93 % is past 90 %: launches ask from now when the new reserve is kept and the stop line is already reached, and released for this week; kept again from the reset Sat 31 05:00 when the new release day has passed. Moving the release to a later weekday after the reserve was released this week holds it again at once, and the answer says so. A write is refused while the session's account is not known yet, and skipped for a clock ahead of the wall clock (clock is ahead of the wall clock: nothing written).
  • With --json a write prints key (reserve_pct, reserve_release or reserve_name), old and new of the first change in that order, changes (every change as key, old, new; a release of null means last), the reserve object, and written.

The reserve is a safety stop, not part of the plan: before its release instant a launch asks once the week's usage reaches 100 less the reserve. reserve followed by an old subcommand, such as acquire, exits 2 and names the paceline hold command that took over. The settings pane and paceline settings show the three values as reserve_pct, reserve_release and reserve_name under the plan.

Holds

  • paceline hold acquire --kind subagent|workflow|gate|queue [--estimate PCT] [--label TEXT] [--key KEY] [--pid PID] [--item ID] places a hold. --estimate is the expected cost in percent of the weekly limit; it is required for every kind except subagent, which defaults to subagent_estimate_pct. With --key, a session keeps one hold per key, and a repeated acquire renews it. --pid is the owning Claude Code process; the default is the nearest parent process whose name starts with claude, else the live claude process that the CLAUDE_PID variable Claude Code exports names, as when a shell launcher has already exited (Git Bash on Windows). With neither, the hold has no owner process and ends when it is released or its lease runs out. Hold IDs are H- and eight hex digits.
  • paceline hold renew ID renews a lease. It exits 4 when the hold has expired or was released.
  • paceline hold release [ID] [--key KEY] [--actual PCT] releases one hold, named by ID or by key. The actual cost defaults to the change in weekly usage since the hold was acquired. It exits 4 when there is nothing to release.
  • paceline hold release-session [--target-session ID] releases every hold of a session, by default the one in --session.
  • paceline hold prune drops holds whose lease expired or whose process is gone.
  • paceline hold list lists the active holds.
  • paceline hold reconcile summarizes completed holds by kind: count, estimated and actual sums, and the median ratio of actual to estimate.
  • A hold of kind launch is not acquired with hold acquire. paceline status --launch-key KEY holds it, under the same lock that counts the active holds. It carries no estimate, never reaches the completed holds, and ends after 60 seconds. hold acquire --kind subagent closes the oldest launch hold of the same session, and hold release --key KEY --session ID drops one by hand; both the key and the session must be those of the launch. hold list shows it.

A hold is dropped when its lease expires (30 minutes without a key, 240 minutes with one) or when its process is gone. A completed hold records overlapped when another hold ran at the same time: its measured cost is a change in account-wide weekly usage, so parallel work inflates it.

Night queue

The night queue moved to the Stint plugin: stint add|list|report|start|done|fail|defer|retry|remove|clear-done replace paceline queue ..., stint next replaces paceline auto, and /stint:queue and /stint:run replace the night-queue skill. paceline queue and paceline auto print where they went on stderr and exit with status 2. The answer Stint obeys is paceline advice; paceline hold acquire --kind queue --item ID stays, and Stint uses it for its holds.

cache-watch and context-watch

Both moved to the PitCrew plugin: see PitCrew's reference. paceline cache-watch and paceline context-watch print one line that says so on stderr and exit with status 2.

usage-watch

  • paceline usage-watch on and paceline usage-watch off write the switch, <state>/usage-watch.json.
  • paceline usage-watch status prints the switch, the account whose state it reports (account: <key>, or account: unknown when none is known), the last attempt, the last success, and the last error of that account. Times are ISO 8601 in UTC, or never.

away

  • paceline away on [--session ID] sets the away marker, <state>/away.json, for every session. It prints away: on since <time> and a note that a launch that would ask for confirmation is now denied. The skill passes the session ID.
  • paceline away off clears the marker and prints away: off.
  • paceline away status prints away: off, or away: on since <time> and the session that set it.
  • The hooks module clears the marker at prompt.submit on your next message in any session. A prompt from a schedule or a loop, a notification, another session, a channel, a plugin, claude -p or the Agent SDK leaves it, and so do a cache-watch wake of the PitCrew plugin and the /paceline:away command, in its raw form (/paceline:away or /away), expanded into a <command-name> tag, or as the command Claude Code names.

away takes no common option. While the marker is set, the Agent and Workflow hook denies a launch that would ask, for a hard limit, the weekly reserve's stop line, or the plan in limit mode. paceline status --json shows the marker under away. See The away marker.

Skills

Each skill runs the matching command for you:

  • /paceline:pace on|off|status|doctor|profile|profile set KEY VALUE|simulate|plan
  • /paceline:away on|off|status
  • /paceline:usage-watch on|off|status
  • /paceline:settings [pane | advanced [topic]]

/paceline:settings shows every setting and switch. In a session where PaceLine's module runs, it answers before the model: a summary with the three switches, a table for each group (You and your day, This machine), a ● before each value that differs from its default, and the count of Advanced settings that differ. pane opens an editable pane in Claude Code Desktop and in the terminal; it writes through the same commands as above, so profile set's checks apply. Its Calendar tab shows the week plan, a card per date with the ☼ and ☾ marks and shares and a bar on a grey track that runs up to the bar top, an ended part showing what it spent or not recorded, the ended days folded into one line that unfolds when pressed, and − and + change a part that has not started through paceline plan set; see Plan a week. The PaceLine button opens the same pane, and a second click closes it; a click on a pane that is open but not in front brings it to the front first. In the terminal [ PaceLine ] follows PitBoard's button when PitBoard is installed, and in Claude Code Desktop [ PaceLine ] is always in the footer. The pane is read-only on a phone, and it has no switch element, so each switch is a button. advanced [topic] lists the Advanced settings with their identifiers. Where the module does not run, the skill runs paceline settings instead. A skill that an update adds needs a new session in Claude Code Desktop before the command appears.

Service commands

These commands calibrate, diagnose, simulate or merge by hand. Everyday use does not need them.

CommandWhat it does
paceline calibratepropose parameter corrections from history
paceline simulatereplay a week through the budget with your profile (a model: one reading per hour, no plans or holds)
paceline doctordiagnose pace on this machine; read-only without --live
paceline mergemerge the sessions' readings from the inbox into rate-limits.json

paceline calibrate reads the limits history and the completed holds and proposes new values for five_hour_to_week_pct, the weekly reserve, and subagent_estimate_pct, plus a ratio of actual to estimated cost for your task estimates. The proposal to raise the reserve by 2 (at most to 50; none at 50, and none while the reserve is 0 %) rests on the weekly usage at the release instant of each past window, the working start of the reserve's release day (see reserve.release_at); a window without a reading at or before that instant is skipped. A proposal names its command, for example reserve 8 -> 10 (...): paceline reserve 10. With --json, evidence.left_at_release_pct lists, for each window, what was left at the release instant. It needs 14 days of history and changes nothing.

paceline merge [--verbose] merges the inbox into the limits file now. It prints nothing unless you pass --verbose or --json.

paceline doctor [--live] [--bundle PATH] diagnoses PaceLine on this machine. It runs these probes: runtime, paths, switch, inbox, limits, account, process, memory, timezone, hooks, and debug_log, each ok, warn, or fail, with a hint for some. The timezone probe reports the profile's zone, the mode, and the zone in use. The account probe reports known or unknown, a reason code, the source of the key (env-key, profile, session, state-file, or none), and the key each source would give (session_key, variables_key, state_file_key), never an identifier or a token; see Status says account unknown. --json shows the evidence of each probe. Without --live it changes nothing; --live also runs one merge. --bundle writes a zip with the report, the debug log, the profile, the pace switch, the limits file, the last 50 history lines, the last 20 holds, and the week plan file of the account in use. The report and the bundle write your home directory as ~. The bundle holds hold labels and session IDs, and the plan file holds the free-text name of the reserve.

Simulate a week

paceline simulate replays one weekly window through PaceLine's own budget code, hour by hour (168 steps), and prints what your profile does to it. It reads the profile and the account's reading, writes nothing except its cache <state>/pace-simulate.json, and never changes the profile. Options:

  • --week on-track|heavy-start|light-start|away-thu-fri|all, repeatable, default all: the shape of the week. In each working hour the simulated operator spends the hour's budget times a factor: on-track 1 every working hour; heavy-start 2 in the window's first 72 hours, then 1; light-start 0.5 in the first 72 hours, then 1; away-thu-fri 0 in the working hours of local Thursday and Friday, else 1. The spend never exceeds five_hour_to_week_pct / 5 per hour, and stops while the recommendation blocks.
  • --night-queue no|yes|both, default both: each week without and with a night queue. A night queue spends the off-hours part's whole allowance over the hours of that part. With the default off-hours mark of 0 the allowance is 0 and the queue spends nothing. The allowance is the night.allowance_pct of status; the real advice leaves what is left of the current part's share.
  • --reset ISO: the weekly reset that the window ends at. Default: the account's next reset from the current reading, else the next Monday 00:00 in the profile's zone (reset_source default).
  • --defaults: the built-in defaults, the default plan (working hours 09:00-18:00, no marks) and the zone UTC, instead of your profile and your plan.
  • --cached: answer from <state>/pace-simulate.json when its key matches, else compute and store the result; the file holds at most eight results, and a new reset, a changed profile, or an update of PaceLine misses once.

The text output is a header line with the reset in the profile's zone, the zone, the working hours, whether the profile is yours or the defaults, and the note that this is a model, then one row for each week and queue:

Reset Mon 2026-10-19 00:00+00:00 (argument) | zone UTC | work hours 09:00-18:00 | the defaults | a model: one reading per hour, working and off-hours from the week plan, no holds

week          queue   unused   night asks h  peak 5h
on-track      no       5.1 %   0.0 %      1  100.0 %
on-track      yes      5.1 %   0.0 %      1  100.0 %
heavy-start   no       5.1 %   0.0 %      4  100.0 %
heavy-start   yes      5.1 %   0.0 %      4  100.0 %
light-start   no       8.7 %   0.0 %      1  100.0 %
light-start   yes      8.7 %   0.0 %      1  100.0 %
away-thu-fri  no      28.6 %   0.0 %      2  100.0 %
away-thu-fri  yes     28.6 %   0.0 %      2  100.0 %

unused is 100% less the usage at the reset; night the spend in off-hours by a night queue; asks h the hours in which a launch would ask you first; peak 5h the highest five-hour usage. The working hours and the weekday template come from your plan file, and --defaults uses the default plan. With --json, the result has model (version, steps, pins), inputs (reset, reset_local, reset_source (account, argument, or default), profile (own or defaults), timezone, work_hours), results (one object for each row, with week, night_queue, unused_pct, used_pct, night_pct, asks_h, blocked_h, and peak_five_hour_pct), warnings, and cache (key, hit).

Exit code 0 on success; 2 for a usage error, such as an unknown week or queue, or a --reset that is not an ISO 8601 instant; 1, with the reason, for a profile that cannot be read. The same inputs give the same figures on one Python version; across versions the last digit can differ. The explanation says what the model leaves out.

The profile is <state>/pace-profile.json. The first paceline command creates it. A new profile follows this machine's time zone (timezone_mode machine): when Python can use that zone here, the profile stores it as confirmed, and every later command checks the machine's zone again; otherwise it keeps UTC, unconfirmed, and tries again on every load. A profile created by an earlier version has no mode and reads as fixed, so its zone does not move. Keys missing from the file are filled with their defaults when it is read, and keys that earlier versions kept but that are now fixed in the code are removed from it. version and timezone_confirmed are kept by PaceLine and are not in the table.

paceline profile set KEY VALUE reads VALUE as JSON when it parses, else as text. The value must have the key's type and range: percentages from 0 to 100, counts and sizes not negative, timezone_mode as machine or fixed, and a time zone Python can use here. A refused value exits 2 with the reason on stderr. On success it prints KEY: OLD -> NEW and the paceline status line. Setting timezone also sets timezone_confirmed to true and timezone_mode to fixed, and says so; setting timezone_mode to machine takes the machine's zone at once. You can still edit the file by hand; the checks do not apply to a hand edit.

What each key does:

  • timezone: the IANA zone every wall-clock rule uses, for example America/New_York.
  • timezone_mode: machine or fixed. In machine mode, the default for a new profile, every command takes the zone of this machine, and timezone holds the zone last resolved; when the machine's zone has no data here, the stored zone stays in use. A profile without the key reads as fixed. paceline profile set timezone NAME turns the mode to fixed; paceline profile set timezone_mode machine turns it back.
  • five_hour_stop_pct: five-hour usage, in percent, from which an Agent or Workflow launch asks you first and unattended work waits, 95 by default. It is the same in working hours and off-hours. The five-hour burn rate is projected to the same stop.
  • five_hour_to_week_pct: the share of the week that one full five-hour window costs. It sets the most any hour can get: this value divided by 5, in percent of the week per hour. paceline calibrate proposes a measured value.
  • subagent_estimate_pct: the estimated cost of one subagent, in percent of the week.
  • memory_guard: true or false, false by default. On, a launch asks first below the free memory floor and unattended work stops there. Off, memory is not measured before a launch. Only a JSON boolean is accepted: paceline profile set memory_guard true. A profile file that exists but cannot be read or parsed counts as on with the default floor, and the pre-agent hook logs the read failure to the debug log; a missing file counts as off.
  • min_free_commit_mb: free memory, in MiB, below which no new work starts. Used only while memory_guard is on.
  • commit_reserve_mb, heavy_job_mb, max_heavy_runs: the heavy runs allowed are min(max_heavy_runs, (free memory - commit_reserve_mb) // heavy_job_mb), and never fewer than 0. heavy_job_mb is a whole number of 1 or more: paceline profile set refuses 0 and negative values, and a profile file that holds one leaves the figure out. Used only while memory_guard is on; with it off, the figure is not computed.
  • max_agents: the most parallel agents paceline advice gives, and so Stint's run.

The limits file (for readers)

<state>/rate-limits.json holds the newest limit readings from every session on this machine. A status line plugin or any other program may read it. Its format:

{
  "observed_at": "2026-10-11T09:30:00.000Z",
  "source": "payload",
  "session_id": "<session that gave the newest reading>",
  "model": "<its model id or null>",
  "five_hour": {"used_percentage": 42.5, "resets_at": "2026-10-11T12:00:00.000Z",
                "observed_at": "2026-10-11T09:30:00.000Z", "source": "payload"},
  "seven_day": {"used_percentage": 18, "resets_at": "2026-10-16T03:00:00.000Z",
                "observed_at": "2026-10-11T09:28:00.000Z", "source": "payload"},
  "account": "069e3589b134b882",
  "accounts": {
    "069e3589b134b882": {"observed_at": "2026-10-11T09:30:00.000Z", "source": "payload", "...": "..."},
    "9f44059c413565ef": {"observed_at": "2026-10-10T18:02:00.000Z", "source": "payload", "...": "..."}
  }
}

The fields above account are the newest partition, copied to the top level. A reader that knows nothing of accounts reads them as before.

  • observed_at is the newest bucket time; each bucket carries its own. Times are ISO 8601 in UTC.
  • resets_at is rounded to the minute and may be null.
  • Either bucket may be absent. Ignore fields you do not know.
  • A bucket's source is payload (a session's reading) or usage-endpoint (an exact reading of the account's usage). The top-level source is that of the newest bucket.
  • scoped, when present, is a list of {"name", "used_percentage", "resets_at"?} model-scoped weekly buckets. It comes only with an exact weekly reading and is replaced by the next one. It is dropped when seven_day moves to another window without one.
  • The file is replaced through a temporary file and a rename, so a reader never sees a partial file. It is written only when it changes.
  • accounts maps an account key to that account's record, in the format above without account and accounts. A key is 16 lower-case hex digits, or unknown for readings with no account. Each partition is merged on its own. A reader that knows the account it serves reads accounts[<its key>], else accounts["unknown"] and says that the account is unknown, and never another account's partition.
  • account is the key of the partition copied to the top level, or null when that partition is unknown.
  • A partition that no reading has touched for 7 days is dropped at the next merge, except the newest partition, which stays however old.
  • A file written before accounts existed has no accounts. Its buckets count as readings of the unknown account until the next merge moves them into that partition.
  • <state>/rate-limits.history.jsonl holds one such record per line: the partition that changed, with its account (null when unknown), and never the accounts map. A line with no account, or with an accounts map, was written by PaceLine 0.2.5 and may mix accounts. pace counts such a line only while every tagged line is the signed-in account's.

pace dates the file by its oldest live bucket, and judges freshness from that time.

The five-hour burn file (for readers)

<state>/five-hour-burn-<key>.json holds the burn figures of the current five-hour window of the account with that key (16 lower-case hex digits, the key of the limits file), computed once for every reader. With two accounts in use at once each has its own file. A reader that serves one account reads its own file. PitBoard reads it; any other program may. The format is:

{
  "computed_at": "2026-10-16T16:10:00.000Z",
  "account": "069e3589b134b882",
  "used_pct": 40,
  "resets_at": "2026-10-16T20:45:00.000Z",
  "threshold_pct": 95,
  "budget_per_hour_pct": 12.0,
  "rate_per_hour_pct": 42.7,
  "threshold_at": "2026-10-16T17:27:16.800Z",
  "threshold_at_local": "2026-10-16 20:27+03:00",
  "base_at": "2026-10-16T15:50:00.000Z",
  "span_min": 20.0,
  "limited": true
}

The fields:

  • computed_at is when PaceLine computed the figures. Times are ISO 8601 in UTC with milliseconds, except threshold_at_local, which uses the profile's time zone.
  • account is the key of the account the window belongs to, the same key as in the limits file.
  • used_pct and resets_at are the five-hour percentage and reset time the figures were computed for.
  • threshold_pct is the five-hour stop, five_hour_stop_pct: 95% by default, in working hours and off-hours alike. budget_per_hour_pct is the even pace that reaches it at the reset; it is null in the last 15 minutes before the reset, when such a rate is of no use.
  • rate_per_hour_pct, threshold_at, threshold_at_local, base_at, and span_min are null while no rate is measured; threshold_at and threshold_at_local are also null at a rate of 0 and at or above the threshold.
  • limited is true in the burn state: the rate would reach the threshold before the reset, and the data is fresh.

Use a file only when all of these hold: account is the account you serve; resets_at and used_pct equal the five-hour figures you show; computed_at is at most 3 minutes old. Otherwise compute your own projection. At or above the threshold the file projects nothing.

PaceLine writes the file only while pace is on, only for a known account and a known reset, after every merge that the plugin's hooks run and that wrote the limits file, and from every command that computes the status on the real clock. paceline merge on its own does not write it. A run dated with --now or PACELINE_NOW more than 5 minutes from the real time writes nothing, and neither does paceline status --account. The file is replaced through a temporary file and a rename. The file of an account that is no longer used stays, under 1 KB, until the account's next use replaces it. PaceLine never reads the file back: its own history is the only input of its computation.

The last-request file (for readers)

<state>/last-request-<key>.json holds the time of the newest model request of the account with that key (16 lower-case hex digits, the key of the limits file), for a reader that must tell whether anything was spent since a period began: the account's percentage moves in whole points, so the percentage alone cannot say. PitBoard reads it; any other program may. The format is:

{"version": 1, "account": "0123456789abcdef", "requested_at": "2026-10-29T09:10:00.000Z"}

Use the file only when version is 1, account is the account you serve and requested_at is an ISO 8601 time that parses; otherwise ignore it. Keep the newest requested_at you have seen for the key and forget it when the account changes. A request counts for a period when its time is at or after the period's start.

The module that runs in a session writes the file after every model step that returned usage, main agent and subagents alike, and only while the session's account key is known. Each write replaces the whole file, so it holds the newest request of the account only. A failed write is ignored and never fails the step. The file is written whether or not pace is on, and paceline off leaves it.

The week plan file (for readers)

<state>/week-plan-<key>.json holds what a reader needs to judge the current part of the week without running PaceLine, for the account with that key (16 lower-case hex digits, the key of the limits file). With two accounts in use at once each has its own file. A reader that serves one account reads its own file. PitBoard reads it; any other program may. PaceLine's own plan-<key>.json stays internal and undocumented. The format is:

{
  "version": 1,
  "computed_at": "2026-10-29T09:00:14.211Z",
  "account": "0123456789abcdef",
  "timezone": "Europe/Kyiv",
  "work_hours": "09:00-18:00",
  "mode": "limit",
  "inform_until": null,
  "week_resets_at": "2026-11-02T07:00:00.000Z",
  "five_hour_to_week_pct": 10.0,
  "reserve": {"pct": 8, "name": null, "release": null,
              "release_at": "2026-11-01T07:00:00.000Z", "error": null},
  "part": {"day": "2026-10-29", "kind": "work",
           "start": "2026-10-29T07:00:00.000Z", "end": "2026-10-29T16:00:00.000Z",
           "share_pct": 12.75, "unplanned": false, "used_at_start": 41.0,
           "estimated": false, "fixed_at": "2026-10-29T07:00:09.870Z",
           "weight": 1.0},
  "later": [{"day": "2026-10-29", "kind": "off", "start": "2026-10-29T16:00:00.000Z",
             "end": "2026-10-30T07:00:00.000Z", "weight": 0.0, "share_pct": 0.0}]
}

The fields:

  • version is 1. A reader that meets a higher version ignores the file. computed_at is when PaceLine computed the file. Every time is ISO 8601 in UTC with milliseconds. account is the key of the account, the same key as in the limits file. timezone and work_hours are the profile's time zone and the plan's working hours the parts were cut with; they are informative, and no verdict needs them.
  • mode and inform_until are the stored values, not the effective mode. A reader applies the effective-mode rule: limit reads as inform while now is before inform_until. The file therefore stays right across inform_until without a rewrite.
  • week_resets_at is the weekly reset of the week the part belongs to. five_hour_to_week_pct is the profile value that caps the part's rate at that value divided by 5, per hour.
  • reserve holds pct, name and release as stored, release_at, the instant the reserve opens (null when the reserve is off or could not be computed), and error (null, or the text of the failure). The file carries no released, kept_pct or over: they change with the clock and the usage. A reader derives them: the reserve is released when now is at or after release_at; it keeps pct before the release, else 0; the stop holds when release_at is set, now is before it and the weekly usage is at or above 100 minus pct.
  • part is the part that holds computed_at, as PaceLine fixed it: day, kind (work or off), start, end, share_pct (the fixed share in percent of the week, unrounded; null when the part is unplanned), unplanned, used_at_start (the weekly usage at the start, unrounded), estimated, fixed_at and weight. A reader that wants PaceLine's arithmetic uses these numbers as they are.
  • later lists the parts after the current one up to the reset, oldest first: day, kind, start, end, weight and share_pct, the share as spread at computed_at. The shares are provisional: they move when a command or the merge rewrites the file, which also happens when a weekly window has reset ahead of schedule or its reset has moved later. A reader uses the weights to tell an unplanned week (every weight 0 and share_pct of the part null) and may show the shares as provisional; it never uses them for the verdict.

Use a file only when all of these hold: it parses and its version is 1; account is the account you serve and the weekly figure you show is of that account; week_resets_at differs from the weekly reset you show by less than 10 minutes; now is at or after part.start and before part.end; and computed_at is not more than 5 minutes after now. Otherwise the file does not describe the current part and a reader falls back to what it does without PaceLine. A part that has ended means the writer has not run since the boundary; never extend or re-spread it. There is no age limit on computed_at: a part's figures stay right for its whole length.

The verdict: spent is the weekly usage minus used_at_start, at least 0. allowed is share_pct times the part of the part's length that has passed (0 to 1). The part is above its share when spent exceeds allowed by more than 1 point; a part with share_pct null is never above.

PaceLine writes the file only while pace is on and only for a known account, on the real clock, from every command that computes the plan or changes it: paceline status (also the status the pre-agent hook runs), plan, mode, reserve, every profile set key, and paceline on. It writes after it fixes the current part or saves the plan. The limits merge writes it too, but only when the file does not hold now (missing, unreadable, of another version, its part not started yet or ended, its week ended, or computed more than 5 minutes ahead): it then fixes the current part under the pace lock, waiting at most 3 seconds, and never holds the pace lock and the limits lock together. A busy pace lock leaves the file alone. The merge does not wait for a reading: every 15 seconds the hooks module of a session whose account is known, with pace on, reads the file and runs the merge when the file does not hold now (in the same cases). It runs at most once a minute for 10 minutes after the part end or week end it read, and once every 5 minutes after that and for a missing or unreadable file, until a re-read finds a part that holds now; a file that holds now costs it no run. While the file cannot be written (no weekly reading, the account not known, or a plan that cannot be built), every merge runs the step and pays the cost of loading it. A run dated with --now or PACELINE_NOW more than 5 minutes from the real time writes nothing, and neither does a command with --account. A plan that cannot be built, or a plan file that cannot be read (not one JSON object, or a newer version), removes the account's file; so does paceline off, for every account: off writes the switch first and removes the files under the lock, or without it when the lock stays busy. A busy lock, a missing weekly reading or a failed write removes nothing. The file is replaced through a temporary file and a rename. PaceLine never reads a figure back from it: plan-<key>.json and the usage history are the only inputs of its computation.

The advice format (for readers)

The advice is one JSON object, built by paceline advice --json, attached as advice to paceline status --json, and kept as <state>/advice-<key>.json (16 lower-case hex digits, the account key) after every run of paceline advice while the account is known. A reader without a process, such as a module, may read the file; computed_at says how old it is. The format, version 1:

{
  "advice_version": 1,
  "computed_at": "2026-11-02T20:00:05.114Z",
  "account": "0123456789abcdef",
  "action": "wait",
  "budget_pct": 0.0,
  "agents": 0,
  "wait_until": "2026-11-03T07:00:00.000Z",
  "reasons": [
    {"code": "share_zero", "effect": "wait",
     "text": "this off-hours part has no share: nothing is planned until 2026-11-03 09:00. To plan some now: paceline plan set 2026-11-02 --off-hours 0.5",
     "until": "2026-11-03T07:00:00.000Z",
     "command": "paceline plan set 2026-11-02 --off-hours 0.5"}
  ],
  "part": {"kind": "off", "day": "2026-11-02",
           "start": "2026-11-02T16:00:00.000Z", "end": "2026-11-03T07:00:00.000Z",
           "share_pct": 0.0, "spent_pct": 0.0, "holds_pct": 0.0},
  "stale": false
}

The fields:

  • advice_version is 1. computed_at is the now of the status it was built from (ISO 8601, UTC, milliseconds), and account is the account key, or null.
  • action is start, wait or stop: stop when any reason has the effect stop, else wait when any has the effect wait, else start. Nothing in the object names a model.
  • budget_pct is max(0, share - spent - holds) of the current part, in percent of the week, rounded to 3 decimals: the whole remainder of the part's fixed share, never other parts' shares or the reserve. It is 0 for a part with no fixed share, and for a status without the week's figures. agents is 0 unless action is start; then it is max(1, min(max_agents, host.max_heavy_runs)), with 3 for max_heavy_runs when it is not known, lowered by the five-hour burn.
  • wait_until is, on wait, the latest until among the reasons with the effect wait (null when none has one), and null on start and stop. stale is true when the usage data is stale or missing.
  • part is the current part as the status holds it: kind (work or off), day, start, end, share_pct, spent_pct and holds_pct (the outstanding holds). It is null when the status has no part.
  • reasons is the list of every condition that holds, in a fixed order, each a reason object: code, effect (stop, wait or limit; a limit lowers the agents and stops nothing), text (one line for a person), until (an ISO instant the reason lasts until, or null) and command (the command that removes the reason, or null; only share_zero has one).

The version rule: a later version adds fields without changing the meaning of the ones above, so a reader that knows version 1 may ignore fields it does not know. A change of meaning, such as a new unit, another effect for a code or a field that is dropped, raises advice_version. A reader checks advice_version first and ignores an object whose version it does not know. It takes the account it serves, and ignores the file when computed_at is older than the answer it needs.

The inbox (for writers)

PaceLine's module writes one reading per session to <state>/inbox/<session id>.json after each model turn when the readings change, and an unchanged reading at most once a minute. Another plugin may drop readings there in the same format. Name your files <plugin>-<id>.json, one per writer and session, and overwrite your own file.

{
  "observed_at": "2026-10-11T09:30:00.000Z",
  "session_id": "<session id>",
  "model": "<model id or null>",
  "account": "<account key, optional>",
  "five_hour": {"used_percentage": 42.5, "resets_at": "2026-10-11T12:00:00.000Z"},
  "seven_day": {"used_percentage": 18, "resets_at": "2026-10-16T03:00:00.000Z"}
}

Rules:

  • account is optional and names the account the reading belongs to. A writer that can name the account should set it: a reading without it, or with a value that is not 16 lower-case hex digits, goes to the partition unknown, and readers mark those figures account unknown. Compute the key as the first 16 hex digits of the SHA-256 hash of the UTF-8 text paceline-account-v1:<accountUuid>:<organizationUuid>, with both identifiers lower-cased from oauthAccount in .claude.json (see Files) and <organizationUuid> empty when it is missing. Write no account when accountUuid is not a UUID. Resolve it before every write, not once per process, because a /login in another session changes the file. PaceLine's own module takes the key from the account of the session's credential instead (see Which account a reading belongs to); .claude.json remains the way for a writer that cannot ask Claude Code for it.
  • observed_at is required and dates both buckets. A bucket needs a numeric used_percentage; resets_at is ISO 8601 or null.
  • A reading from the future, or with a reset later than its window allows, is skipped.
  • A half-written file reads as nothing until the next merge. A file older than 7 days is deleted.
  • Merge rule: the later window wins; a window that has passed loses to any reading; within one window the higher reading wins; a tie keeps the later one.

A writer that reads the account's own usage, the figures /usage shows, marks its reading as exact and may add the model-scoped weekly limits:

{
  "observed_at": "2026-10-11T09:30:00.000Z",
  "source": "usage-endpoint",
  "session_id": null,
  "model": null,
  "five_hour": {"used_percentage": 41, "resets_at": "2026-10-11T12:00:00.000Z"},
  "seven_day": {"used_percentage": 18, "resets_at": "2026-10-16T03:00:00.000Z"},
  "scoped": [{"name": "Fable", "used_percentage": 7, "resets_at": "2026-10-16T03:00:00.000Z"}]
}
  • Any source other than usage-endpoint, or none, marks an ordinary reading.
  • The merge takes the readings in the order they were observed, whatever their file names.
  • An exact reading replaces the bucket of the same name, whatever its window and number, unless the bucket in the file is an exact reading observed later, or an ordinary reading observed more than 15 minutes later. An ordinary reading lags the account by one request, so it does not outrank an exact reading taken seconds or minutes before it. Inbox files are read at every merge, so the 15 minutes keep an old exact reading from undoing much newer ones. An exact reading whose window has passed does not replace a bucket of a window still running.
  • For 15 minutes after an exact reading, ordinary readings leave that bucket alone, unless its window has passed. After that the merge rule applies again, so keep posting fresh exact readings for your numbers to stay.
  • scoped is read only from an exact reading with a seven_day bucket. Its entries need a string name and a numeric used_percentage. When that weekly bucket wins, the file's scoped becomes this list, or is removed when the list is empty or absent.

The merge runs when Claude Code starts and then every 15 seconds while the inbox changed, in the background.
