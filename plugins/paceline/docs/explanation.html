How PaceLine works

This page explains where PaceLine's numbers come from and how pace turns them into a budget, a recommendation, and the night queue's decisions. For the exact commands and keys, see the reference. To try the budget with your own numbers, open the budget simulator; to replay a whole week through the budget, run paceline simulate.

Where usage readings come from

pace works from one file, the limits file <state>/rate-limits.json. Two kinds of reading reach it through the inbox, <state>/inbox/:

  • Session readings. With each model turn, Claude Code hands plugins the five-hour and weekly readings that the session's own request carried. PaceLine's module writes them to the session's inbox file when they change, and an unchanged reading at most once a minute. This part, the limits writer, is always on.
  • Exact readings. While usage-watch is on, PaceLine asks Claude Code for the account's own usage, the figures /usage shows, with the model-scoped weekly limits. Claude Code adds the session's claude.ai login to the request; PaceLine never sees a token. The answer goes to <state>/inbox/usage-watch-<key>.json, one file per account (unknown when none is known).

A merge takes the inbox into the limits file. The hooks module checks the inbox when Claude Code starts and then every 15 seconds while a session is open, and merges any change. A pace command merges first when the data is older than 300 seconds. The pace: line before an Agent launch uses the limits file as it stands, without a merge.

Which account a reading belongs to

Two accounts can share one configuration directory, so one limits file. PaceLine's module tags each reading with the key of the account that the session's own credential belongs to. At session start, after /login or /logout, and when the stored credential changes, it asks Claude Code's profile endpoint for the account of the session's login and keeps only a one-way key of the account and organization identifiers in the answer: the first 16 hex digits of a SHA-256 hash, which cannot be turned back into either identifier. Until the first answer the session writes no reading. When the endpoint refuses the request, or three asks in a row fail, the module takes the account named in Claude Code's .claude.json instead, except in Claude Code Desktop or a process started from it, whose .claude.json names the last terminal login; such a session then writes no reading. The account variables that Desktop sets are never used: a claude started from a Desktop terminal tab inherits them while its own login may be another account. The merge puts each account's readings into a partition of its own, accounts[<key>], and mirrors the newest partition at the top level for readers that know nothing of accounts. Readings with no key go to the partition unknown.

Every reader uses only the partition of its session's account. The module records that account for each session in <state>/session-accounts/<session id>.json and passes it to the commands it starts, and a paceline command in a session's Bash tool reads the session's entry; a command outside any session takes the account named in .claude.json. When the account has no partition yet, it uses unknown and marks the figures account unknown; when there is neither, pace says no usage data yet for the signed-in account. While the session's account is not known yet, or cannot be known (pending, desktop, logged-out), the reader shows no figures rather than another account's. The history keeps one line per partition that changed, with its account, and pace's forecast and calibration count only that account's lines.

After /login or /logout, the module holds back a reading whose limits equal the ones it held before the command while the account differs from the held one: Claude Code may still carry the old account's limits in the next request, and they must not be tagged with the new account.

A partition that no reading has touched for 7 days goes at the next merge, except the newest one, which stays however old. Signing in again to an account whose partition remains shows its last figures at once, dated by their age.

How usage-watch paces its requests

Every open session with PaceLine checks at its start and then every 10 seconds whether a request is due: one is due when 125 seconds have passed since the last reading. The sessions of one account share that schedule through <state>/usage-watch.state-<key>.json, so one reading serves them all; sessions of different accounts each have their own schedule and get their own reading every 125 seconds. After an HTTP 429 answer, usage-watch waits one interval; after any other error, it waits 10 minutes. The switch is read on every check, so turning usage-watch on or off takes effect within 10 seconds, with no restart.

usage-watch needs a claude.ai login and an open session. When Claude Code gives no login for the request, usage-watch sends nothing. While CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC is set, Claude Code refuses the request, and usage-watch records network error.

Why the numbers can lag /usage

  • A session reading arrives with the session's own request, so it trails the account by one request. It changes only when a session on this machine takes a turn. Usage from another machine or from claude.ai shows up after the next local turn.
  • pace dates the limits file by its oldest live bucket. When that age passes 30 minutes, the data is STALE: the hard limits on the five-hour and weekly windows are skipped, and the night queue waits.
  • With usage-watch on and any session open, the data is at most about two and a half minutes old: 125 seconds between requests plus up to 15 seconds to the merge.
  • For 15 minutes after an exact reading, session readings leave that bucket alone. The inbox rules give the full merge rule.

Working hours and off-hours

Every wall-clock rule uses the profile's time zone. The weekly window ends at the reported weekly reset and starts 7 days earlier. pace divides it into parts of two kinds, two for each day: the working hours (☼) and the off-hours (☾) that follow them until the next working start. Each part has a mark and, from it, a share of what is left:

Kind Hours by default Budget
working hours (☼)09:00 to 18:00 by default (work_hours of the plan file)The part's share of what is left, by its mark (1 by default)
off-hours (☾)The rest of each day, from the end of the working hours to the next working startThe part's share by its mark (0 by default: no budget, and the night queue's allowance is 0)

A mark is off (0), light (0.5), normal (1), heavy (1.5), or a number from 0 to 2 in steps of 0.25. paceline plan set marks a day, and paceline plan template set marks a weekday of every week. A part's weight is its mark, scaled down when the week cuts the part short.

A part's share is fixed when the part starts: what is left at that instant (100% minus the weekly usage and the reserve) times the part's weight over the sum of the weights of this part and every later part of the week. Usage after the start moves no share of the part that is running; it moves the shares of the parts that have not started. When every weight is 0, the part is unplanned: its budget is 0 and it never asks you.

The five-hour stop does not follow these hours: five_hour_stop_pct is the same in working hours and in off-hours.

The budget per hour

pace computes the budget in these steps:

  1. Effective weekly usage. The weekly reading, or a model-scoped weekly bucket that matches the current model when that is higher. Model-scoped buckets come only from usage-watch, and only count when pace knows the model (--model, PACELINE_MODEL, or ANTHROPIC_MODEL). The part's share and spending below count the plain weekly reading only.

  2. What is left. 100% minus the effective usage.

  3. The reserve. A reserve of the week (8% by default, one per account, set with paceline reserve) is kept whole: the plan spreads only what is left after it. It is released whole at the start of working hours of its release day, by default the last day before the reset, and from that instant the plan spreads the released reserve over the remaining parts of the week by their weights. After the next reset it is kept again. Until the release it is also a safety stop: a launch while the week's usage is at or past 100% minus the reserve asks first, in whole points as Claude Code reports them.

  4. Spendable. What is left minus the reserve still kept, never below 0.

  5. The share. The current part's share, fixed when the part started: what was left after the reserve then kept at its start, times the part's weight over the weights of this part and every later part of the week (see Working hours and off-hours). A part that starts at the release instant is fixed with nothing kept, so the released reserve is shared by it and every later part. A part with weight 0 has share 0. When every weight is 0 the part is unplanned and its budget is 0.

  6. The rate. What is left of the share (the share minus what the part has spent since it started, never below 0) over the hours left in the part. No hour gets more than its capacity, five_hour_to_week_pct / 5 percent of the week (2% by default).

  7. The budget. The rate, or 0 in an unplanned part. A part that spends in step with the clock gets its share divided by its hours as its budget, which is also its norm.

To move these steps with your own numbers at one instant, open the budget simulator. To replay a whole week, run paceline simulate (see the weekly simulation).

The share is fixed at the start of the part, so overspending is not recovered inside the part: the budget falls instead, and the next parts divide what is left by their weights.

The norm is the part's share divided by its hours, the even rate for the part, at most five_hour_to_week_pct / 5. A part with share 0 has a budget of 0, and its norm is the nominal hourly rate (100 - the reserve's size) / 168. paceline status shows the kind of part the budget belongs to, for example budget 1.00%/h (working-hours norm 1.00).

paceline status also warns when what remains of the week reaches 90% of what the hours left in the current part and the later parts with a weight above 0 can spend up to the five-hour stop (five_hour_stop_pct): those hours can then barely use what is left.

The weekly reserve

The weekly reserve is a safety stop outside the plan. It sets aside a share of the week, 8% by default, for work you decide on late in the week. Each account has its own reserve; paceline reserve sets its size, its release day and a name (see Keep a reserve for a task at the end of the week).

  • The stop line. Until the release instant, a launch asks when the week's usage is at or past 100% minus the reserve: 92% for the default 8%. The check reads the plain weekly figure, not a model's own bucket, in whole points as Claude Code reports them and with no tolerance. See The confirmation at a hard limit.
  • The release instant. The start of working hours of the release day, in the profile's time zone. By default the release day is the last day before the reset whose working hours end at or before the reset. It stays that day when you mark its working hours off, because the marks do not move it. --release mon to sun picks a weekday instead. A weekday whose working start has already passed this week means the reserve is released for this week and kept again from the next reset.
  • The spread after it. From the release instant nothing is kept. The part that starts at the release instant is fixed with the whole reserve in what is left, and that part and every later part share it by their weights. A part that started earlier keeps its share. After the next reset the reserve is kept again.
  • A release day that is the reset's day. With a release weekday equal to the weekday of the reset, the hour of the reset decides. A reset at or before the start of working hours puts the release at the start of the week, so the reserve is hardly kept. A reset inside working hours leaves only the hours before the reset. A reset after working hours gives the same instant as the default. In a week with a daylight-saving change that weekday can have no working start inside the week, and then the reserve is kept until the reset. Pick an earlier day unless the reset falls after working hours.
  • What the stop does not catch. It acts on Agent and Workflow launches only. Work the main session does itself, agents that are already running, and launches you approved before the usage reached the line can spend the reserve before its release. Spend outside these hooks (claude.ai, other machines, sessions where pace is off) is not seen either. See The reserve stop does not catch work you do yourself.

The stop asks in inform and limit mode alike, and the away marker, or a permission mode where no one answers (auto, bypassPermissions, dontAsk), turns the question into a denial. A reserve of 0% turns the stop off. When the reserve cannot be computed, paceline status says reserve unknown: the stop is off and the hard limits work as before.

The five-hour stop

One profile key, five_hour_stop_pct (95% by default, 0 to 100), sets how close to its limit PaceLine lets the five-hour window run. From that usage an Agent or Workflow launch asks you first, the night queue waits, and the burn rate is projected to it. The value is the same in working hours and off-hours. A lower value keeps a margin; a higher one lets a burst take the window closer to its limit. Change it with paceline profile set five_hour_stop_pct 90 or in the settings view (/paceline:settings pane). The reference lists the key.

The weekly reserve is a separate setting: it is kept per account (see the weekly reserve).

The weekly simulation

paceline simulate replays one weekly window through the same budget code that paceline status runs, hour by hour, 168 steps, so you can see what your profile does to a week.

What the simulated operator does, each hour:

  • It builds an exact reading: the weekly usage so far, and a five-hour usage that is the spend of the last five hours over five_hour_to_week_pct, with the five-hour reset three hours ahead.
  • In a working hour it spends the hour's budget times the week's factor, never more than five_hour_to_week_pct / 5 per hour, and nothing while the recommendation blocks.
  • With a night queue it also spends the off-hours part's whole allowance over the hours of that part. With the default off-hours mark of 0 the allowance is 0, so the queue spends nothing until the plan marks the night.

The four week shapes:

  • on-track: the factor is 1 in every working hour.
  • heavy-start: the factor is 2 in the window's first 72 hours, then 1. It shows how the budget re-plans after an early overspend.
  • light-start: the factor is 0.5 in the first 72 hours, then 1. It shows how the budget re-plans after an early underspend.
  • away-thu-fri: the factor is 0 in the working hours of local Thursday and Friday, then 1. It shows how the budget re-plans when two working days go unused.

It is a model: one reading per hour, a rolling five-hour sum instead of Claude Code's fixed windows, no dated marks and no holds (the working hours and the weekday template come from your plan file), free memory pinned at 64 GiB and data age at 0, a night queue that spends its whole allowance, and week shapes that are synthetic, not your history. The same inputs give the same figures on one Python version, and the last digit can differ between versions.

The reset day changes the figures. The release day counts back from the account's own reset, and the week's days fall differently on it, so an account that resets on Friday evening releases its reserve on another day from one that resets on Monday morning. The recommendation

The recommendation says whether new work is blocked. It names no model and no number of agents.

  • Blocked. No new work starts when the memory guard is on and free memory is below min_free_commit_mb (2048 MiB), when five-hour usage reaches five_hour_stop_pct (95%), or when the weekly limit is used up. paceline status --json shows recommendation.blocked and its reasons.
  • Five-hour burn. The recent burn rate of the five-hour window is a measured fact, shown in paceline status --json as five_hour.burn. It changes no recommendation and makes no launch ask. The five-hour burn rate describes the measurement.
  • Heavy runs (not part of the recommendation). While the memory guard is on, paceline status --json shows under host the number of heavy runs the memory allows, max_heavy_runs: min(max_heavy_runs, (free memory - commit_reserve_mb) // heavy_job_mb), never below 0: 3 at most by default. With the guard off the figure is not computed.

The memory guard (memory_guard, off by default; turn it on with paceline profile set memory_guard true) decides whether free memory counts at all. With it off, no launch, night allowance or paceline auto answer depends on memory, and memory is measured only when paceline status runs without a launch key, as it does when you run it to read it, or when paceline doctor runs. Free memory is free commit on Windows, kern.memorystatus_level times physical memory on macOS, and MemAvailable on Linux. When it cannot be measured while the guard is on, paceline status says host memory unknown, and the memory checks do not apply.

The five-hour burn rate

The budget per hour spreads the weekly limit, and the five-hour window can still fill faster than the time left allows. pace therefore projects the recent burn rate of the window to the five-hour stop, five_hour_stop_pct (95% by default), in working hours and off-hours alike.

  • Rate. The rise of the five-hour percentage over the last 90 minutes, in percentage points per hour. The base is the reading held 90 minutes ago, or the first reading of the window when the window is younger. Only readings of the current window count. There is no rate until the base lies at least 10 minutes back, so a fresh window, or a machine with no history yet, shows no burn state.
  • Budget rate. (stop - used) / hours to the reset: the even pace that reaches the five-hour stop exactly at the reset.
  • Burn state. The data is fresh, the reset is known, usage is below the five-hour stop, a rate is measured, and the rate is above the budget rate, so the window would reach the stop before the reset. limited in five_hour.burn is then true.
  • Night queue. Only paceline auto acts on the burn state: it lowers max_parallel_agents to the share of the rate that the window's budget covers, down to 0, and waits at 0. The burn never makes a launch ask.
  • Where it shows. paceline status --json shows the burn under five_hour.burn; paceline status text does not state it; in limit mode the pace: line gives it as the recent rate.

The burn is a measured fact only. paceline status --json shows the figures as five_hour.burn, which is null while no rate is measured: with too few readings, stale data, or usage at or above the five-hour stop. The budget simulator has no history, so it shows no burn.

PaceLine publishes the same figures for other readers; see The five-hour burn file (for readers).

The confirmation at a hard limit

In limit mode the hook before every Agent and Workflow launch gives the model one plain pace: line: where the current part stands against its share, what the share allows per hour, and each safety stop within reach. In inform mode the model reads nothing, unless a stop holds the launch. The hook asks you to confirm the launch when one of these holds:

  • The memory guard is on and free memory is below min_free_commit_mb. This is measured at every launch. It also holds while the session's account is not known and no weekly reading exists: the free-memory floor then applies, the five-hour and weekly stops act on the highest fresh figures of any account on this machine (nothing to stop on without a fresh one), and the plan gate and the budget wait for data. With the guard off, memory is not measured and this limit never applies.
  • With fresh data only: five-hour usage is at or above the five-hour stop, 95% by default in all hours, or the weekly limit is used up.
  • Before the reserve's release instant, in inform and limit mode alike, and on stale data too: the week's usage is at or past 100% minus the reserve (92% with the default 8%; 91% passes), in whole points as Claude Code reports them. The reason names the reserve, its name if it has one, and when it opens, for example weekly reserve 8 % kept until Fri 30 09:00. A reserve of 0%, a released reserve and a reserve that cannot be computed (reserve unknown: the stop is off) never ask; the other limits do not depend on it.
  • With fresh data only, and only in limit mode: the current part is planned and its spending is more than 1 point above the part of its share that the clock allows by now (the share times the elapsed fraction of the part). An unplanned part never asks. In inform mode, the default, or while paceline mode inform --until-part-end holds, the plan only shows in paceline status and in PitBoard's Week card, which shows the deviation from the plan (see PitBoard's explanation), and the model reads nothing about it.

The reason goes in front of the tool's description, so it shows in every permission prompt. A hard limit's reason starts with pace hard limit:, the reserve's with pace reserve: and a plan's with pace plan:; when several hold, their reasons follow in that order and the first sets the prefix. When a stop or the plan holds the launch, the model also reads what holds it, what that means for its launches and that it must not retry a declined launch; with the owner away it reads that the launch was refused because the owner cannot confirm it. When pace has no usage data or fails, the hook adds no line and the launch goes ahead, unless the memory guard is on and free memory is below its floor.

While the away marker is set, the hook denies the launch instead of asking. It also denies in the auto, bypassPermissions and dontAsk permission modes, where no one answers the prompt: in auto the auto-mode classifier, not you, approves the question and the launch would run past the stop. The reason then says which mode holds the launch and that switching the session to the default (Manual) mode lets you confirm it, and the model is told to tell you what holds the launch and not to retry. In default, acceptEdits and plan mode, or when Claude Code sends no mode, the hook still asks. See The away marker.

The first plan question of a part names the command that stops them until the part ends, paceline mode inform --until-part-end; later questions in the same part do not repeat it. A hard limit never depends on the mode or the plan.

The away marker

A permission prompt that nobody answers holds the session, and the prompt cache can expire while it waits. When you leave, /paceline:away (or paceline away on) sets the away marker. While it is set, a launch that would ask, at a hard limit, past the weekly reserve's stop line, or over a part's share in limit mode, is denied instead. The denial names the reason and tells the agent that you are away and that it must not retry: after the reserve it waits for the release, and after a hard limit it waits for the limit to clear.

  • One file, <state>/away.json, serves every session on the machine.
  • Your next message in any session clears the marker, so you do not need to turn it off. A cache-watch wake does not clear it, nor does the /paceline:away command that sets it, nor a prompt from a schedule, a loop, a notification, another session or a channel.
  • paceline away off clears it by hand, and paceline away status shows whether it is set, since when, and by which session.
  • The marker has no expiry, and it changes nothing while no hard limit holds, the week's usage is short of the reserve's stop line and the plan, in limit mode, is not over its share. See The away marker has no expiry and A prompt through the Agent SDK leaves the away marker.

The forecast

The forecast is the share of the week that would be left unused at the reset if the burn rate of the last 24 hours continued. It needs at least two history points in the current weekly window, 3 hours or more apart; without them, paceline status shows no forecast.

The night allowance

The night is tonight's off-hours part of the week plan: the part that is running when you are in off-hours, else the one after today's working hours. The allowance for the night queue is the smallest of these, never below 0:

  • The part's share: its fixed share minus what the part has spent while it runs, or its provisional share (what the weights of the parts after it would give it now) before it starts.
  • The night's capacity: its hours × five_hour_to_week_pct / 5 × five_hour_stop_pct.
  • 0 while the memory guard is on and free memory is below min_free_commit_mb; otherwise (including with the guard off, the default) this bound does not apply.
  • Nothing else is kept back. The default off-hours mark is 0, so the allowance is 0 until you mark the night, for example paceline plan set 2026-10-29 --off-hours 0.5 (the date of tonight); paceline queue add says so, with the command for the date, when tonight's share is 0.

Holds

A hold records work that has started but whose cost has not shown in the weekly usage yet. While pace is on, its hooks place one for each subagent, at subagent_estimate_pct (1%), and release it when the subagent stops. You hold budget for gates and other work by hand with paceline hold acquire; paceline queue start places a hold for a queue item.

The outstanding share is the sum of the active estimates minus the weekly usage added since the earliest of them was acquired, never below 0. Only the night queue subtracts it from its budget; the budget per hour does not change.

A hold ends when it is released, when its lease expires (30 minutes, or 240 minutes for a subagent's keyed hold), or when its process is gone. At session end, the hook records the end and releases the session's holds; when Claude Code's time for session-end hooks cuts it off, the next pace call releases them (see limitations). The released hold records its actual cost: the change in weekly usage since it was acquired.

The Agent and Workflow hook also records a launch hold for every launch it allows or asks about. It is recorded under the same lock that counts the active holds, so the launches of one assistant message see each other, and the nth gate counts the n-1 launches before it, those of other sessions too. A launch hold carries no estimate, never reaches the history that calibration reads, and ends after 60 seconds. The start of an agent takes over the oldest launch hold of its session, so a started agent counts once; a Workflow holds one launch for all its agents, and the first start takes it over. A launch denied because you are away releases its hold at once; a launch that you decline in a prompt keeps it until it ends. paceline hold list shows it. See Launch holds rest on the order of Claude Code's hooks.

The night queue's decisions

A night run starts with paceline auto --start-run, which fixes the night allowance, the end of the off-hours part and the weekly usage the run counts from. Before each item, the agent runs paceline auto. Its budget for the next item is the allowance minus what the run has spent minus the outstanding holds.

To walk through the same decisions one step at a time, answer the questions below.

  1. Does PaceLine hold usage readings for the signed-in account?
    1. No: Wait (exit 10): no figures can be computed until a reading arrives. A run that started under another account stops instead.
    2. Yes: Did you start the run with paceline auto --start-run?
      1. No: Stop (exit 11): no run was started.
      2. Yes: Is the signed-in account the one the run started under?
        1. No: Stop (exit 11): account changed during the run. auto checks the account before every other stop.
        2. Unknown: Wait (exit 10): account unknown. The stops below still come first: the memory floor (while the memory guard is on), the end of the night, and the queue's own stops (empty, every remaining item needs the owner's permission, or the night budget is spent with nothing running).
        3. Yes: Is the memory guard off or free memory at or above the floor, and is the night still on?
          1. No: Stop (exit 11): the memory guard is on and free memory is below the floor, or the night is over.
          2. Yes: What does the queue hold?
            1. Nothing left to start: Stop (exit 11): the queue is empty, every remaining item is deferred or blocked, or the next item does not fit the budget and nothing is running.
            2. Work in progress: Wait (exit 10): items are running or dependencies are pending. Run paceline auto again later.
            3. An item is ready: Is the data fresh and is five-hour usage below the stop?
              1. No: Wait (exit 10): the data is stale, or five-hour usage is at or above the stop (five_hour_stop_pct, 95% by default; wait_until says when the window resets).
              2. Yes: Does the five-hour burn rate leave room for at least one agent?
                1. No: Wait (exit 10): at the recent rate the five-hour window would reach the stop (95% by default) before it resets, and the burn leaves room for no agent (max_parallel_agents 0). wait_until is the five-hour reset. Run paceline auto again later: a slower burn lets the queue start.
                2. Yes: Start (exit 0): run paceline queue start <id> for the item in the output. max_parallel_agents is lower than without the burn when the five-hour window would still reach the stop before the reset.
  • Start (exit 0): the first pending item, in queue order, whose dependencies are done, that fits the budget, and that may run beside the running items. Only independent items run side by side. auto advises min(max_agents, heavy runs) agents, or min(max_agents, 3) when the memory guard is off or memory is unknown, and at least 1; the five-hour burn can lower it, down to 0 (see Wait).
  • Wait (exit 10): running items or unfinished dependencies; stale data; five-hour usage at the five-hour stop, with wait_until set to the five-hour reset; a five-hour burn that would reach the stop before the window resets and leaves room for no agent (max_parallel_agents 0), with wait_until set to the five-hour reset too; no usage data at all; or the account cannot be resolved (account unknown).
  • Stop (exit 11): no run was started; free memory below the floor while the memory guard is on; the off-hours part has ended; the queue is empty; every remaining item is deferred or depends on a deferred item; the next item does not fit the budget and nothing is running; or the signed-in account is not the one the run started under (account changed during the run). auto checks the account before every other stop, and stops at once, because the new account may have no readings yet. A run started with no known account is not checked.

auto names no model: the orchestrator picks the model of each item, and reads the model-scoped weekly buckets in weekly.scoped of paceline status --json; a model whose scoped weekly limit is at 100% cannot run. When five-hour usage is at or above 85% and the data is older than 125 seconds, auto merges the inbox first, so a window that has already filled is not missed.

In auto, the burn rate is projected to five_hour_stop_pct, the same stop as in working hours. The burn lowers max_parallel_agents, and when no agent fits, auto waits; the burn reason joins reasons. The queue calls auto before each item, so a burn that slows lets it start again before the reset.

The leftover pool runs only on the last night before the weekly reset, only when it was approved for the current weekly window, and only when the queue has no item to start. Its items share the run's budget.

After the run, the agent writes a morning report from templates/morning-report.md, a template it fills from paceline queue report and the queue's state.
