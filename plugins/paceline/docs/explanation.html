How PaceLine works

This page explains where PaceLine's numbers come from and how pace turns them into a budget, a recommendation, and the night queue's decisions. For the exact commands and keys, see the reference. To try the budget with your own numbers, open the budget simulator.

Where usage readings come from

pace works from one file, the limits file <state>/rate-limits.json. Two kinds of reading reach it through the inbox, <state>/inbox/:

  • Session readings. With each model turn, Claude Code hands plugins the five-hour and weekly readings that the session's own request carried. PaceLine's module writes them to the session's inbox file when they change, and an unchanged reading at most once a minute. This part, the limits writer, is always on.
  • Exact readings. While usage-watch is on, PaceLine asks Claude Code for the account's own usage, the figures /usage shows, with the model-scoped weekly limits. Claude Code adds the session's claude.ai login to the request; PaceLine never sees a token. The answer goes to <state>/inbox/usage-watch-<key>.json, one file per account (unknown when none is known).

A merge takes the inbox into the limits file. The hooks module checks the inbox when Claude Code starts and then every 15 seconds while a session is open, and merges any change. A pace command merges first when the data is older than usage_snapshot_max_age_sec (300 seconds). The pace: line before an Agent launch uses the limits file as it stands, without a merge.

Which account a reading belongs to

Two accounts can share one configuration directory, so one limits file. The writers tag each reading with the key of the account signed in at the moment they write it. The key is the first 16 hex digits of a SHA-256 hash of the account and organization identifiers in Claude Code's .claude.json; it cannot be turned back into either identifier, and PaceLine stores nothing else from the file. The merge puts each account's readings into a partition of its own, accounts[<key>], and mirrors the newest partition at the top level for readers that know nothing of accounts. Readings with no key go to the partition unknown.

Every reader resolves the signed-in account itself and uses only that account's partition. When the account has no partition yet, it uses unknown and marks the figures account unknown; when there is neither, pace says no usage data yet for the signed-in account. When the account cannot be resolved at all, the reader takes the top level and marks it the same way. The history keeps one line per partition that changed, with its account, and pace's forecast and calibration count only the signed-in account's lines.

After /login or /logout, the module holds back a reading whose limits equal the ones it held before the command while the account differs from the held one: Claude Code may still carry the old account's limits in the next request, and they must not be tagged with the new account.

A partition that no reading has touched for 7 days goes at the next merge, except the newest one, which stays however old. Signing in again to an account whose partition remains shows its last figures at once, dated by their age.

How usage-watch paces its requests

Every open session with PaceLine checks at its start and then every 10 seconds whether a request is due: one is due when 125 seconds have passed since the last reading. The sessions of one account share that schedule through <state>/usage-watch.state-<key>.json, so one reading serves them all; sessions of different accounts each have their own schedule and get their own reading every 125 seconds. After an HTTP 429 answer, usage-watch waits one interval; after any other error, it waits 10 minutes. The switch is read on every check, so turning usage-watch on or off takes effect within 10 seconds, with no restart.

usage-watch needs a claude.ai login and an open session. When Claude Code gives no login for the request, usage-watch sends nothing. While CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC is set, Claude Code refuses the request, and usage-watch records network error.

Why the numbers can lag /usage

  • A session reading arrives with the session's own request, so it trails the account by one request. It changes only when a session on this machine takes a turn. Usage from another machine or from claude.ai shows up after the next local turn.
  • pace dates the limits file by its oldest live bucket. When that age passes stale_threshold_min (30 minutes), the data is STALE: the hard limits on the five-hour and weekly windows are skipped, and the night queue waits.
  • With usage-watch on and any session open, the data is at most about two and a half minutes old: 125 seconds between requests plus up to 15 seconds to the merge.
  • For 15 minutes after an exact reading, session readings leave that bucket alone. The inbox rules give the full merge rule.

Day, night, and off hours

Every wall-clock rule uses the profile's time zone. The weekly window ends at the reported weekly reset and starts 7 days earlier. pace sorts each hour of the window into one kind:

Kind Hours by default Budget
night00:00 to 08:00 (night_hours)None; the night queue has its own allowance
weekdayMonday to Friday, 08:00 to 22:00 (day_hours)Weight weekday_weight
weekendSaturday and Sunday, 08:00 to 22:00Weight weekend_weight, within weekend_cap_pct
offEvery other hour, 22:00 to 24:00 by defaultNone

Declared plans change the weight of day hours: an away plan sets it to 0, and a heavy plan multiplies it by the plan's weight (heavy_weight, 2, by default). Where plans overlap, the later declaration wins.

The budget per hour

pace computes the budget in these steps:

  1. Effective weekly usage. The weekly reading, or a model-scoped weekly bucket that matches the current model when that is higher. Model-scoped buckets come only from usage-watch, and only count when pace knows the model (--model, PACELINE_MODEL, or ANTHROPIC_MODEL).

  2. What is left. 100% minus the effective usage.

  3. The reserve. reserve_pct (8%) is held back until the last reserve_decay_start before the reset (Friday 18:00 by default). From then it falls in a straight line to 0 at the reset.

  4. Spendable. What is left minus the reserve, never below 0.

  5. The split. pace spreads the spendable share over the remaining day hours up to the reset, in proportion to each hour's weight. No hour gets more than its capacity, five_hour_to_week_pct / 5 percent of the week (2% by default); what a capped hour cannot take goes to the others. When the spendable share covers every hour's capacity, each hour gets its capacity.

  6. The weekend cap. The weekend day hours get at most weekend_cap_pct (20%) together, minus what the current weekend's day hours have already spent. Weekend nights are not counted against the cap. The rest goes to the weekday hours.

  7. The budget. The share of the current hour, or of the next day hour with a weight above 0 when the current hour is a night, off, or away hour.

To move these steps with your own numbers, open the budget simulator.

The split starts from what remains now, so a past absence creates no lag to catch up.

The norm is the same split of 100 - reserve_pct over the whole weekly window, without plans: the even rate for a week used from start to end. paceline status shows the norm for the kind of hour the budget belongs to, for example budget 1.45%/h (weekday norm 1.03).

paceline status also warns when what remains of the week reaches capacity_warn_ratio (0.9) of what the remaining day hours can spend at the day threshold: the remaining day hours can then barely use what is left.

The recommendation

pace compares the budget with the norm: ratio = budget / norm.

  • Blocked. No new work starts when free memory is below min_free_commit_mb (2048 MiB), when five-hour usage reaches five_hour_hard_stop (95%), or when the weekly limit is used up. The recommendation is then 0 agents and model none.
  • Background paused. When five-hour usage reaches the current threshold, the recommendation is 0 agents until the five-hour window resets. The threshold is five_hour_threshold_night (95%) during the night hours and five_hour_threshold_day (80%) at every other hour.
  • Agents. Otherwise, round(2 × ratio), at least 1 and at most max_agents (6). At the norm, that is 2 agents.
  • Five-hour burn. When the five-hour window, at its recent burn rate, would reach the current threshold before it resets, the agent count falls to the share of the rate that the window's budget covers, down to 0. The five-hour burn rate describes the measurement.
  • Throttle. When the ratio is below 0.7, or when weekly usage has reached throttle_weekly_pct (85%) with more than 24 hours left to the reset, the allowed models are routine_models (sonnet, haiku) instead of models.
  • Model. The first allowed model. A model whose model-scoped weekly bucket has reached scoped_exhausted_pct (95%) is left out.
  • Heavy runs. min(max_heavy_runs, (free memory - commit_reserve_mb) // heavy_job_mb), never below 0: 3 at most by default.

Free memory is free commit on Windows, kern.memorystatus_level times physical memory on macOS, and MemAvailable on Linux. When it cannot be measured, paceline status says host memory unknown, and the memory checks do not apply.

The five-hour burn rate

The budget per hour spreads the weekly limit, and the five-hour window can still fill faster than the time left allows. pace therefore projects the recent burn rate of the window to the current threshold: five_hour_threshold_day (80%) by day and five_hour_threshold_night (95%) during the night hours.

  • Rate. The rise of the five-hour percentage over the last 90 minutes, in percentage points per hour. The base is the reading held 90 minutes ago, or the first reading of the window when the window is younger. Only readings of the current window count. There is no rate until the base lies at least 10 minutes back, so a fresh window, or a machine with no history yet, shows no burn state.
  • Budget rate. (threshold - used) / hours to the reset: the even pace that reaches the threshold exactly at the reset.
  • Burn state. The data is fresh, the reset is known, usage is below the threshold, a rate is measured, and the rate is above the budget rate, so the window would reach the threshold before the reset. limited in five_hour.burn is then true.
  • Agent cap. In the burn state the agent count becomes floor(agents × budget_share), where budget_share is the budget rate over the rate, not rounded. A mild overshoot keeps some agents, and a steep one gives 0. With 1 agent, any burn state gives 0. A recommendation that is already blocked or paused stays as it is.
  • Reason. paceline status and the pace: line before a launch add the reason, for example 5h burn 42.7%/h vs budget 13.9%/h: 80% at 2026-10-16 19:40+03:00, before reset 2026-10-16 21:15+03:00.

Outside the burn state the agent count, the model, and the status line are as without the rule: with a safe projection, too few readings, stale data, or usage at or above the threshold. paceline status --json shows the figures as five_hour.burn, which is null while no rate is measured, and the cap as recommendation.five_hour_burn_limited. The budget simulator has no history, so it never shows the burn state.

PaceLine publishes the same figures for other readers; see The five-hour burn file (for readers).

The confirmation at a hard limit

While pace is on, the hook before every Agent and Workflow launch adds the pace: line. It also asks you to confirm the launch when one of these holds:

  • Free memory is below min_free_commit_mb. This is measured at every launch.
  • With fresh data only: five-hour usage is at or above the current threshold, 80% by day and 95% at night, or the weekly limit is used up.
  • With fresh data only: the five-hour burn state holds (see The five-hour burn rate) and the launch goes over the agent cap, that is, the active reservations of all sessions are at or above max_parallel_agents. A cap of 0 asks for every launch. Within the cap the burn is advice only. A reservation of an agent that never reported its stop counts until its lease ends (agent_lease_ttl_min, 240 minutes), so a crashed agent can keep the count up for that long.

The reason goes in front of the tool's description, so it shows in every permission prompt. A hard limit's reason starts with pace hard limit: and a burn's with pace 5h burn:; when both hold, the burn reason follows the hard limit's. Everything else stays advice. When pace has no usage data or fails, the hook adds nothing and the launch goes ahead.

While the away marker is set, the hook denies the launch instead of asking. See The away marker.

The away marker

A permission prompt that nobody answers holds the session, and the prompt cache can expire while it waits. When you leave, /paceline:away (or paceline away on) sets the away marker. While it is set, a launch that would ask, at a hard limit or over the agent cap in the burn state, is denied instead. The denial names the reason and tells the agent that you are away and that it must not retry: after a burn it continues within the cap or waits, and after a hard limit it waits for the limit to clear.

  • One file, <state>/away.json, serves every session on the machine.
  • Your next message in any session clears the marker, so you do not need to turn it off. A cache-watch wake does not clear it, nor does the /paceline:away command that sets it, nor a prompt from a schedule, a loop, a notification, another session or a channel.
  • paceline away off clears it by hand, and paceline away status shows whether it is set, since when, and by which session.
  • The marker has no expiry, and it changes nothing while no hard limit holds and the burn stays within the cap. See The away marker has no expiry and A prompt through the Agent SDK leaves the away marker.

The forecast

The forecast is the share of the week that would be left unused at the reset if the burn rate of the last 24 hours continued. It needs at least two history points in the current weekly window, 3 hours or more apart; without them, paceline status shows no forecast. On Thursday and Friday, a forecast above leftover_suggest_pct (10%) adds the suggestion to propose leftover tasks.

The night allowance

The night is the current night hours, or the next ones when the clock is outside them, cut at the weekly reset. The allowance for the night queue is the smallest of these, never below 0:

  • night_base_pct (5%) plus the surplus: the spendable share minus what the norm would spend in the remaining day hours.
  • The night's capacity: its hours × five_hour_to_week_pct / 5 × five_hour_threshold_night.
  • host_night_capacity_pct, when set; 0 while free memory is below min_free_commit_mb.
  • The spendable share minus what the next day's day hours are allocated. On the last night before the reset, nothing is kept for the next day.

Reservations

A reservation records work that has started but whose cost has not shown in the weekly usage yet. While pace is on, its hooks hold one for each subagent, at subagent_estimate_pct (1%), and release it when the subagent stops. You reserve gates and other work by hand with paceline reserve acquire; paceline queue start reserves for a queue item.

The outstanding share is the sum of the active estimates minus the weekly usage added since the earliest of them was acquired, never below 0. Only the night queue subtracts it from its budget. The pace: line shows the number of active reservations; the budget per hour does not change.

A reservation ends when it is released, when its lease expires (30 minutes, or 240 minutes for a subagent's keyed reservation), or when its process is gone. At session end, the hook records the end and releases the session's reservations; when Claude Code's time for session-end hooks cuts it off, the next pace call releases them (see limitations). The released reservation records its actual cost: the change in weekly usage since it was acquired.

The Agent and Workflow hook also records a launch reservation for every launch it allows or asks about. It is recorded in the same lock hold that counts the active reservations, so the launches of one assistant message see each other, and the nth gate counts the n-1 launches before it, those of other sessions too. A launch reservation carries no estimate, never reaches the history that calibration reads, and ends after 60 seconds. The start of an agent takes over the oldest launch reservation of its session, so a started agent counts once; a Workflow holds one launch for all its agents, and the first start takes it over. A launch denied because you are away releases its reservation at once; a launch that you decline in a prompt keeps it until it ends. paceline reserve list shows it. See Launch reservations rest on the order of Claude Code's hooks.

The night queue's decisions

A night run starts with paceline auto --start-run, which fixes the night allowance and the weekly usage the run counts from. Before each item, the agent runs paceline auto. Its budget for the next item is the allowance minus what the run has spent minus the outstanding reservations.

To walk through the same decisions one step at a time, answer the questions below.

  1. Does PaceLine hold usage readings for the signed-in account?
    1. No: Wait (exit 10): no figures can be computed until a reading arrives. A run that started under another account stops instead.
    2. Yes: Did you start the run with paceline auto --start-run?
      1. No: Stop (exit 11): no run was started.
      2. Yes: Is the signed-in account the one the run started under?
        1. No: Stop (exit 11): account changed during the run. auto checks the account before every other stop.
        2. Unknown: Wait (exit 10): account unknown. The stops below still come first: the memory floor, the end of the night, and the queue's own stops (empty, every remaining item needs the owner's permission, or the night budget is spent with nothing running).
        3. Yes: Is free memory at or above the floor, and is the night still on?
          1. No: Stop (exit 11): free memory is below the floor, or the night is over.
          2. Yes: What does the queue hold?
            1. Nothing left to start: Stop (exit 11): the queue is empty, every remaining item is deferred or blocked, or the next item does not fit the budget and nothing is running.
            2. Work in progress: Wait (exit 10): items are running or dependencies are pending. Run paceline auto again later.
            3. An item is ready: Is the data fresh, is five-hour usage below its threshold, and does an allowed model have weekly headroom?
              1. No: Wait (exit 10): the data is stale, five-hour usage is at or above its threshold (80% by day by default; wait_until says when the window resets), or no allowed model has headroom.
              2. Yes: Does the five-hour burn rate leave room for at least one agent?
                1. No: Wait (exit 10): at the recent rate the five-hour window would reach the night threshold (95% by default) before it resets, and the agent cap is 0. wait_until is the five-hour reset. Run paceline auto again later: a slower burn lets the queue start.
                2. Yes: Start (exit 0): run paceline queue start <id> for the item in the output. max_parallel_agents is lower than without the burn when the five-hour window would still reach the night threshold before the reset.
  • Start (exit 0): the first pending item, in queue order, whose dependencies are done, that fits the budget, and that may run beside the running items. Only independent items run side by side. auto advises min(max_agents, heavy runs) agents, or min(max_agents, 3) when memory is unknown, and at least 1; the five-hour burn can lower it, down to 0 (see Wait).
  • Wait (exit 10): running items or unfinished dependencies; stale data; five-hour usage at the threshold or the hard stop, whichever is lower, with wait_until set to the five-hour reset; a five-hour burn that would reach the night threshold before the window resets and leaves a cap of 0 agents, with wait_until set to the five-hour reset too; no allowed model with weekly headroom for the item; no usage data at all; or the account cannot be resolved (account unknown).
  • Stop (exit 11): no run was started; free memory below the floor; the night is over; the queue is empty; every remaining item is deferred or depends on a deferred item; the next item does not fit the budget and nothing is running; or the signed-in account is not the one the run started under (account changed during the run). auto checks the account before every other stop, and stops at once, because the new account may have no readings yet. A run started with no known account is not checked.

In auto, the throttle depends only on weekly usage: at throttle_weekly_pct with more than 24 hours to the reset, the allowed models are routine_models. When five-hour usage is at or above auto_refresh_five_hour_pct (85%) and the data is older than auto_refresh_cache_sec (125 seconds), auto merges the inbox first, so a window that has already filled is not missed.

In auto, the burn rate is projected to five_hour_threshold_night at any hour, because a night run answers to the night threshold. The agent count is capped as in The five-hour burn rate, and the burn reason joins reasons. The queue calls auto before each item, so a burn that slows lets it start again before the reset.

The leftover pool runs only on the last night before the weekly reset, only when it was approved for the current weekly window, and only when the queue has no item to start. Its items share the night budget and are also limited to the surplus at the start of the run, minus what the pool has already started.

After the run, the agent writes a morning report from templates/morning-report.md, a template it fills from paceline queue report and the queue's state.
