Як працює PaceLine

Ця сторінка пояснює, звідки беруться числа PaceLine і як pace перетворює їх на бюджет, рекомендацію та пораду для роботи без нагляду. Точні команди і ключі наведено в довіднику. Щоб спробувати бюджет на власних числах, відкрити симулятор бюджету; щоб програти весь тиждень через бюджет, запустити paceline simulate.

Звідки беруться показники використання

pace працює з одним файлом, файлом лімітів <state>/rate-limits.json. Туди через inbox, <state>/inbox/, надходять показники двох видів:

  • Показники сесії. З кожним ходом моделі Claude Code передає плагінам п'ятигодинні й тижневі показники, які несе власний запит сесії. Модуль PaceLine записує їх у файл inbox сесії, коли вони змінюються, а незмінний показник — щонайбільше раз на хвилину. Ця частина, запис лімітів, працює завжди.
  • Точні показники. Поки usage-watch увімкнено, PaceLine запитує в Claude Code власне використання акаунта, тобто ті самі числа, що показує /usage, разом із тижневими лімітами окремих моделей. Claude Code додає до запиту вхід сесії через claude.ai; токена PaceLine ніколи не бачить. Відповідь потрапляє в <state>/inbox/usage-watch-<key>.json, окремий файл для кожного акаунта (unknown, коли акаунт невідомий).

Злиття переносить inbox у файл лімітів. Модуль hooks перевіряє inbox на старті Claude Code, далі кожні 15 секунд, поки сесія відкрита, і зливає будь-яку зміну. Команда pace спершу виконує злиття, коли дані старші за 300 секунд. Рядок pace: перед запуском Agent використовує файл лімітів як є, без злиття.

Якому акаунту належить показник

Два акаунти можуть ділити один каталог конфігурації, а отже й один файл лімітів. Модуль PaceLine позначає кожен показник ключем акаунта, якому належать облікові дані сесії. На старті сесії, після /login або /logout і коли збережені облікові дані змінюються, він запитує в endpoint профілю Claude Code акаунт входу сесії та зберігає з відповіді лише односторонній ключ ідентифікаторів акаунта й організації: перші 16 шістнадцяткових цифр хешу SHA-256, за яким жоден із ідентифікаторів не відновлюється. До першої відповіді сесія показників не записує. Коли endpoint відхиляє запит або три запити поспіль завершуються помилкою, модуль бере акаунт, названий у .claude.json Claude Code; винятком є Claude Code Desktop і процес, запущений із нього, чий .claude.json називає останній термінальний вхід, тож така сесія показників не записує. Змінні акаунта, які задає Desktop, не використовуються ніколи: claude, запущений із термінальної вкладки Desktop, успадковує їх, хоча його власний вхід може бути іншим акаунтом. Злиття розкладає показники кожного акаунта в окремий розділ, accounts[<key>], і дублює найновіший розділ на верхній рівень для програм, які про акаунти нічого не знають. Показники без ключа потрапляють до розділу unknown.

Кожна програма, що читає файл, використовує лише розділ акаунта своєї сесії. Модуль записує цей акаунт для кожної сесії у <state>/session-accounts/<session id>.json і передає його командам, які запускає; команда paceline у Bash tool сесії читає запис цієї сесії, а команда поза будь-якою сесією бере акаунт, названий у .claude.json. Якщо в акаунта ще немає розділу, програма бере unknown і позначає показники account unknown; якщо немає й цього, pace пише no usage data yet for the signed-in account. Поки акаунт сесії не відомий або не може бути відомий (pending, desktop, logged-out), програма не показує жодних показників, а не чужого акаунта. Історія містить по одному рядку на кожен змінений розділ, з його акаунтом; прогноз і калібрування pace враховують лише рядки цього акаунта.

Після /login або /logout модуль затримує показник, чиї ліміти дорівнюють тим, що він тримав до команди, поки акаунт відрізняється від збереженого: Claude Code може ще передати в наступному запиті ліміти старого акаунта, і їх не можна позначати новим акаунтом.

Розділ, який жоден показник не оновлював 7 днів, прибирається на наступному злитті, крім найновішого, який лишається за будь-якого віку. Повторний вхід в акаунт, чий розділ лишився, одразу показує його останні числа з позначкою їхнього віку.

Як usage-watch розподіляє запити

Кожна відкрита сесія з PaceLine на старті, а далі кожні 10 секунд перевіряє, чи настав час запиту: він настає, коли від останнього показника минуло 125 секунд. Сесії одного акаунта ділять цей розклад через <state>/usage-watch.state-<key>.json, тож один показник обслуговує їх усі; сесії різних акаунтів мають власний розклад і отримують власний показник кожні 125 секунд. Після відповіді HTTP 429 usage-watch чекає один інтервал; після будь-якої іншої помилки — 10 хвилин. Перемикач читається під час кожної перевірки, тож увімкнення або вимкнення usage-watch набуває чинності протягом 10 секунд, без перезапуску.

usage-watch потребує входу через claude.ai і відкритої сесії. Коли Claude Code не дає входу для запиту, usage-watch нічого не надсилає. Поки задано CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC, Claude Code відхиляє запит, і usage-watch записує network error.

Чому числа можуть відставати від /usage

  • Показник сесії надходить із власним запитом сесії, тож відстає від акаунта на один запит. Він змінюється лише тоді, коли сесія на цій машині робить хід. Використання з іншої машини або з claude.ai з'являється після наступного локального ходу.
  • pace датує файл лімітів за найстарішим живим bucket. Коли цей вік перевищує 30 хвилин, дані стають STALE: жорсткі ліміти п'ятигодинного і тижневого вікон не застосовуються, і порада — чекати.
  • З увімкненим usage-watch і будь-якою відкритою сесією вік даних щонайбільше приблизно дві з половиною хвилини: 125 секунд між запитами плюс до 15 секунд до злиття.
  • Протягом 15 хвилин після точного показника показники сесій не чіпають цей bucket. Повне правило злиття наведено в правилах inbox.

Для кого pace

pace окупається, коли тижневий ліміт вичерпується до скидання, коли працює багато агентів або Workflows, або коли потрібно використати весь тижневий ліміт. Профіль підбирають за тим, що показують PitBoard або /usage:

Профіль Ознаки в PitBoard або /usage Що підходить
A. Тижневого ліміту завжди вистачає, і більше використовувати не потрібноНа момент скидання картка Week показує Spare більше ніж на добу (близько 14 пунктів); 7d лишається сірим; /usage показує тижневий ліміт значно нижче 100% на момент скиданняpace додає мало. usage-watch вмикати лише заради точних чисел у PitBoard
B. Тижневий ліміт закінчується до скиданняOverspent жовтим або червоним посеред тижня; 7d жовтий від 80%, червоний від 95% до дня скидання; /usage показує, що тижневий ліміт вичерпано раноpace: бюджет на годину, тижневий резерв, утримуваний до дня відкриття, підтвердження, коли тиждень вичерпано
C. Сплески багатьох агентів заповнюють п'ятигодинне вікноКартка 5h limit показує Runs out або червоніє; Pace вищий за Budgetpace: рядок pace: перед кожним запуском у режимі limit, підтвердження від 95% п'ятигодинного вікна, утримання; usage-watch для свіжих даних
D. Потрібно використати весь тижневий лімітSpare близько скидання, хоча робота чекає; /paceline:pace status показує forecast unusedpace з тижневим планом, щоб остання ніч перед скиданням отримала те, що лишилося від тижня; usage-watch, щоб нічні дані лишалися свіжими
E. Агенти мають працювати за відсутності власникаБудь-що з наведеного плюс робота без наглядуpace з увімкненим usage-watch і машиною, яка не засинає; нічна черга є плагіном Stint (Нічна черга перейшла)

Сторінка початку роботи ставить три запитання: де зазвичай стоїть картка Week близько скидання (Spare більше ніж на добу, приблизно рівно, Overspent або ліміт вичерпано, або невідомо); одна сесія з кількома субагентами чи багато субагентів, Workflows або паралельних сесій; і чи мають агенти працювати за відсутності власника. Рекомендацію дає перше правило, що підходить:

  1. Невідомо, де стоїть картка Week: стежити за нею в PitBoard тиждень або ввімкнути pace і читати /paceline:pace status; /paceline:pace off скасовує це.
  2. Агенти мають працювати за відсутності власника: профілі D і E, pace з usage-watch і плагіном Stint.
  3. Overspent або ліміт вичерпано: профіль B, pace, а за багатьох агентів ще й п'ятигодинна межа профілю C і режим limit.
  4. Багато агентів: профіль C, pace і usage-watch.
  5. Приблизно рівно з кількома субагентами: pace необов'язковий; він тримає рівномірний темп і попереджає перед лімітами.
  6. Spare з кількома субагентами: профіль A; pace додає мало.

Робочі та неробочі години

Усі правила за настінним годинником використовують часовий пояс профілю. Тижневе вікно закінчується на повідомленому тижневому скиданні і починається на 7 днів раніше. pace ділить його на частини двох типів, по дві на кожен день: робочі години (☼) і неробочі години (☾), що йдуть за ними до наступного початку робочого дня. Кожна частина має позначку, а з неї випливає її частка від залишку:

Тип Типові години Бюджет
робочі години (☼)З 09:00 до 18:00 типово (work_hours у файлі плану)Частка залишку за позначкою частини (типово 1)
неробочі години (☾)Решта кожної доби, від кінця робочих годин до наступного початку робочого дняЧастка частини за її позначкою (типово 0: без бюджету, а робота без нагляду чекає)

Позначка — це off (0), light (0.5), normal (1), heavy (1.5) або число від 0 до 2 з кроком 0.25. paceline plan set позначає день, а paceline plan template set позначає день тижня для кожного тижня. Вага частини дорівнює її позначці, зменшеній, коли тиждень обрізає частину.

Частка частини фіксується на її початку: залишок на цей момент (100% мінус тижневе використання і резерв), помножений на вагу частини і поділений на суму ваг цієї частини та всіх наступних частин тижня. Використання після початку не змінює частку частини, що триває; воно змінює частки частин, які ще не почалися. Виняток — зміна позначки частини, що триває: вона ділить частину в цю мить, перша половина зберігає частку та витрату, а решта починається зараз за тим самим правилом від залишку тижня. Коли всі ваги 0, частина без плану: її бюджет дорівнює 0, і вона ніколи не запитує підтвердження.

Межа п'ятигодинного вікна не залежить від цих годин: five_hour_stop_pct однаковий у робочі години та в неробочі.

Бюджет на годину

pace обчислює бюджет за такими кроками:

  1. Ефективне тижневе використання. Тижневий показник або тижневий bucket для моделі, що відповідає поточній моделі, якщо він вищий. Buckets окремих моделей надходять лише від usage-watch і враховуються, лише коли pace знає модель (--model, PACELINE_MODEL або ANTHROPIC_MODEL). Частка частини і витрата нижче рахують лише звичайний тижневий показник.

  2. Залишок. 100% мінус ефективне використання.

  3. Резерв. Тижневий резерв (типово 8%, один на акаунт, задається командою paceline reserve) утримується цілком: план розподіляє лише те, що лишилося після нього. Він відкривається цілком на початку робочих годин дня відкриття, типово останнього дня перед скиданням, і з цього моменту план розподіляє відкритий резерв між рештою частин тижня за їхніми вагами. Після наступного скидання він знову утримується. До відкриття він також є захисною зупинкою: запуск, коли тижневе використання досягає або перевищує 100% мінус резерв, спершу запитує підтвердження, у цілих пунктах, як їх показує Claude Code.

  4. Доступне для витрати. Залишок мінус резерв, що ще утримується, але не менше 0.

  5. Частка. Частка поточної частини, зафіксована на її початку: залишок після резерву, що утримувався на її початку, помножений на вагу частини і поділений на суму ваг цієї частини та всіх наступних частин тижня (див. Робочі та неробочі години). Частина, що починається в момент відкриття резерву, фіксується без утримання, тож відкритий резерв розподіляється між нею і всіма наступними частинами. Частина з вагою 0 має частку 0. Коли всі ваги 0, частина без плану, і її бюджет дорівнює 0.

  6. Швидкість. Залишок частки (частка мінус те, що частина витратила від свого початку, але не менше 0), поділений на години, що лишилися в частині. Жодна година не отримує більше за свою місткість, five_hour_to_week_pct / 5 відсотка тижня (типово 2%).

  7. Бюджет. Швидкість або 0 у частині без плану. Частина, що витрачається в такт із годинником, отримує як бюджет свою частку, поділену на години; це водночас її норма.

Щоб переглянути ці кроки з власними числами для одного моменту, відкрити симулятор бюджету. Щоб програти цілий тиждень, запустити paceline simulate (див. тижневу симуляцію).

Частка фіксується на початку частини, тож перевитрату всередині частини не надолужують: бюджет зменшується, а наступні частини ділять залишок за своїми вагами.

Норма — частка частини, поділена на її години, рівномірна швидкість для частини, не більше five_hour_to_week_pct / 5. Частина з часткою 0 має бюджет 0, а її норма — номінальна погодинна швидкість (100 - the reserve's size) / 168. paceline status показує, до якого типу частини належить бюджет, наприклад budget 1.00%/h (working-hours norm 1.00).

paceline status також попереджає, коли залишок тижня досягає 90% того, що можуть витратити до п'ятигодинної межі (five_hour_stop_pct) години, які лишилися в поточній частині, і наступні частини з вагою понад 0: тоді ці години ледве встигнуть використати залишок.

Тижневий резерв

Тижневий резерв — це захисна зупинка поза планом. Він відкладає частину тижня, типово 8%, для роботи, рішення про яку ухвалюють наприкінці тижня. Кожен акаунт має власний резерв; paceline reserve задає його розмір, день відкриття і назву (див. Зберегти резерв для завдання наприкінці тижня).

  • Межа зупинки. До моменту відкриття резерву запуск запитує підтвердження, коли тижневе використання досягає або перевищує 100% мінус резерв: 92% за типового 8%. Перевірка читає звичайний тижневий показник, а не власну квоту моделі, у цілих пунктах, як їх показує Claude Code, і без допуску. Див. Підтвердження на жорсткому ліміті.
  • Момент відкриття. Початок робочих годин дня відкриття резерву в поясі профілю. Типово день відкриття — останній день перед скиданням, чиї робочі години закінчуються не пізніше скидання. Він лишається тим самим днем, коли його робочі години позначають як неробочі, бо позначки його не переносять. --release mon до sun обирає день тижня. День тижня, чий початок робочих годин уже минув цього тижня, означає, що резерв відкрито на цей тиждень, а з наступного скидання він знову утримується.
  • Розподіл після відкриття. Із моменту відкриття нічого не утримується. Частина, що починається в момент відкриття, фіксується з усім резервом у залишку, і ця частина та всі наступні частини ділять його за своїми вагами. Частина, що почалася раніше, зберігає свою частку. Після наступного скидання резерв знову утримується.
  • День відкриття, що збігається з днем скидання. Якщо день відкриття збігається з днем тижня скидання, вирішує година скидання. Скидання не пізніше початку робочих годин переносить відкриття на початок тижня, тож резерв майже не утримується. Скидання всередині робочих годин лишає лише години до скидання. Скидання після робочих годин дає той самий момент, що й типове значення. У тижні зі зміною літнього часу в цей день тижня може не бути початку робочих годин у межах тижня; тоді резерв утримується до скидання. Раніший день обирати, якщо скидання не припадає на час після робочих годин.
  • Що зупинка не ловить. Вона діє лише на запуски Agent і Workflow. Роботу, яку основна сесія виконує сама, агентів, що вже працюють, і запуски, схвалені до того, як використання досягло межі зупинки, можуть витратити резерв до його відкриття. Витрати поза цими hooks (claude.ai, інші машини, сесії, де pace вимкнено) також не відстежуються. Див. Зупинка резерву не ловить роботу, яку основна сесія виконує сама.

Зупинка запитує підтвердження в режимах inform і limit однаково, а позначка відсутності або режим дозволів, де ніхто не відповідає (auto, bypassPermissions, dontAsk), перетворює це запитання на відмову. Резерв 0% вимикає зупинку. Коли резерв неможливо обчислити, paceline status виводить reserve unknown: the stop is off, а жорсткі ліміти працюють як раніше.

П'ятигодинна межа

Один ключ профілю, five_hour_stop_pct (типово 95%, від 0 до 100), задає, наскільки близько до свого ліміту PaceLine дозволяє працювати п'ятигодинному вікну. Від цього використання запуск Agent або Workflow спершу запитує підтвердження, робота без нагляду чекає, а темп витрати проєктується на нього. Значення однакове в робочі й неробочі години. Менше значення залишає запас, більше дозволяє сплеску підвести вікно ближче до ліміту. Змінити його можна командою paceline profile set five_hour_stop_pct 90 або у вигляді налаштувань (/paceline:settings pane). Ключ наведено в довіднику.

Тижневий резерв — окремий параметр: його утримують окремо для кожного акаунта (див. тижневий резерв).

Тижнева симуляція

paceline simulate програє одне тижневе вікно через той самий код бюджету, який виконує paceline status, година за годиною, 168 кроків, тож можна побачити, що профіль робить із тижнем.

Що робить змодельований користувач щогодини:

  • Він будує точний показник: тижневе використання на цей момент і п'ятигодинне використання, що дорівнює витраті останніх п'яти годин, поділеній на five_hour_to_week_pct, зі скиданням п'ятигодинного вікна через три години.
  • У робочу годину вона витрачає бюджет години, помножений на коефіцієнт тижня, але не більше five_hour_to_week_pct / 5 на годину, а нічого, поки рекомендація блокує.
  • З нічною чергою вона також витрачає всю квоту частини неробочих годин протягом годин цієї частини. За типової позначки неробочих годин 0 квота дорівнює 0, тож черга нічого не витрачає, доки план не позначить ніч. Модель витрачає значення night.allowance_pct зі status; справжня порада лишає те, що лишилося від частки поточної частини (див. «Що може витратити робота без нагляду»).

Чотири форми тижня:

  • on-track: коефіцієнт 1 у кожну робочу годину.
  • heavy-start: коефіцієнт 2 у перші 72 години вікна, далі 1. Показує, як бюджет перепланується після раннього перевитрачання.
  • light-start: коефіцієнт 0,5 у перші 72 години, далі 1. Показує, як бюджет перепланується після раннього недовитрачання.
  • away-thu-fri: коефіцієнт 0 у робочі години місцевих четверга і п'ятниці, далі 1. Показує, як бюджет перепланується, коли два робочі дні лишаються невикористаними.

Це модель: один показник на годину, ковзна п'ятигодинна сума замість фіксованих вікон Claude Code, без датованих позначок і утримань (робочі години та шаблон днів тижня беруться з файлу плану), вільна пам'ять зафіксована на 64 ГіБ, вік даних — 0, нічна черга витрачає все своє night.allowance_pct, а форми тижня синтетичні, а не історія користувача. Однакові вхідні дані дають однакові значення в межах однієї версії Python, а остання цифра може відрізнятися між версіями.

День скидання змінює значення. День відкриття резерву відраховується від власного скидання акаунта, а дні тижня на ньому лягають інакше, тож акаунт, що скидається в п'ятницю ввечері, відкриває резерв в інший день, ніж той, що скидається в понеділок зранку. Рекомендація

Рекомендація показує, чи блокується нова робота. Вона не називає ні моделі, ні кількості агентів.

  • Блокування. Нова робота не стартує, коли захист пам'яті увімкнено і вільної пам'яті менше за min_free_commit_mb (2048 MiB), коли п'ятигодинне використання досягає five_hour_stop_pct (95%) або коли тижневий ліміт вичерпано. paceline status --json показує recommendation.blocked і причини.
  • Витрата п'ятигодинного вікна. Недавній темп витрати п'ятигодинного вікна є виміряним фактом, який paceline status --json показує як five_hour.burn. Він не змінює рекомендацію і не викликає запиту підтвердження запуску. Темп витрати п'ятигодинного вікна описує вимірювання.
  • Важкі запуски (не частина рекомендації). Коли захист пам'яті увімкнено, paceline status --json показує в host кількість важких запусків, яку дозволяє пам'ять, max_heavy_runs: min(max_heavy_runs, (free memory - commit_reserve_mb) // heavy_job_mb), але не менше 0; типово щонайбільше 3. Коли захист вимкнено, кількість не обчислюють.

Захист пам'яті (memory_guard, типово вимкнений; увімкнути його можна командою paceline profile set memory_guard true) визначає, чи враховується вільна пам'ять узагалі. Коли він вимкнений, жодна відповідь щодо запуску, нічної квоти чи paceline advice не залежить від пам'яті, а пам'ять вимірюється лише тоді, коли paceline status виконується без ключа запуску, як це відбувається, коли його запускають, щоб прочитати пам'ять, або коли виконується paceline doctor. Вільна пам'ять — на Windows це вільний commit, на macOS — kern.memorystatus_level, помножений на фізичну пам'ять, на Linux — MemAvailable. Коли за увімкненого захисту виміряти її неможливо, paceline status пише host memory unknown, і перевірки пам'яті не застосовуються.

Темп витрати п'ятигодинного вікна

Бюджет на годину розподіляє тижневий ліміт, але п'ятигодинне вікно все одно може заповнитися швидше, ніж дозволяє час, що лишився. Тому pace проєктує недавній темп витрати вікна на п'ятигодинну межу, five_hour_stop_pct (типово 95%), в робочі й неробочі години однаково.

  • Темп. Зростання відсотка п'ятигодинного вікна за останні 90 хвилин, у відсоткових пунктах на годину. Базою є показник, зафіксований 90 хвилин тому, або перший показник вікна, якщо вікно молодше. Враховуються лише показники поточного вікна. Темпу немає, доки база не лежить щонайменше на 10 хвилин у минулому, тож у новому вікні або на машині без історії стан перевитрати не показується.
  • Бюджетний темп. (stop - used) / hours to the reset: рівномірний темп, за якого п'ятигодинну межу буде досягнуто рівно до скидання.
  • Стан перевитрати. Дані свіжі, скидання відоме, використання нижче п'ятигодинної межі, темп виміряно, і він перевищує бюджетний темп, тож вікно досягло б межі до скидання. Тоді limited у five_hour.burn має значення true.
  • Робота без нагляду. Лише paceline advice реагує на стан перевитрати: він знижує max_parallel_agents до частки темпу, яку покриває бюджет вікна, аж до 0, і чекає, коли ліміт дорівнює 0. Перевитрата ніколи не викликає запиту підтвердження запуску.
  • Де показано. paceline status --json показує темп витрати в five_hour.burn; текст paceline status його не наводить; у режимі limit рядок pace: подає його як недавній темп.

Темп витрати є лише виміряним фактом. paceline status --json показує значення як five_hour.burn, яке дорівнює null, доки темп не виміряно: за замалої кількості показників, за застарілих даних або коли використання дорівнює п'ятигодинній межі чи перевищує її. Симулятор бюджету не має історії, тож темпу витрати він не показує.

PaceLine надає ті самі показники іншим програмам, що їх читають; див. Файл темпу витрати п'ятигодинного вікна: формат для читання.

Підтвердження на жорсткому ліміті

У режимі limit hook перед кожним запуском Agent і Workflow дає моделі один простий рядок pace:: стан поточної частини щодо її частки, скільки на годину дозволяє частка і кожну захисну зупинку, що близько. У режимі inform модель нічого не читає, якщо зупинка не утримує запуск. Hook просить підтвердити запуск, коли виконується одна з цих умов:

  • Захист пам'яті увімкнено, а вільної пам'яті менше за min_free_commit_mb. Це вимірюється під час кожного запуску. Це діє й тоді, коли акаунт сесії не відомий і тижневого показника немає: нижня межа вільної пам'яті застосовується, п'ятигодинна й тижнева зупинки діють за найвищими свіжими показниками будь-якого акаунта на цій машині (без свіжого показника зупиняти нічого), а перевірка плану й бюджет чекають на дані. Коли захист вимкнено, пам'ять не вимірюється, і цей ліміт ніколи не діє.
  • Лише зі свіжими даними: п'ятигодинне використання досягло п'ятигодинної межі або перевищило її, типово 95% в усі години, або тижневий ліміт вичерпано.
  • До моменту відкриття резерву, в режимах inform і limit однаково, навіть на застарілих даних: тижневе використання досягає або перевищує 100% мінус резерв (92% за типового 8%; 91% проходить), у цілих пунктах, як їх показує Claude Code. Причина називає резерв, його назву, якщо вона є, і момент відкриття, наприклад weekly reserve 8 % kept until Fri 30 09:00. Резерв 0%, відкритий резерв і резерв, який неможливо обчислити (reserve unknown: the stop is off), ніколи не запитують підтвердження; інші ліміти від нього не залежать.
  • Лише зі свіжими даними і лише в режимі limit: поточна частина запланована, а її витрата більш ніж на 1 пункт перевищує ту частину її частки, яку годинник дозволяє на цей момент (частка, помножена на пройдений дріб частини). Частина без плану ніколи не запитує. У режимі inform, типовому, або поки діє paceline mode inform --until-part-end, план лише показується в paceline status і на картці Week у PitBoard, яка показує відхилення від плану (див. пояснення PitBoard), а модель про нього нічого не читає.

Причину додано на початок опису інструмента, тож вона видна в кожному запиті дозволу. Причина жорсткого ліміту починається з pace hard limit:, резерву — з pace reserve:, плану — з pace plan:; коли діє кілька, їхні причини йдуть у цьому порядку, і перша задає префікс. Коли зупинка або план утримує запуск, модель також читає, що саме його утримує, що це означає для її запусків і що відхилений запуск не можна повторювати. За відсутності власника модель читає, що запуск відхилено, бо власник не може його підтвердити. Коли pace не має даних про використання або завершується з помилкою, hook нічого не додає і запуск відбувається, хіба що захист пам'яті увімкнено і вільна пам'ять нижча за її нижню межу.

Поки встановлено позначку відсутності, hook відхиляє запуск замість запиту підтвердження. Так само він відхиляє запуск у режимах дозволів auto, bypassPermissions і dontAsk, де на запит ніхто не відповідає: в auto запитання схвалює класифікатор автоматичного режиму, а не користувач, і запуск пройшов би повз зупинку. Причина тоді називає режим, що утримує запуск, і повідомляє, що перемикання сесії на режим default (Manual) дає змогу підтвердити запуск, а модель дістає вказівку повідомити користувачеві, що утримує запуск, і не повторювати його. У режимах default, acceptEdits і plan, або коли Claude Code не передає режим, hook, як і раніше, запитує підтвердження. Див. Позначка відсутності.

Перше запитання плану в частині називає команду, яка припиняє такі запитання до кінця частини, paceline mode inform --until-part-end; наступні запитання в тій самій частині її не повторюють. Жорсткий ліміт ніколи не залежить від режиму чи плану.

Позначка відсутності

Запит дозволу, на який ніхто не відповідає, утримує сесію, і поки він чекає, термін кешу промпту може минути. Коли користувач відходить, /paceline:away (або paceline away on) встановлює позначку відсутності. Поки вона встановлена, запуск, який запитав би підтвердження (на жорсткому ліміті, понад межу зупинки тижневого резерву або понад частку частини в режимі limit), відхиляється. Відмова називає причину і повідомляє агентові, що користувача немає і повторювати запуск не можна: після резерву агент чекає відкриття, а після жорсткого ліміту чекає, доки ліміт не зніметься.

  • Один файл, <state>/away.json, обслуговує всі сесії на машині.
  • Наступне повідомлення користувача в будь-якій сесії знімає позначку, тож вимикати її не потрібно. Її не знімають пробудження cache-watch плагіна PitCrew, команда /paceline:away, що її встановлює, і промпт від розкладу, циклу, сповіщення, іншої сесії чи каналу.
  • paceline away off знімає її вручну, а paceline away status показує, чи її встановлено, з якого часу і якою сесією.
  • Позначка не має терміну дії і нічого не змінює, поки жоден жорсткий ліміт не діє, тижневе використання нижче межі зупинки резерву і план у режимі limit не перевищує своєї частки. Див. Позначка відсутності не має терміну дії і Промпт через Agent SDK не знімає позначку відсутності.

Прогноз

Прогноз — частка тижня, яка лишилася б невикористаною на момент скидання, якби темп витрати останніх 24 годин зберігся. Він потребує щонайменше двох точок історії в поточному тижневому вікні з інтервалом 3 години або більше; без них paceline status прогнозу не показує.

Що може витратити робота без нагляду

Робота без нагляду, тобто запуск, що виконує команду paceline advice, як-от запуск Stint, витрачає з одного місця: з того, що лишилося від частки поточної частини тижневого плану. Поточна частина — та, що триває зараз, робочі чи неробочі години, у будь-яку годину. Її бюджет — це фіксована частка частини мінус витрачене частиною мінус неврахована частка утримань, але не менше 0.

  • Лише поточна частина. Наступні частини зберігають свої частки, а тижневий резерв не чіпається ніколи: частку частини зафіксовано на її початку з того, що лишалося від тижня після резерву.
  • Увесь залишок, а не пропорційна частка. Перевірка ліміту порівнює запуски під наглядом із часткою, що минула за часом; робота без нагляду може витратити частку частини раніше, а тоді чекає наступної частини.
  • Спільний із власною роботою. Те, що витрачено в тій самій частині, вважається витраченим, а робота без нагляду в робочі години бере з тієї самої частки.
  • Типова позначка неробочих годин — 0, тож без позначки частина неробочих годин не має частки, і відповідь — чекати, а не стартувати: причина share_zero називає команду, що планує частку, наприклад paceline plan set 2026-10-29 --off-hours 0.5 (день частини), а wait_until — це наступна запланована частина. Позначка, встановлена, поки частина триває, ділить її і одразу дає решті частку. Запуск без нагляду, як-от Stint, перетворює очікування, що сягає за кінець ночі, на зупинку. П'ятигодинне вікно, тижневий ліміт і резерв та пам'ять хоста — це причини поради: вони стримують роботу і ніколи не збільшують бюджет. stint add теж виводить команду, коли частка сьогоднішньої ночі дорівнює 0.

Утримання

Утримання фіксує роботу, яку вже почато, але її вартість ще не відобразилася у тижневому використанні. Поки pace увімкнено, його hooks встановлюють утримання для кожного субагента за subagent_estimate_pct (1%) і звільняють його, коли субагент зупиняється. Утримання бюджету для gates та іншої роботи встановлюють вручну командою paceline hold acquire; Stint бере утримання queue для кожного елемента, що виконується, командою paceline hold acquire --kind queue.

Неврахована частка — це сума активних оцінок мінус тижневе використання, додане від моменту отримання найранішої з них, але не менше 0. Лише порада віднімає її від свого бюджету; бюджет на годину не змінюється.

Утримання завершується, коли його звільняють, коли минає його lease (30 хвилин або 240 хвилин для утримання субагента з ключем), або коли зникає його процес. Наприкінці сесії hook записує її завершення і звільняє утримання сесії; коли час, відведений Claude Code для hooks завершення сесії, перериває hook, наступний виклик pace звільняє їх (див. обмеження). Звільнене утримання записує свою фактичну вартість: зміну тижневого використання від моменту отримання.

Hook Agent і Workflow також записує утримання launch для кожного запуску, який він дозволяє або про який запитує. Воно записується під тим самим блокуванням, під яким рахуються активні утримання, тож запуски одного повідомлення асистента бачать один одного, а n-й gate враховує n-1 запусків перед ним, зокрема й запуски інших сесій. Утримання launch не містить оцінки, ніколи не потрапляє в історію, яку читає калібрування, і завершується через 60 секунд. Старт агента переймає найстаріше утримання launch своєї сесії, тож запущений агент враховується один раз; Workflow тримає одне утримання launch на всіх своїх агентів, і перший старт його переймає. Запуск, відхилений через відсутність користувача, одразу звільняє своє утримання; запуск, від якого відмовилися в запиті підтвердження, тримає його, доки воно не завершиться. paceline hold list його показує. Див. Утримання launch залежить від порядку hooks Claude Code.

Робота без нагляду і плагін Stint

Нічна черга перейшла до плагіна Stint. Перед кожним елементом Stint запитує paceline advice і виконує відповідь: start, wait або stop, з бюджетом із розділу що може витратити робота без нагляду і кількістю агентів. Власні правила Stint, тобто запуск, елементи і кінець ночі, наведено в документації Stint.
