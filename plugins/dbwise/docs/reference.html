dbWise reference

The commands, the tools and their levels, the configuration format, the files and environment variables dbWise uses, the exit codes, and the texts the role gate and the tools answer with. The tables come from the plugin's code: python .ci/docs_facts.py build writes its facts, and python .ci/pages.py build writes the tables from them. What dbWise cannot do is in Limitations.

In this page, <home> is dbWise's home directory: $DBWISE_HOME, else ~/.dbwise.

Commands

Run the commands in a terminal, or let the agent run them through its Bash tool, except where a password is typed. Inside a session, the plugin's bin/ directory is on the PATH of the Bash tool.

  • dbwise credential add NAME --user U leaves the password to dbwise set-password NAME, which asks for it in a terminal that hides typed input and stores it in the OS keychain. With --password-env VAR or --password-file PATH the credential reads its password from the environment of the Claude Code process or from a file instead.
  • dbwise alias add ALIAS SERVER --level LEVEL --credential NAME takes one --credential NAME, which serves every level up to the alias's level, or --credential LEVEL=NAME once for each level from read up to the alias's level.
  • dbwise import FILE merges a team file into the local config. With --from-vault it also fills the values the file maps to Vault. With --prune it removes what the file does not list. Every command that changes the config keeps the previous file as config.json.bak.
  • The server reads the config once when it starts: after a change, reconnect plugin:dbwise:postgres in /mcp or start a new session.

Levels and tools

An alias has one of three levels, read (the default), diagnose and write. A tool has a level, or none. A call is allowed when the tool's level is at or below the alias's level, and it connects with the alias's credential for the tool's level. A tool without a level is offered on every alias and uses the read credential.

A server registers a tool only when at least one alias admits it, and each description starts with Level: <level>. Aliases: <the aliases that admit it, with their levels>.

Tool What it does
list_databasesLists every alias with its level, databases, reachability, role check mode and the reasons of the role check

analyze_db_healthIndex, connection, vacuum, sequence, replication, buffer-cache and constraint checks
analyze_workload_indexes, analyze_query_indexesRecommend indexes with the database tuning advisor, using hypopg
diagnose_sqlRuns what read_sql runs, plus EXPLAIN with ANALYZE, and reads the statistics the diagnose role can see
write_sqlRuns any SQL with the write credential and commits it

Each query text a tool sends starts with a comment, /* dbwise read */, /* dbwise diagnose */ or /* dbwise write */, so a DBA reading pg_stat_activity or pg_stat_statements can see which level sent it. The comment is added once in front of each query text a tool sends. read_sql and write_sql send their whole text as one query, so with several statements pg_stat_activity shows the comment once at the start, while pg_stat_statements splits the text and only the first statement carries it. Only the leading /* dbwise <level> */ comment is authoritative. A query can carry its own comment of the same shape later in its text, and that one says nothing about the level.

A call at read or diagnose stops after 30 seconds, on the server through statement_timeout and at the client. write has no timeout.

When a call is refused for its level, the text reads Error: Alias '<alias>' is at level '<level>', but this tool is at level '<level>'. Nothing was sent to the database. and no connection is opened.

Configuration format

<home>/config.json and a team file share one format. Neither holds a password, only a reference to where one lives; a password key whose value is a string is refused at any depth, except inside the fields of a Vault mapping, where "password": "<secret key>" names the key that holds it. Names of credentials, servers and aliases start with a letter or a digit and continue with letters, digits, ., _ or -. examples/team.example.json is a complete team file.

Path Meaning
dbwiseThe schema version, 1. Required
vaultOptional. Where import --from-vault reads: addr and mount (both required in the section), namespace, and login, the vault login method (default oidc)
credentials.<name>.userThe database user. Required, unless a Vault mapping supplies it
credentials.<name>.passwordOptional. Where the password lives: {"keyring": {}} (the default), {"env": "VAR"} or {"file": "PATH"}
credentials.<name>.vaultOptional. A Vault mapping; path and fields are required in it, and fields names the secret keys holding user and password
servers.<name>.engineThe database engine. Required; postgresql is the only one
servers.<name>.host, dbname, databasesThe endpoint. All three are required, but a Vault mapping may supply host and databases instead. dbname is the discovery database, databases the non-empty list the agent may use
servers.<name>.port, sslmodeOptional. port defaults to 5432, sslmode to require (also disable, allow, prefer, verify-ca, verify-full)
servers.<name>.role_checkOptional: enforce (the default) or warn. See the role gate
servers.<name>.vaultOptional. A Vault mapping that may fill host, port and databases
aliases.<alias>.serverThe server the alias reaches. Required
aliases.<alias>.levelOptional: read (the default), diagnose or write
aliases.<alias>.credentialRequired. A credential name, or a map from level to credential name that names every level from read up to the alias's level and none above it

A credential is identified by its name, not by its user. A keychain entry has the service dbwise and the credential's name as its username, so two credentials with the same user keep two passwords.

The role gate

When a pool opens for an alias at read or diagnose, the server runs one query as the pool's role, in the database of the pool, and refuses the alias when the role holds more than its level allows. At start-up the server opens a discovery pool on the database dbname too, with the same gate, so the role is checked there as well. A write alias has no gate. With "role_check": "warn" on the server, the reasons become warnings, listed by list_databases, and the alias opens. The tool descriptions only say that the role check is relaxed. dbwise doctor runs the same query for each credential and database, and for the read credential in the server's discovery database when the alias's list does not name it, then adds findings that refuse nothing.

A refusal reads Access refused by the role check of alias '<alias>': <reason>; <reason>. The reasons:

Reason What clears it
the role is a superuser; has BYPASSRLS, CREATEROLE, CREATEDB or REPLICATIONUse a role without the attribute
the role is a member of predefined role(s) pg_write_all_data, pg_signal_backend, pg_maintain, pg_read_server_files, pg_write_server_files, pg_execute_server_program, pg_checkpoint or pg_create_subscriptionREVOKE the membership
the role is a member of non-predefined role(s) ...REVOKE the membership; membership lets the role cancel and terminate that role's sessions and passes on what that role owns
the role owns the current database, relations, functions or schemas of this databaseGive the objects to another role
the role holds a write privilege on relation(s) ... (at most 3 are listed); a column-level INSERT or UPDATE grant countsREVOKE INSERT, UPDATE, DELETE, TRUNCATE (or MAINTAIN on PostgreSQL 17 and later) on tables, including the column-level INSERT and UPDATE grants, and USAGE and UPDATE on sequences, from the role and from PUBLIC
the role can execute functions of the dblink extension; has USAGE on a foreign serverREVOKE EXECUTE ... FROM PUBLIC on the dblink functions of that database, and REVOKE USAGE on the foreign server
at read: the role is a member of pg_monitor, pg_read_all_stats or pg_stat_scan_tables, which belong to the diagnose levelUse the monitoring roles on the diagnose credential only

Roles in pg_* that are not in the list above, such as pg_read_all_data, are accepted.

Vault

dbwise import --from-vault reads secrets through the vault CLI, which must be on an absolute PATH entry. The CLI uses the address, namespace, mount and login method of the config's vault section.

  • The address a team file names in its vault section receives the operator's Vault token, so read a team file like code before its first import --from-vault. dbWise accepts https:// addresses, and http:// only for localhost, 127.0.0.1 and [::1].
  • The login method name may hold only letters, digits, ., _ and -.
  • A mapping may fill user and password of a credential, and host, port and databases of a server. A password goes to the OS keychain only, never to the config.
  • A login with the default oidc method can be started by the agent; the sign-in finishes in the browser. Other methods ask for input and need a terminal.
