How dbWise limits what an agent does to a database

This page explains the three levels, which layer guarantees what at each of them, what each level's SQL policy admits, and why dbWise offers three SQL tools. For the exact commands, tools and texts, see the reference. To set up roles that match the levels, see Create the database roles for dbWise.

The three levels

An alias is a name the agent uses in a tool call. It has a level, read unless you say otherwise. A call never does more than its alias's level allows.

Level What the agent can do Login
readLook at schemas and objects, and run SELECT and SHOW statementsThe alias's read credential
diagnoseEverything at read, plus EXPLAIN with ANALYZE, health checks, top queries from pg_stat_statements and index adviceThe diagnose credential for the diagnose tools; read_sql keeps using the read credential
writeEverything at diagnose, plus any SQL, committedThe write credential for write_sql; the other tools use the credential of their own level

Each level can name its own credential, so each can have its own database role. That is the point of the split: the role that may read data, the role that may also look at other sessions' activity, and the role that may change data are three roles, and you can revoke one without touching the others.

A call names an alias. It is allowed when the tool's level is at or below the alias's level, and it connects with the alias's credential for the tool's level. read_sql on a write alias runs as the read login under the read policy. A call that is refused for its level sends nothing to the database.

Where the guarantee comes from

At read and diagnose, the agent can change no schema, no data and nothing else that affects the business: not other sessions, server configuration, statistics counters, replication consumers or remote databases. Four layers hold that, and they are not equally strong.

  1. The database role. It decides what the connection may do at all, and it is the one layer a statement in the session cannot switch off. A session can lift default_transaction_read_only and statement_timeout for itself, and it cannot grant itself a privilege. dbWise enforces this layer with the role gate: when a pool opens, the server runs one catalog query as the pool's role and refuses the alias when the role is a superuser, owns objects, holds a write grant, belongs to an application's role or can execute dblink. The rules are in the reference. The role is where the guarantee for schema and data, and for reach into other sessions, rests.
  2. The SQL policy. Every statement is parsed with PostgreSQL's own parser and checked before it is sent. Only statements of the level's kind pass, and every function call anywhere in the statement has to be in the level's function set: the check walks the whole parse tree, including FROM clauses, ROWS FROM, LATERAL, VALUES and CTEs. This layer stops the side effects that PostgreSQL lets a plain role execute by default: pg_terminate_backend, pg_cancel_backend, pg_logical_emit_message, pg_advisory_lock, dblink_exec and set_config. None of them is in the read or diagnose function set. The role recipe adds REVOKEs where the DBA can apply them.
  3. The read-only transaction and its ROLLBACK. Every call at read and diagnose runs in a read-only transaction and ends with ROLLBACK. This is defence in depth: it stops DML and DDL hidden in views and functions, nextval, SELECT ... FOR UPDATE and CREATE EXTENSION. It holds because the policy refuses the statements that would make the transaction writable (SET TRANSACTION READ WRITE, SET transaction_read_only = off, BEGIN READ WRITE).
  4. The statement timeout. A call at read or diagnose runs under statement_timeout = '30s', and the client stops waiting after the same time. It bounds availability. It is not a security boundary, because a session could set it to 0; the policy refuses set_config and SET, which keeps the agent from doing so.

After every call the connection goes back to the pool reset: DISCARD ALL releases advisory locks and prepared statements, and the hypopg extension's hypothetical and hidden indexes are cleared. A call can then not leave session state behind for the next one.

At write there is no policy and no timeout: the agent runs whatever the login may run, and the database role is the only limit. This is why a write login should have only the grants the task needs, and why the role gate does not apply to it.

What each level's policy admits

read diagnose
StatementsSELECT without a locking clause, SHOWThe same, plus EXPLAIN with any options, ANALYZE included, when the explained statement passes the policy
FunctionsA fixed list of functions for aggregates, math, strings, dates, JSON, arrays, catalog information and the likeThe same list, plus hypopg_create_index, hypopg_reset, hypopg_list_indexes, hypopg_relation_size, hypopg_get_indexdef, hypopg, pg_last_wal_receive_lsn, pg_last_wal_replay_lsn and pg_last_xact_replay_timestamp

Neither level admits the statements VACUUM and ANALYZE, CREATE EXTENSION, PREPARE and DEALLOCATE, DECLARE, FETCH and CLOSE, or NOTIFY. Neither admits pg_current_xact_id (each call consumes a transaction id), gen_salt and crypt, ts_stat and ts_rewrite (each executes SQL passed as an argument), set_config, pg_sleep, or the pg_advisory_*, lo_* and dblink* functions.

EXPLAIN ANALYZE of an INSERT, UPDATE or DELETE is refused before it reaches PostgreSQL, because the explained statement has to pass the same policy. EXPLAIN ANALYZE of a SELECT executes it, with its full load, inside the transaction that is rolled back. The policy matches function names as written, with a pg_catalog. prefix stripped, while PostgreSQL resolves the name through search_path. It does not look at relations, operators or casts, so what the policy leaves open is closed by the role and by the read-only transaction.

Every query text a tool sends starts with a marker comment, /* dbwise read */, /* dbwise diagnose */ or /* dbwise write */, so a DBA reading pg_stat_activity can see which level sent it.

What separates read from diagnose

The database role of each level's credential does, enforced by the role gate, together with the tool split and the per-level statement and function sets. A diagnose role is a member of pg_monitor, which shows other sessions' query text in pg_stat_activity and pg_stat_statements. A read role should not be: the gate refuses it on an alias at read. On an alias at diagnose, every login is checked at diagnose, so there it is the DBA's choice. PostgreSQL also grants some statistics views, such as pg_stat_user_tables, to every role, so a read alias can query those. See Limitations.

Why there are three SQL tools

read_sql, diagnose_sql and write_sql could be one tool whose effect depends on the alias. They are three because Claude Code's permission rules match tool names. With three names you can allow read_sql everywhere and keep write_sql on ask. One tool whose behaviour changed with the alias could not be given that rule.

The tools that are not SQL tools follow the same rule. list_schemas, list_objects and get_object_details are read; explain_query, get_top_queries, analyze_db_health, analyze_workload_indexes and analyze_query_indexes are diagnose. A server registers a tool only when at least one alias admits it, and each description starts with its level and the aliases that admit it.

Where the guarantee ends

  • A server with "role_check": "warn" keeps the SQL policy and the read-only transaction and gives up the role layer, so it suits local and test databases. See Limitations.
  • The role gate takes a snapshot when a pool opens. A grant made afterwards shows up after a reconnect.
  • A view or a function that already exists in the database can do a lot of work inside the 30 seconds a call has.

The full list is in Limitations.
