Довідник dbWise

Команди, інструменти та їхні рівні, формат конфігурації, файли і змінні середовища, які використовує dbWise, коди виходу, а також тексти, якими відповідають перевірка ролі й інструменти. Таблиці беруться з коду плагіна: python .ci/docs_facts.py build записує його факти, а python .ci/pages.py build записує таблиці з них. Чого dbWise не може, описано в Обмеженнях.

На цій сторінці <home> — домашній каталог dbWise: $DBWISE_HOME, інакше ~/.dbwise.

Команди

Запускайте команди в терміналі або доручайте агентові виконувати їх через Bash tool, крім випадків, коли потрібно ввести пароль. Усередині сесії каталог bin/ плагіна є в PATH Bash tool.

  • dbwise credential add NAME --user U залишає пароль команді dbwise set-password NAME, яка запитує його в терміналі з прихованим введенням і зберігає в сховищі ключів ОС. З --password-env VAR або --password-file PATH облікові дані читають пароль зі середовища процесу Claude Code або з файлу.
  • dbwise alias add ALIAS SERVER --level LEVEL --credential NAME приймає один --credential NAME, який обслуговує кожен рівень до рівня псевдоніма, або --credential LEVEL=NAME по одному разу для кожного рівня від read до рівня псевдоніма.
  • dbwise import FILE об'єднує файл команди з локальною конфігурацією. З --from-vault вона також заповнює значення, які файл зіставляє з Vault. З --prune вона прибирає те, чого файл не перелічує. Кожна команда, яка змінює конфігурацію, зберігає попередній файл як config.json.bak.
  • Сервер читає конфігурацію один раз, коли стартує: після зміни перепідключіть plugin:dbwise:postgres у /mcp або почніть нову сесію.

Рівні та інструменти

Псевдонім має один із трьох рівнів: read (типовий), diagnose або write. Інструмент має рівень або не має його. Виклик дозволено, коли рівень інструмента не вищий за рівень псевдоніма, і він підключається обліковими даними псевдоніма для рівня інструмента. Інструмент без рівня пропонується на кожному псевдонімі і використовує облікові дані read.

Сервер реєструє інструмент лише тоді, коли його допускає принаймні один псевдонім, і кожен опис починається з Level: <level>. Aliases: <the aliases that admit it, with their levels>.

Інструмент Що робить

reconnectЗнову перевіряє недоступні псевдоніми їхніми обліковими даними read або один псевдонім, якщо задано alias

diagnose_sqlВиконує те, що read_sql, плюс EXPLAIN з ANALYZE, і читає статистику, яку бачить роль diagnose
write_sqlВиконує будь-який SQL обліковими даними write і фіксує його

Кожен текст запиту, який надсилає інструмент, починається з коментаря /* dbwise read */, /* dbwise diagnose */ або /* dbwise write */, тож DBA, який читає pg_stat_activity або pg_stat_statements, бачить, з якого рівня надійшов запит. Коментар додається один раз перед кожним текстом запиту, який надсилає інструмент. read_sql і write_sql надсилають увесь свій текст одним запитом, тому за кількох операторів pg_stat_activity показує коментар один раз на початку, тоді як pg_stat_statements розбиває текст і лише перший оператор має коментар. Визначальним є лише початковий коментар /* dbwise <level> */. Запит може мати власний коментар такої самої форми пізніше в тексті, і цей коментар нічого не каже про рівень.

Виклик на read або diagnose зупиняється після 30 секунд: на сервері через statement_timeout і на клієнті. write не має тайм-ауту.

Коли виклик відхилено через його рівень, текст має вигляд Error: Alias '<alias>' is at level '<level>', but this tool is at level '<level>'. Nothing was sent to the database., і жодне з'єднання з базою не відкривається.

Формат конфігурації

<home>/config.json і файл команди мають один формат. Жоден з них не містить пароля, лише посилання на місце, де він зберігається: ключ password, значенням якого є рядок, відхиляється на будь-якій глибині, крім fields зіставлення Vault, де "password": "<secret key>" називає ключ, який його містить. Назви облікових даних, серверів і псевдонімів починаються з літери або цифри і продовжуються літерами, цифрами, ., _ або -. examples/team.example.json — повний файл команди.

Шлях Значення
dbwiseВерсія схеми, 1. Обов'язково
vaultНеобов'язково. Звідси читає import --from-vault: addr і mount (обидва обов'язкові в розділі), namespace і login, метод vault login (типово oidc)
credentials.<name>.userКористувач бази даних. Обов'язково, якщо його не задає зіставлення Vault
credentials.<name>.passwordНеобов'язково. Місце, де зберігається пароль: {"keyring": {}} (типово), {"env": "VAR"} або {"file": "PATH"}
credentials.<name>.vaultНеобов'язково. Зіставлення Vault; у ньому обов'язкові path і fields, а fields називає ключі секретів, які містять user і password
servers.<name>.engineРушій бази даних. Обов'язково; postgresql — єдиний
servers.<name>.host, dbname, databasesКінцева точка. Усі три обов'язкові, але зіставлення Vault може натомість задати host і databases. dbname — база виявлення, databases — непорожній список, яким може користуватися агент
servers.<name>.port, sslmodeНеобов'язково. port типово 5432, sslmode — require (також disable, allow, prefer, verify-ca, verify-full)
servers.<name>.role_checkНеобов'язково: enforce (типово) або warn. Див. перевірку ролі
servers.<name>.vaultНеобов'язково. Зіставлення Vault, яке може заповнити host, port і databases
aliases.<alias>.serverСервер, до якого звертається псевдонім. Обов'язково
aliases.<alias>.levelНеобов'язково: read (типово), diagnose або write
aliases.<alias>.credentialОбов'язково. Назва облікових даних або зіставлення рівня з назвою облікових даних, яке називає кожен рівень від read до рівня псевдоніма і жодного вищого

Облікові дані розрізняють за назвою; користувач на це не впливає. Запис у сховищі ключів має службу dbwise і назву облікових даних як ім'я користувача, тож два набори облікових даних з одним користувачем зберігають два паролі.

Перевірка ролі

Коли відкривається пул для псевдоніма на рівні read або diagnose, сервер виконує один запит від імені ролі пулу в базі пулу і відхиляє псевдонім, якщо роль має більше, ніж дозволяє його рівень. Під час запуску сервер також відкриває пул виявлення в базі dbname з тією самою перевіркою, тож роль перевіряють і там. Псевдонім write перевірки не має. Коли на сервері стоїть "role_check": "warn", причини стають попередженнями, які перелічує list_databases, а псевдонім відкривається. Описи інструментів лише кажуть, що перевірку ролі послаблено. dbwise doctor виконує той самий запит для кожних облікових даних і кожної бази, а також для облікових даних read у базі виявлення сервера, коли список псевдоніма її не називає, а потім додає висновки, які нічого не відхиляють.

Текст відмови має вигляд Access refused by the role check of alias '<alias>': <reason>; <reason>. Причини:

Причина Що її усуває
роль є суперкористувачем; має BYPASSRLS, CREATEROLE, CREATEDB або REPLICATIONВикористайте роль без цього атрибута

роль є членом невбудованих ролей ...Відкличте членство через REVOKE; членство дає змогу ролі скасовувати й завершувати сесії цієї ролі та передає те, чим вона володіє

Ролі pg_*, яких немає у списку вище, як-от pg_read_all_data, приймаються.

Vault

dbwise import --from-vault читає секрети через vault CLI, який має бути в абсолютному записі PATH. CLI використовує адресу, простір імен, mount і метод входу з розділу vault конфігурації.

  • Адреса, яку файл команди називає в розділі vault, отримує токен Vault оператора, тож перед першим import --from-vault прочитайте файл команди як код. dbWise приймає адреси https://, а http:// лише для localhost, 127.0.0.1 і [::1].
  • Назва методу login може містити лише літери, цифри, ., _ і -.
  • Зіставлення може заповнити user і password облікових даних, а також host, port і databases сервера. Пароль потрапляє лише до сховища ключів ОС, ніколи до конфігурації.
  • Вхід із типовим методом oidc може почати агент; авторизацію завершують у браузері. Інші методи запитують введення і потребують терміналу.
