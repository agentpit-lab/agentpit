Обмеження dbWise

Чого dbWise не може робити або робить лише частково, згруповано за місцем, де ви з цим стикаєтеся. Кожен запис пояснює, що ви бачите, і що працює далі або що зробити. Формат конфігурації, команди та причини відмови перевірки ролі описано в довіднику.

Встановлення і запуск

Windows на ARM64 не підтримується

Скомпільований пакет psycopg-binary, потрібний серверу PostgreSQL, не публікує wheel для нативного Python під Windows ARM64. З таким Python bootstrap зупиняється до запуску pip і повідомляє про це. Обхід — x64-версія Python від 3.12 до 3.14: Windows на ARM запускає її емуляцією. Те, що x64-wheel після цього встановлюються і працюють під емуляцією, не перевірено.

сервер postgres запускається як заготовка і пропонує лише dbwise_status, який повідомляє, що dbWise не працює на нативному Python під Windows ARM64. У bootstrap.log нічого не записується. У терміналі dbwise виводить той самий текст і завершується зі статусом 1.

Перший запуск потребує доступу до PyPI

Під час першого запуску після встановлення і після оновлення, яке змінює requirements.txt, dbWise збирає Python-середовище з залежностей, зафіксованих за хешами. pip завантажує лише бінарні wheel (--only-binary :all:), тому машина без доступу до PyPI або до дзеркала, на яке налаштовано pip, не може завершити збирання. Збирання виконується один раз для кожної версії requirements.txt; наступні запуски використовують уже створене середовище.

сервер postgres пропонує лише dbwise_status і ніколи не отримує інструментів бази даних. Журнал збирання — це bootstrap.log у домашній теці dbWise (див. Файли).

Перша сесія пропонує лише dbwise_status, доки збирання не завершиться

Claude Code чекає на відповідь MCP-сервера кілька десятків секунд, а перше збирання триває довше. Тому перша сесія після встановлення або після оновлення, яке змінює requirements.txt, запускає сервер-заготовку з одним інструментом dbwise_status, поки середовище збирається у фоновому режимі. Інструменти бази даних з'являються після того, як ви підключите plugin:dbwise:postgres повторно в /mcp або почнете нову сесію.

немає жодного з інструментів list_databases, read_sql та інших; dbwise_status повідомляє, що залежності встановлюються, або що їх уже встановлено і сервер треба підключити повторно.

власна перевірка хука SessionStart. Команда dbwise у терміналі чекає завершення збирання, а потім виконується.

Сервер потребує Python від 3.12 до 3.14

Скрипти запуску шукають python3.14, python3.13, python3.12, потім python3 і python (у Windows py -3.14, py -3.13, py -3.12, потім python) і беруть перший у діапазоні від 3.12 до 3.14. Якщо такого немає, скрипт запуску виводить, що dbWise потребує Python від 3.12 до 3.14, і завершується зі статусом 1, до того як може запуститися заготовка. Тому сервер не запускається й узагалі не відповідає. Python 3.15 і новіші також не входять до діапазону.

plugin:dbwise:postgres завершився з помилкою в /mcp. Той самий діапазон діє для команди dbwise у терміналі.

Хук SessionStart потребує Python у PATH

Хук запускає python3, або python, якщо python3 не запускається, з PATH середовища, у якому запускається Claude Code, хоч би якої версії був цей Python. Без жодного з них оболонка не знаходить програму, і хук завершується зі статусом 127. Хук лише додає до сесії рядки офлайн-перевірки стану; сервер від нього не залежить.

хук SessionStart dbWise завершується зі статусом 127, і в сесії немає рядків про проблеми dbWise. Машина, на якій є лише інтерпретатор з номером версії, наприклад python3.12, або лише засіб запуску py, опиняється в цій ситуації, хоча сам сервер запускається.

інструменти бази даних і dbwise doctor із терміналу.

На Intel Mac встановлюється старіший cryptography з відкритими повідомленнями про вразливості

cryptography 49 і новіші не публікують wheel для macOS на x86_64. Тому lock-файл фіксує cryptography 48.0.1 для цієї платформи, а на всіх інших платформах — новішу версію. Для 48.0.1 є три відкриті повідомлення про вразливості (GHSA-g6cj-pr64-35w5, GHSA-jwv3-5hgf-82ww, GHSA-m2h6-j472-rp4c). dbWise доходить до cryptography лише через pyjwt, залежність бібліотеки MCP, і secretstorage, бекенд сховища ключів ОС у Linux; сам пакет він не викликає.

нічого під час роботи. Сканування залежностей lock-файлу для Intel Mac показує ці три повідомлення про вразливості.

Конфігурація читається один раз, під час запуску сервера

Сервер читає config.json у домашній теці dbWise ($DBWISE_HOME, типово ~/.dbwise) і під час запуску отримує кожен пароль. Зміна, зроблена командою dbwise, відредагованим файлом або зміненим записом у сховищі ключів ОС, набирає чинності після того, як ви підключите plugin:dbwise:postgres повторно в /mcp або почнете нову сесію. Інструмент reconnect файл не перечитує: він повторно перевіряє псевдоніми, які були недоступні, з даними підключення, які сервер уже має. Це допомагає, коли причиною була мережа.

щойно доданого псевдоніма немає в list_databases, або далі використовується старий пароль.

Некоректний config.json зупиняє сервер

Щойно Python-середовище зібрано, сервер читає config.json до того, як відкриє будь-який псевдонім. Файл, який не можна прочитати, який не є коректним JSON або який не відповідає формату, змушує сервер вивести причину і завершитися зі статусом 1, тож жоден псевдонім не пропонується, зокрема коректні. Файл конфігурації, якого ще немає, не є помилкою: сервер запускається без псевдонімів.

plugin:dbwise:postgres завершився з помилкою в /mcp. Перевірка хука SessionStart позначає конфігурацію як непридатну, а dbwise doctor виводить config unusable: із файлом, описом помилки і — для порушення формату — JSON-шляхом першої проблеми.

виправте файл або скопіюйте на його місце config.json.bak, якщо він є, а потім підключіть plugin:dbwise:postgres повторно в /mcp.

Vault

Адреса Vault, яку вказує файл команди, отримує токен Vault оператора

dbwise import --from-vault запускає CLI vault для addr розділу vault файлу команди, а CLI надсилає токен Vault оператора на цю адресу з кожним читанням. dbWise приймає лише адресу https:// (для localhost, 127.0.0.1 і [::1] — http://) і відхиляє в ній лапки та керівні символи, але відрізнити довірену адресу від іншої не може. Звичайний dbwise import файлу команди зберігає розділ vault без звернення до Vault, а наступний імпорт з --from-vault використовує збережену адресу.

перед першим import --from-vault читайте файл команди як код і звіряйте його vault.addr з адресою, яку дає ваша команда.

Назва методу входу Vault обмежена кількома символами

Поле login розділу vault задає метод, який передається в vault login -method=. dbWise приймає в ньому лише літери, цифри, ., _ і -, тож назва методу з іншим символом, наприклад пробілом або косою рискою, змушує імпорт відхилити файл команди до будь-якого виклику. Відмова залишає локальну конфігурацію без змін.

$.vault.login: must use only letters, digits, '.', '_' and '-'; nothing was changed.

увійдіть через CLI vault самостійно, а потім виконайте імпорт.

Імпорт із Vault потребує CLI vault

dbWise читає Vault через CLI vault від HashiCorp, який знаходить через абсолютний запис у PATH, і входить через нього. Вбудованого HTTP-клієнта немає. Машина без CLI не може виконати import --from-vault; команда виводить, як його встановити.

dbwise import <team file> без --from-vault і будь-яка інша команда.

Що гарантують рівні доступу

Авторитетна лише початкова позначка

Кожен текст запиту, надісланий на рівнях read, diagnose і write, має коментар, який dbWise ставить перед ним: /* dbwise read */, /* dbwise diagnose */ або /* dbwise write */. Тож DBA, який читає pg_stat_activity або pg_stat_statements, бачить, який рівень надіслав запит. Коментар додається один раз перед кожним текстом запиту, надісланим інструментом. read_sql і write_sql надсилають увесь текст як один запит, тому за кількох операторів pg_stat_activity показує коментар один раз на початку, а pg_stat_statements розбиває текст, і коментар є лише в першому операторі. Належить dbWise лише початковий коментар /* dbwise <level> */. Запит може містити власний коментар такої самої форми далі в тексті, і той не каже нічого про рівень.

читайте початок тексту запиту; збіг деінде в тексті про рівень нічого не каже.

Сервер із role_check, встановленим на warn, втрачає рольовий шар

Якщо на сервері встановлено "role_check": "warn", відмова перевірки ролі перетворюється на попередження, тож суперкористувач або власник таблиць може обслуговувати псевдонім рівня read або diagnose. Залишаються політика SQL dbWise і транзакція лише для читання. Оператор, якого політика не передбачає, або функція, яку вона допускає, тоді виконується з привілеями цієї ролі. Використовуйте warn для локальних і тестових баз даних.

в описах інструментів цих псевдонімів написано role check relaxed (warn), а list_databases перелічує причини, які знайшла перевірка.

Статистичні представлення, які PostgreSQL надає кожній ролі, лишаються видимими на рівні read

Різницю між read і diagnose задає роль бази даних облікових даних кожного рівня, яку забезпечує перевірка ролі, разом із розподілом інструментів і окремими для кожного рівня наборами операторів та функцій. PostgreSQL надає кожній ролі деякі статистичні представлення, наприклад pg_stat_user_tables, тож псевдонім read може їх запитувати. Текст чужих запитів у pg_stat_activity і pg_stat_statements потребує pg_read_all_stats, який перевірка на рівні read відхиляє.

VACUUM не працює через write_sql

write_sql виконується всередині транзакції, яку він сам і фіксує, а PostgreSQL відхиляє VACUUM у блоці транзакції. CREATE INDEX CONCURRENTLY та інші оператори, які не можуть виконуватися в блоці транзакції, завершуються з тією самою помилкою. Виконуйте їх інструментом поза dbWise.

VACUUM cannot run inside a transaction block.

Тайм-аути і налаштування ресурсів — це запобіжники, які сесія може зняти

Виклик на рівнях read або diagnose має тайм-аут оператора 30 секунд, встановлений для виклику через SET LOCAL, і клієнт перестає чекати через той самий час. Типові значення ролі, які DBA задає через ALTER ROLE ... SET (default_transaction_read_only, statement_timeout та інші), є запобіжниками доступності, а не частиною гарантії: сесія сама може зняти statement_timeout і default_transaction_read_only. У PostgreSQL 17.11 сесія звичайної ролі також скидала назад work_mem і idle_in_transaction_session_timeout і отримувала відмову для temp_file_limit. Модель не може цього зробити завдяки списку дозволених операторів dbWise: він відхиляє оператори, які змінюють ці налаштування. На рівні write тайм-ауту оператора немає. Оператори, які задають ці типові значення, наведено в Створення ролей бази даних для dbWise.

EXPLAIN ANALYZE виконує запит і навантажує сервер

diagnose_sql і explain_query з analyze виконують SELECT, для якого подано EXPLAIN, на сервері з повним навантаженням, у транзакції, яку відкочують. Довгий SELECT утримує свої блокування ACCESS SHARE, доки не завершиться або доки не спрацює тайм-аут; інші сесії, яким потрібне сильніше блокування цих таблиць, чекають на нього. Див. документацію PostgreSQL про явне блокування.

Зловмисне представлення або функція, які вже є в базі даних, можуть використовувати ресурси

Виклик може виконати лише те, що допускає політика, але представлення або функція, які вже є в базі даних, можуть виконати багато роботи всередині виклику. Тайм-аут оператора обмежує це 30 секундами на виклик, і кілька викликів можуть іти один за одним.

На рівні read кожна транзакція, яка отримує ідентифікатор транзакції, його витрачає

PostgreSQL присвоює транзакції ідентифікатор, коли він їй уперше потрібен, і бере його з лічильника сервера, навіть коли транзакцію відкочують. dbWise відхиляє pg_current_xact_id, який присвоює ідентифікатор за кожного виклику. Інші способи присвоїти ідентифікатор не перелічено.

База даних із встановленим dblink відхиляє псевдоніми read і diagnose

dblink_exec може виконати запис у віддаленій базі, який лишається після локального відкочування, а PostgreSQL типово залишає право EXECUTE на функції dblink за PUBLIC. Перевірка ролі відхиляє роль read або diagnose, яка може їх виконувати, тож псевдонім недоступний, доки ви не виконаєте REVOKE EXECUTE ... FROM PUBLIC для функцій dblink цієї бази і не надасте право назад лише ролям, яким воно потрібне. Те саме стосується ролі з USAGE на зовнішньому сервері.

псевдонім недоступний, а причина така: the role can execute functions of the dblink extension.

pg_stat_statements охоплює весь сервер

get_top_queries і analyze_workload_indexes читають pg_stat_statements, який веде один список для всього сервера PostgreSQL. Їхні результати містять запити з кожної бази на сервері, а не лише з вказаної вами. Розширення має бути завантажене через shared_preload_libraries і створене в базі даних.

Парсер SQL приймає синтаксис PostgreSQL 18

dbWise розбирає SQL за граматикою PostgreSQL 18, тож оператор, допустимий лише в PostgreSQL 18, проходить розбір, але сервер старішої версії його відхиляє. Конструкцію, якої не знає список дозволених операторів, dbWise відхиляє ще до того, як оператор потрапить на будь-який сервер.

Перевірка стану послідовностей

analyze_db_health на рівні diagnose виконує перевірку послідовностей. Вона розглядає послідовності, якими володіє стовпець або з яких він бере типове значення, і повідомляє про ті, що використали понад 90% своїх значень. Прогалини нижче — це випадки, які перевірка не бачить або вимірює відносно іншої межі.

Послідовність, до якої роль не має SELECT, не перевіряється

Перевірка потребує SELECT або USAGE для кожної послідовності. Роль, яка має SELECT на таблиці, не має його на їхніх послідовностях, а перевірка ролі зараховує USAGE на послідовність як привілей на запис. Натомість надайте SELECT командами GRANT SELECT ON ALL SEQUENCES IN SCHEMA <schema> і ALTER DEFAULT PRIVILEGES IN SCHEMA <schema> GRANT SELECT ON SEQUENCES або зробіть роль членом pg_read_all_data. Оператори з клаузою FOR ROLE, яку потребують типові привілеї, наведено в Створення ролей бази даних для dbWise.

частина звіту Sequence health: завершується рядком <n> sequence(s) could not be read with this role's privileges and were not checked:, за яким ідуть назви послідовностей. Решта перевірки та інші перевірки стану виконуються далі.

Типове значення, що шукає послідовність за назвою, залежить від search_path ролі diagnose

Типове значення стовпця, як-от nextval('orders_seq'::text), не створює залежності від послідовності, тому перевірка вирізає назву з типового значення і розв'язує її через to_regclass у сесії ролі diagnose. Назва без префікса схеми знаходиться через search_path ролі diagnose. Якщо цей шлях відрізняється від шляху застосунку, назва вказує на іншу послідовність або ні на яку, і стовпець тоді вимірюється щодо тієї послідовності або пропускається.

Назва послідовності з одинарною лапкою не знаходиться

Назву вирізають з типового значення між одинарними лапками, тому послідовність, назва якої містить одинарну лапку, не знаходиться через типове значення, що шукає її за назвою. Стовпці serial або identity і типове значення, яке називає послідовність прямо в nextval(...), не зачіпаються.

Типове значення нерозпізнаної форми вимірюється щодо власного максимуму послідовності

Максимум — це менше з max_value послідовності та діапазону типу стовпця, але лише тоді, коли стовпець приймає значення без змін: він володіє послідовністю або його типове значення — саме nextval(...) з необов'язковим приведенням типу. Для типового значення, як-от nextval('s') % 1000, перевірка лишає власний максимум послідовності, тож стовпець, вужчий за послідовність, може переповнитися раніше, ніж перевірка попередить.

Після setval з is_called false послідовність показується як використана на 0%

PostgreSQL показує last_value як порожній для послідовності, з якої ще не читали, і для послідовності, встановленої через setval('seq', N, false). Перевірка рахує порожнє значення як 0, тож така послідовність показує 0% використання, доки nextval не виконається один раз, хоч би як близько до максимуму було N.

Низхідні послідовності не перевіряються

Перевірка пропускає послідовність із від'ємним кроком.

Дочірні таблиці з успадкуванням потрапляють у звіт кожна окремо

Таблиця, яка успадковує стовпець і його типове значення від батьківської через INHERITS, є окремою таблицею, і перевірка звітує про послідовність окремо для кожної такої таблиці, тож одна послідовність може з'являтися в звіті по разу для кожної дочірньої таблиці. Секція секціонованої таблиці потрапляє у звіт лише через батьківську таблицю, якщо в секції немає власної послідовності.

Стовпець типу домен або numeric не обмежується власним діапазоном

Перевірка обмежує максимум діапазоном стовпців smallint, integer і bigint. Стовпець, тип якого є доменом, навіть домен над integer, і стовпець numeric вимірюються щодо власного максимуму послідовності, але не більше за максимум bigint. Домен над smallint або стовпець numeric(5,0) можуть вичерпати значення раніше, ніж перевірка попередить.
