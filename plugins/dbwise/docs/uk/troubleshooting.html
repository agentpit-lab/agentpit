Усунення проблем dbWise

Знайдіть симптом, потім прочитайте його причину, перевірку і виправлення. Для більшості проблем почніть із dbwise doctor (або /dbwise:doctor у сесії). Команда перевіряє сховище ключів ОС, Python-середовище і кожен псевдонім, а завершується одним рядком VERDICT:: ready або перелік проблем. Команда dbwise є в PATH лише в Bash tool агента, тож агент може запускати її саме там. Щоб запустити її в терміналі самостійно, використайте рядок команди, який виводить dbwise credential add; у Windows це PowerShell або cmd, бо Git Bash не може приховати введений текст. У довіднику перелічено команди і причини відмови перевірки ролі, а в Обмеженнях — те, чого dbWise не може.

Зміна конфігурації набирає чинності після того, як ви перепідключите plugin:dbwise:postgres у /mcp або почнете нову сесію.

Сервер відсутній або з помилкою в /mcp

/mcp не показує plugin:dbwise:postgres або показує його з помилкою.

одна з таких причин:

  • Плагін не встановлено або його вимкнено. Встановіть його командою /plugin install dbwise@agentpit і почніть нову сесію.
  • У PATH середовища, з якого стартує Claude Code, немає Python 3.12–3.14. Скрипт запуску виводить, що dbWise потребує Python 3.12–3.14, і завершується зі статусом 1. Див. Сервер потребує Python від 3.12 до 3.14.
  • config.json некоректний, тому сервер завершується зі статусом 1. Див. Некоректний config.json зупиняє сервер.

виконайте python3 --version (у Windows py --list) в середовищі, з якого стартує Claude Code, і dbwise doctor.

Скрипт запуску перебирає py -3.14, py -3.13, py -3.12, а потім python у Windows, і python3.14, python3.13, python3.12, python3, а потім python у macOS і Linux, і бере перший, що має версію від 3.12 до 3.14.

встановіть Python з потрібного діапазону або виправте конфігурацію, а потім почніть нову сесію. У Claude Code 2.1.296 під claude -p сервер, що вичерпав тайм-аут під час старту, не запускався знову в новій сесії близько 15 хвилин. Чи так само затримується сервер, що завершився зі статусом 1, не перевірено. Якщо нова сесія його не повертає, зачекайте цей період.

Сервер не показує інструментів

plugin:dbwise:postgres підключено, але жодного інструмента для бази даних не показано.

сервер реєструє інструмент лише тоді, коли його допускає псевдонім. Без псевдонімів пропонувати нічого, і це не помилка. Або config.json не існує, або в ньому немає псевдонімів, або DBWISE_ALIASES не називає жодного з них. Псевдонім рівня read дає лише інструменти рівня read; інструменти diagnose і write з'являються, коли псевдонім їх допускає.

dbwise alias list

і echo $DBWISE_ALIASES (у PowerShell $env:DBWISE_ALIASES) в середовищі, з якого стартує Claude Code. Назви у змінній мають бути назвами псевдонімів, і сервер попереджає про кожну назву, яка псевдонімом не є.

додайте псевдонім (Додавання псевдоніма) або виправте DBWISE_ALIASES, а потім перепідключіть сервер.

Сервер показує лише dbwise_status

Єдиний інструмент — dbwise_status, а list_databases, read_sql та інші відсутні.

Python-середовище плагіна ще не збудовано. Claude Code чекає на відповідь сервера кілька десятків секунд, а перша збірка триває довше. Тому в першій сесії після встановлення (і після оновлення, яке змінює requirements.txt) сервер є заготовкою з одним інструментом, поки збірка виконується у фоні. Невдала збірка, платформа, яку dbWise відхиляє, і збірка в іншій сесії дають однакову картину.

попросіть агента викликати dbwise_status і передати його текст або викличте інструмент самостійно. Значення тексту:

Повний журнал збірки — це bootstrap.log у домашньому каталозі dbWise, ~/.dbwise або $DBWISE_HOME (див. Файли). Він містить вивід pip. Зазвичай збірку зриває відсутність доступу до PyPI або до дзеркала, яке налаштовано для pip, бо pip встановлює лише бінарні wheel-пакети. Див. Перший запуск потребує доступу до PyPI.

щойно причину усунено, перезапустіть Claude Code або виконайте dbwise doctor у терміналі: команда дочекається збірки і запуститься. Відхилена платформа не записує в bootstrap.log нічого.

Псевдонім недоступний

list_databases показує псевдонім з reachable: false, або виклик відповідає Access refused by the role check of alias '<alias>': ..., або причиною, яку сервер записав для псевдоніма, наприклад Alias '<alias>' has no usable connection at level 'read': ... чи Timed out after 5s connecting to alias '<alias>'.

під час запуску сервер перевіряє кожен псевдонім його обліковими даними read, і псевдонім, який сервер не може відкрити, лишається в списку без бази даних. Текст інструмента і поле error псевдоніма в list_databases називають причину; відмова перевірки ролі називає свої причини і в тексті, і в полі reasons псевдоніма.

dbwise doctor --alias prod

Команда doctor розрізняє такі причини: NO HOST і NO USER (у конфігурації їх немає; виправлення — dbwise server add або dbwise credential add, або dbwise import --from-vault), NETWORK (хост не відповідає протягом 5 секунд; перевірте VPN, тунель, хост і порт), відсутній пароль (dbwise set-password NAME у терміналі), AUTH FAILED (сервер відхилив користувача; пароль змінено або він неправильний, тож виконайте dbwise set-password NAME), NOT FOUND і NO ACCESS для бази зі списку (виправте список командою dbwise server add або попросіть власника бази надати CONNECT), а також REFUSED: від перевірки ролі в базі зі списку псевдоніма або в базі виявлення сервера.

Коли причиною була мережа, інструмент агента reconnect знову перевіряє псевдонім. Після зміни конфігурації або пароля замість цього перепідключіть plugin:dbwise:postgres у /mcp.

Перевірка ролі відхилила псевдонім

У відмові перелічено всі знайдені причини, розділені ;. Кожен рядок нижче називає причину, оператор, що її усуває, і те, що вона означає. Виконуйте оператори від імені суперкористувача в тій базі, де знайдено причину: одна з баз псевдоніма або база виявлення сервера, dbname, типово postgres, яку перевіряють і сервер, і dbwise doctor. Замініть dbwise_read роллю, яку використовують облікові дані псевдоніма. Після виправлення перепідключіть plugin:dbwise:postgres (або викличте reconnect), бо перевірка ролі робить знімок, коли відкривається пул.

Причина Оператор, що усуває причину
the role is a superuser, has BYPASSRLS, has CREATEROLE, has CREATEDB, has REPLICATIONALTER ROLE dbwise_read NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOREPLICATION; або використайте іншу роль

Наведені вище оператори виконано на PostgreSQL 17.11 для ролі, побудованої так, щоб викликати кожну причину, і кожен оператор її усунув. Звідки походять привілеї, найлегше побачити в dbwise doctor: рядки audit: перелічують, чим володіє роль і які привілеї запису до неї доходять, безпосередньо, через PUBLIC або через успадковану роль.

Сервер налаштовано з role_check warn

Для сервера, у записі якого в config.json стоїть "role_check": "warn", відхилена перевірка є попередженням: псевдонім відкривається, а list_databases показує role_check: warn з причинами. Це налаштування призначено для локальних і тестових баз; див. Обмеження. Настройку редагують у config.json вручну: dbwise server add замінює запис і прибирає цей параметр.

Виклик відхилено через його рівень

Інструмент відповідає Error: Alias '<alias>' is at level '<alias level>', but this tool is at level '<tool level>'. Nothing was sent to the database.

рівень псевдоніма нижчий за рівень інструмента. diagnose_sql, explain_query, get_top_queries, analyze_db_health, analyze_workload_indexes і analyze_query_indexes мають рівень diagnose; write_sql має рівень write.

підвищення рівня — ваше рішення. Замініть псевдонім новим, з вищим рівнем, і дайте йому облікові дані для кожного рівня до нового включно:

dbwise alias add prod prod-db --level diagnose --credential read=prod-reader --credential diagnose=prod-monitor

Спершу створіть ролі (Створення ролей бази даних для dbWise), бо роль із правом входу для diagnose має пройти перевірку ролі на рівні diagnose.

Запит відхилено або минув тайм-аут

read_sql або diagnose_sql відповідає Error: Error validating query: <the query text>; explain_query відповідає Error: Error executing explain plan: Error validating query: EXPLAIN (<options>) <the query text>.

політика SQL рівня псевдоніма відхилила оператор до того, як він дійшов до бази. Текст інструмента не називає причину. Так відхиляються тип оператора, який рівень не допускає, функція поза набором рівня і SELECT із секцією блокування. Оператор, який PostgreSQL не може розібрати, отримує відповідь Error: Failed to parse SQL statement.

порівняйте оператор із розділом Що допускає політика кожного рівня. EXPLAIN виконується лише через diagnose_sql або explain_query на псевдонімі рівня diagnose або write, а функція на кшталт pg_sleep, set_config або pg_advisory_* не входить до жодного набору.

перепишіть запит із допущеними операторами і функціями. Якщо завдання потребує того, що допускає лише diagnose, підвищення рівня псевдоніма — ваше рішення; див. Виклик відхилено через його рівень. На рівні write політики немає, єдине обмеження задає роль бази даних.

Виклик відповідає Error: Query execution timed out after 30 seconds at level read. Далі текст містить Consider simplifying your query or increasing the timeout. На рівні diagnose у тексті вказано diagnose.

виклик на read або diagnose має 30 секунд, і цей ліміт фіксований.

спростіть запит: відфільтруйте раніше, додайте LIMIT або попросіть DBA створити індекс. Жодне налаштування не підвищує ліміт для read і diagnose. write_sql не має тайм-ауту, і його використання — ваше рішення.

Інструмент diagnose повідомляє про проблему з правами

Частина Sequence health: у analyze_db_health закінчується фразою <n> sequence(s) could not be read with this role's privileges and were not checked:, за якою йдуть назви. Роль не має SELECT на цих послідовностях. Надайте SELECT і ніколи не надавайте USAGE, бо перевірка ролі зараховує його як привілей запису:

GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO dbwise_diagnose;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON SEQUENCES TO dbwise_diagnose;

або зробіть роль членом pg_read_all_data. Решту перевірок стану виконано.

Запит до hypopg_list_indexes відповідає permission denied for view hypopg_list_indexes. hypopg 1.4.3 надає це подання лише власникові, а GRANT SELECT ON ALL TABLES IN SCHEMA public з рецепта ролей покриває його лише тоді, коли розширення вже існує в public. У базі з розширенням виконайте GRANT SELECT ON hypopg_list_indexes, hypopg_hidden_indexes TO dbwise_diagnose;. Якщо розширення лежить в іншій схемі, вкажіть цю схему перед назвами обох подань і надайте USAGE на неї кожній ролі dbWise (dbwise_read, dbwise_diagnose, dbwise_write): скидання пулу після кожного виклику запускає hypopg_reset() і hypopg_unhide_all_indexes() цієї схеми на пулах усіх рівнів. Рецепт описано в Створення ролей бази даних для dbWise. Інструменти індексів ці подання не використовують.

get_top_queries або інструмент індексів для навантаження не знаходить pg_stat_statements або інструменти індексів не знаходять hypopg. Команда doctor виводить note: extension ... is not installed in <database>. Попросіть власника бази створити розширення або створіть його через write_sql на псевдонімі рівня write.

Некоректний config.json зупиняє сервер

plugin:dbwise:postgres завершився з помилкою в /mcp, і жоден псевдонім не пропонується, навіть коректні.

коли Python-середовище збудовано, сервер читає config.json до того, як відкриє псевдонім. Файл, який не можна прочитати, який не є коректним JSON або не відповідає формату, змушує сервер вивести причину і завершитися зі статусом 1.

dbwise doctor виводить config unusable: з файлом, описом проблеми і, для порушення формату, шляхом JSON до першої проблеми. Рядки хука SessionStart у сесії теж позначають конфігурацію як непридатну.

виправте файл або скопіюйте на його місце config.json.bak, якщо він є, а потім перепідключіть сервер. Див. Некоректний config.json зупиняє сервер.

Сервер не запускається на повільній машині

Середовище збудовано, конфігурація коректна, але plugin:dbwise:postgres усе одно завершується з помилкою або перевищує тайм-аут, коли стартує сесія, на повільній або сильно завантаженій машині.

Claude Code закрив вхідний потік сервера, коли надто довго чекав першої відповіді. Значення, яке спостерігали з Claude Code 2.1.296 під claude -p: 27 секунд. Вимірювання старту сервера зі збудованим середовищем на машині з Windows 11 зайняло близько 2 секунд під час першого старту після збірки і менше 1 секунди потім, тож це стосується лише повільних машин.

збільште очікування через MCP_TIMEOUT у мілісекундах, задавши його в середовищі, з якого стартує Claude Code. В оболонці POSIX:

export MCP_TIMEOUT=60000

У PowerShell:

$env:MCP_TIMEOUT = "60000"

dbWise не може задати це за вас: змінна належить середовищу Claude Code. Перший запуск після встановлення охоплює заготовка з інструментом dbwise_status, і налаштування для нього не потрібне.
