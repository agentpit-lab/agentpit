Практичні інструкції dbWise

Інструкції до задач dbWise. Кожна описує, коли вона потрібна, кроки і як перевірити результат. Команда dbwise є в PATH лише в Bash tool агента, тож агент запускає її там, крім випадків, коли потрібно ввести пароль. Щоб запустити її в терміналі самостійно, використати повний рядок команди, який виводить dbwise credential add (крок 3 першої інструкції). У довіднику перелічено кожну команду і кожен параметр, а Усунення проблем починається із симптому.

Після кожної зміни конфігурації перепідключити plugin:dbwise:postgres у /mcp або почати нову сесію. Сервер читає config.json один раз, коли стартує.

Додавання псевдоніма

потрібно, щоб агент міг звертатися до бази даних.

  1. Описати сервер і бази даних, якими може користуватися агент. --dbname — це база виявлення, типово postgres; --port типово 5432, а --sslmode — require:

    dbwise server add main --host db.example.com --databases app

  2. Описати роль із правом входу. Облікові дані містять користувача бази даних і місце, де зберігається його пароль, але ніколи сам пароль:

    dbwise credential add main-read --user dbwise_read

  3. Ввести пароль у терміналі. dbwise credential add виводить точний рядок команди для запуску в терміналі системи, зі шляхом до скрипту запуску плагіна. У Windows слід використовувати PowerShell або cmd: Git Bash не може приховати введений текст. Команда запитує пароль з прихованим введенням і зберігає його у сховищі ключів ОС; пароль ніколи не проходить через чат. Рядок, який вона виводить, запускає таку команду:

    dbwise set-password main-read

    Щоб читати пароль зі змінної середовища процесу Claude Code або з файлу, під час додавання облікових даних указати джерело: --password-env VAR або --password-file PATH.

  4. Створити псевдонім. Рівень — read, якщо не вказано інше:

    dbwise alias add main main --level read --credential main-read

  5. Перепідключити plugin:dbwise:postgres у /mcp, потім виконати /dbwise:doctor (або dbwise doctor).

dbwise alias list показує псевдонім з його рівнем і обліковими даними, dbwise doctor завершується рядком VERDICT: ready, а виклик list_databases агента показує псевдонім з reachable: true. Роль із правом входу для read має пройти перевірку ролі; щоб створити роль, яка її пройде, див. Створення ролей бази даних для dbWise.

Надання агентові diagnose на робочій базі даних із власною роллю

агент має знаходити повільні запити, читати плани через EXPLAIN ANALYZE і отримувати поради щодо індексів на робочій базі даних, а цей доступ потрібно мати змогу відкликати, не змінюючи доступу до схем і даних.

Рівень diagnose має власні облікові дані, тож його обслуговує окрема роль бази даних. Виклики read_sql агента на псевдонімі, як і раніше, використовують роль read.

  1. Попросити DBA створити дві ролі або створити їх за рецептом у Створення ролей бази даних для dbWise: dbwise_read для рівня read і dbwise_diagnose для рівня diagnose. Роль diagnose є членом pg_monitor, а роль read ним бути не повинна: перевірка відхиляє члена pg_monitor на псевдонімі рівня read.

  2. Додати облікові дані для кожної ролі та ввести їхні паролі:

    dbwise credential add prod-reader --user dbwise_read
dbwise credential add prod-monitor --user dbwise_diagnose
dbwise set-password prod-reader
dbwise set-password prod-monitor

  3. Додати сервер, якщо його ще немає, і псевдонім з одними обліковими даними для кожного рівня до рівня псевдоніма. Зіставлення, яке пропускає рівень або називає рівень вищий за рівень псевдоніма, відхиляється:

    dbwise server add prod-db --host db.example.com --databases app
dbwise alias add prod prod-db --level diagnose --credential read=prod-reader --credential diagnose=prod-monitor

    dbwise alias add замінює псевдонім із такою самою назвою. З одним --credential NAME одна роль із правом входу обслуговує кожен рівень до рівня псевдоніма, і тоді ця роль має пройти перевірку на рівні псевдоніма; для diagnose перевірка допускає ролі моніторингу.

  4. Перепідключити plugin:dbwise:postgres у /mcp і виконати dbwise doctor --alias prod.

для кожних облікових даних і кожної бази псевдоніма команда doctor виводить role check (diagnose, enforce): passed in <n> ms: псевдонім diagnose застосовує перевірки diagnose до обох своїх ролей із правом входу. Коли список псевдоніма не називає базу виявлення сервера (dbname), команда виводить той самий рядок також у розділі discovery database <name>:, для ролі з правом входу, що обслуговує read (лише його сервер відкриває там). get_top_queries потребує pg_stat_statements у базі, а інструменти індексів потребують hypopg; команда doctor позначає відсутнє розширення. Які інструменти потребують які розширення, див. у Вимогах.

Імпорт облікових даних з Vault

команда зберігає хости, користувачів і паролі у Vault і має спільний файл, який їх зіставляє.

  1. Перед запуском прочитати файл команди як код. vault.addr у ньому отримує токен Vault оператора: vault CLI надсилає токен туди з кожним читанням. Звірити адресу з тією, яку дала команда.

  2. Запустити імпорт. vault CLI має бути в PATH:

    dbwise import team.json --from-vault

    За типового методу входу oidc команда сама запускає вхід, а авторизація завершується в браузері. Інший метод запитує введення і потребує терміналу.

  3. Перепідключити plugin:dbwise:postgres у /mcp і виконати dbwise doctor.

dbwise credential list показує імпортовані облікові дані з їхніми джерелами паролів, серед яких є сховище ключів ОС, а doctor не виводить NO HOST, NO USER чи AUTH FAILED. Пароль із Vault потрапляє лише до сховища ключів ОС, ніколи до config.json.

Без --from-vault команда dbwise import team.json об'єднує файл і запитує паролі, яких бракує. dbwise export --aliases a,b --output team.json записує файл команди без пароля.

Обмеження проєкту кількома псевдонімами

один проєкт має бачити лише деякі псевдоніми, наприклад тестову базу, але не робочу.

  1. Задати DBWISE_ALIASES як список, розділений комами, у середовищі, з якого стартує Claude Code. В оболонці POSIX:

    export DBWISE_ALIASES=staging,prod-replica

    У PowerShell:

    $env:DBWISE_ALIASES = "staging,prod-replica"

  2. Запустити Claude Code з цього середовища або перепідключити plugin:dbwise:postgres у /mcp, якщо Claude Code вже був запущений з нього.

list_databases показує лише ці псевдоніми. Назва зі списку, яка не є псевдонімом, ігнорується, і сервер записує попередження з її назвою. Без змінної сервер пропонує всі псевдоніми. Змінна обмежує те, що пропонує сервер; конфігурації вона не змінює.

Створення ролей бази даних для dbWise

роль створює DBA або його про це просять, і dbWise має звертатися до бази даних роллю, яка проходить перевірку ролі на рівнях read і diagnose. Перевірка відхиляє псевдонім, чия роль має більше привілеїв, ніж дозволяє його рівень; довідник перелічує тексти відмов.

Жоден приклад нижче не містить пароля. Оператори виконуються від імені суперкористувача (або ролі, якій платформа дозволяє те саме) через psql. Приклади використовують базу app і схему public; надання привілеїв слід повторити для кожної схеми, яку агент має бачити, і для кожної бази зі списку псевдоніма. Роль read також має пройти перевірку в базі виявлення сервера (--dbname, типово postgres), де сервер під час запуску виконує ту саму перевірку; крок 5 виконати там також, якщо там встановлено dblink. app_owner позначає роль, яка володіє таблицями застосунку.

Що роль має мати і чого не повинна мати

На рівнях read і diagnose роль має:

  • бути роллю з правом входу без атрибутів SUPERUSER, BYPASSRLS, CREATEROLE, CREATEDB і REPLICATION;
  • нічим не володіти в базі: ні базою, ні схемою, ні таблицею, поданням, послідовністю чи функцією;
  • не мати привілею запису на жодне відношення поза системними схемами, з будь-якого джерела. До цього належать INSERT, UPDATE, DELETE і TRUNCATE на таблицях і поданнях, INSERT і UPDATE на окремому стовпці, MAINTAIN на PostgreSQL 17 і новіших, а також USAGE або UPDATE на послідовності. Привілей, наданий PUBLIC, теж враховується, бо PUBLIC є частиною кожної ролі;
  • не бути членом жодної ролі, крім вбудованих ролей pg_*, і жодної з ролей pg_write_all_data, pg_signal_backend, pg_maintain, pg_read_server_files, pg_write_server_files, pg_execute_server_program, pg_checkpoint і pg_create_subscription. Членство в ролі застосунку дає змогу її членові скасовувати й завершувати сесії цієї ролі (перевірено на PostgreSQL 17 і 18) і передає те, чим ця роль володіє і що їй надано;
  • не мати змоги виконувати функції розширення dblink і не мати USAGE на зовнішньому сервері. На базі з встановленим dblink і типовими привілеями для цього потрібен REVOKE з кроку 5.

На рівні read роль не має бути членом pg_monitor, pg_read_all_stats або pg_stat_scan_tables: ці ролі належать до diagnose. Перевірка робить знімок, коли відкривається пул, тож привілей, наданий пізніше, з'явиться після перепідключення.

1. Створення ролей із правом входу

CREATE ROLE dbwise_read LOGIN;
CREATE ROLE dbwise_diagnose LOGIN;

CREATE ROLE не надає жодній з цих ролей жодного з відхилених атрибутів. Задати кожен пароль у psql: він запитує його з прихованим введенням і надсилає серверу хеш:

\password dbwise_read
\password dbwise_diagnose

Потім ввести той самий пароль для кожних облікових даних командою dbwise set-password.

2. Привілеї для ролі read

У кожній базі псевдоніма:

GRANT CONNECT ON DATABASE app TO dbwise_read;
GRANT USAGE ON SCHEMA public TO dbwise_read;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dbwise_read;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON TABLES TO dbwise_read;

ALL TABLES охоплює таблиці, подання, матеріалізовані подання та зовнішні таблиці, що існують зараз. Типові привілеї охоплюють ті, які app_owner створить згодом. Вони застосовуються до об'єктів, створених роллю, названою в FOR ROLE; без неї — до об'єктів, створених роллю, яка виконує оператор, а це зазвичай не власник застосунку. Вказати роль, яка створює таблиці, і повторити оператор для кожної ролі, яка їх створює.

Коротший шлях до того самого доступу — членство у вбудованій ролі, яка охоплює кожну схему і кожен об'єкт, створений згодом, послідовності включно:

GRANT pg_read_all_data TO dbwise_read;

pg_read_all_data проходить перевірку на рівнях read і diagnose (перевірено на PostgreSQL 17 і 18). Вона поширюється на кожну схему бази, тож доцільно використовувати явні привілеї, коли агент має бачити лише деякі з них.

3. Привілеї для ролі diagnose

Роль diagnose отримує той самий доступ, що й read, SELECT на послідовності і pg_monitor:

GRANT CONNECT ON DATABASE app TO dbwise_diagnose;
GRANT USAGE ON SCHEMA public TO dbwise_diagnose;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dbwise_diagnose;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO dbwise_diagnose;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON TABLES TO dbwise_diagnose;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON SEQUENCES TO dbwise_diagnose;
GRANT pg_monitor TO dbwise_diagnose;

pg_monitor дає ролі змогу бачити запити інших сесій у pg_stat_activity і pg_stat_statements. Він не дозволяє скасовувати або завершувати сесії інших ролей (перевірено на PostgreSQL 17 і 18). Лаг слотів у перевірці реплікації не потребує привілеїв: будь-яка роль, що може підключитися, читає pg_replication_slots і викликає pg_current_wal_lsn та pg_wal_lsn_diff, а pg_monitor додатково заповнює позиції відправників у pg_stat_replication (перевірено на PostgreSQL 17 і 18).

Надати SELECT на послідовності і ніколи не надавати USAGE. analyze_db_health читає кожну послідовність, щоб побачити, яка частина її діапазону використана, і без SELECT інструмент перелічує такі послідовності як неперевірені. USAGE дав би ролі змогу викликати nextval, а перевірка зараховує USAGE на послідовність як привілей запису, тож псевдонім було б відхилено. pg_read_all_data замість цих привілеїв дає той самий SELECT на послідовності без USAGE (перевірено на PostgreSQL 17 і 18).

hypopg 1.4.3 надає свої подання гіпотетичних індексів лише власникові. Наведені вище привілеї на схему покривають їх, коли розширення вже існує в public. Якщо hypopg створено пізніше, надати доступ до них у базі з розширенням:

GRANT SELECT ON hypopg_list_indexes, hypopg_hidden_indexes TO dbwise_diagnose;

Якщо hypopg лежить в іншій схемі, назвати її і надати на неї USAGE кожній ролі dbWise: після кожного виклику сервер скидає гіпотетичні індекси через функції цієї схеми на пулах усіх рівнів.

GRANT USAGE ON SCHEMA <hypopg_schema> TO dbwise_read, dbwise_diagnose, dbwise_write;
GRANT SELECT ON <hypopg_schema>.hypopg_list_indexes, <hypopg_schema>.hypopg_hidden_indexes TO dbwise_diagnose;

4. Типові значення сесії для обох ролей

Виконати один раз для кластера, для кожної з двох ролей. Значення — приклади; вибрати власні:

ALTER ROLE dbwise_read SET default_transaction_read_only = on;
ALTER ROLE dbwise_read SET statement_timeout = '30s';
ALTER ROLE dbwise_read SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE dbwise_read SET temp_file_limit = '1GB';
ALTER ROLE dbwise_read SET work_mem = '32MB';
ALTER ROLE dbwise_diagnose SET default_transaction_read_only = on;
ALTER ROLE dbwise_diagnose SET statement_timeout = '30s';
ALTER ROLE dbwise_diagnose SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE dbwise_diagnose SET temp_file_limit = '1GB';
ALTER ROLE dbwise_diagnose SET work_mem = '32MB';

Ці типові значення є запобіжниками для доступності та від помилок. Вони не входять до гарантії, бо сесія може змінити деякі з них. На PostgreSQL 17 і 18 сесія звичайної ролі може повернути до попередніх значень default_transaction_read_only, statement_timeout, work_mem та idle_in_transaction_session_timeout, а змінити temp_file_limit їй відмовлено. dbWise відхиляє оператори, які їх змінюють, і саме це не дає агентові їх змінити. Гарантію забезпечують наведені вище привілеї і перевірка ролі.

5. Відкликання функцій, які може виконувати PUBLIC

PostgreSQL дозволяє кожній ролі виконувати pg_logical_emit_message, функції pg_advisory_* і pg_try_advisory_*, а після встановлення розширення — функції dblink. dbWise відхиляє їх виклик з read і diagnose, а REVOKE закриває їх і на рівні бази. Для dblink це обов'язково: без нього перевірка відхиляє псевдоніми read і diagnose у базі, де встановлено dblink.

Сигнатури відрізняються між версіями PostgreSQL (у версії 17 до pg_logical_emit_message додали аргумент), тож оператори слід генерувати з каталогу, а не вписувати вручну. У кожній базі, від імені суперкористувача:

SELECT format('REVOKE EXECUTE ON FUNCTION %s FROM PUBLIC', p.oid::regprocedure)
FROM pg_proc p
WHERE p.pronamespace = 'pg_catalog'::regnamespace
  AND (p.proname = 'pg_logical_emit_message'
       OR p.proname LIKE 'pg\_advisory\_%'
       OR p.proname LIKE 'pg\_try\_advisory\_%')
UNION ALL
SELECT format('REVOKE EXECUTE ON FUNCTION %s FROM PUBLIC', d.objid::regprocedure)
FROM pg_depend d
JOIN pg_extension e ON e.oid = d.refobjid AND d.refclassid = 'pg_extension'::regclass
WHERE e.extname = 'dblink' AND d.classid = 'pg_proc'::regclass AND d.deptype = 'e'
\gexec

\gexec виконує кожен рядок як оператор. Частина для dblink вибирає власні функції розширення, тож інших функцій вона ніколи не зачіпає. Повторний запуск оператора безпечний. dbwise doctor виводить той самий REVOKE для функції PostgreSQL, яку знаходить виконуваною для PUBLIC, як рядок advice:.

База, створена пізніше з template1, копіює її каталог, тож виконання оператора також у template1 робить так, що нові бази починають із відкликаними функціями (перевірено на PostgreSQL 17 і 18). На керованому сервісі, де немає прав суперкористувача, можливість змінювати ACL функцій pg_catalog: не перевірено.

застосунок, що бере advisory lock або використовує dblink через PUBLIC, утрачає їх, доки їх не буде надано назад ролям, які ними користуються. Надати кожну функцію, яку потребує застосунок, наприклад:

GRANT EXECUTE ON FUNCTION pg_advisory_lock(bigint) TO app_owner;

Перевірити використання advisory lock і dblink перед відкликанням, наприклад у коді застосунку та в pg_stat_statements. Якщо відкликати не вдається, псевдоніми read і diagnose усе одно працюють, а функції pg_advisory_* і pg_logical_emit_message відхиляє політика SQL dbWise. Виняток — база зі встановленим dblink: там перевірка ролі відхиляє самі псевдоніми.

6. Роль для write

write_sql виконує будь-який SQL, який дозволено виконувати ролі з правом входу, і перевірка не застосовується. Надати те, що агент має мати змогу змінювати. Цей приклад дає змінювати дані в одній схемі і не дає змінювати схему:

CREATE ROLE dbwise_write LOGIN;
GRANT CONNECT ON DATABASE app TO dbwise_write;
GRANT USAGE ON SCHEMA public TO dbwise_write;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO dbwise_write;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO dbwise_write;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO dbwise_write;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO dbwise_write;

Задати пароль командою \password dbwise_write. Право CREATE на схему або володіння додавати лише для псевдоніма, агент якого має виконувати DDL. Не використовувати роль write для read або diagnose: перевірка її відхилить.

7. Підключення dbWise до ролей і перевірка

Додати облікові дані й псевдонім, як у Додавання псевдоніма і Надання агентові diagnose на робочій базі даних. Потім виконати:

dbwise doctor --alias prod

кожна база і база виявлення, якщо список псевдоніма її не називає, показує role check (<level>, enforce): passed in <n> ms з рівнем псевдоніма, по одному разу для кожної ролі з правом входу псевдоніма; базу виявлення перевіряють лише для ролі з правом входу рівня read. Відхилена роль показує REFUSED: з кожною причиною, а сторінка усунення проблем називає GRANT або REVOKE, які усувають кожну з них.
