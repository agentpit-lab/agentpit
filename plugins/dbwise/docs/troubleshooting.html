dbWise troubleshooting

Find the symptom, then read its cause, the check and the fix. For most problems, start with dbwise doctor (or /dbwise:doctor in a session). It checks the OS keychain, the Python environment and every alias, and ends with one VERDICT: line, ready or the list of problems. The dbwise command is on the PATH of the agent's Bash tool only, so the agent can run it there. To run it in a terminal yourself, use the command line that dbwise credential add prints; on Windows that is PowerShell or cmd, because Git Bash cannot hide typed input. The reference lists the commands and the role gate's refusal reasons, and Limitations lists what dbWise cannot do.

A change to the configuration takes effect after you reconnect plugin:dbwise:postgres in /mcp or start a new session.

Symptoms

  • The server is missing or failed in /mcp
  • The server shows no tools
  • The server shows only dbwise_status
  • An alias is unreachable
  • A call is refused for its level
  • A query is refused or times out
  • A diagnose tool reports a permission problem
  • An invalid config.json stops the server
  • The server fails at start on a slow machine

The server is missing or failed in /mcp

/mcp lists no plugin:dbwise:postgres, or lists it as failed.

one of these:

  • The plugin is not installed or is disabled. Install it with /plugin install dbwise@agentpit and start a new session.
  • There is no Python 3.12 to 3.14 on the PATH of the environment Claude Code starts in. The launcher prints that dbWise needs Python 3.12 to 3.14 and exits with status 1. See The server needs Python 3.12 to 3.14.
  • config.json is invalid, so the server exits with status 1. See An invalid config.json stops the server.

run python3 --version (on Windows py --list) in the environment Claude Code starts from, and dbwise doctor.

The launcher tries py -3.14, py -3.13, py -3.12 and then python on Windows, and python3.14, python3.13, python3.12, python3 and then python on macOS and Linux, and takes the first that is 3.12 to 3.14.

install a Python in the range, or correct the config, then start a new session. With Claude Code 2.1.296 under claude -p, a server that timed out at start was not started again by a new session for about 15 minutes; whether a server that exited with status 1 is held back the same way is not verified. If a new session does not bring it back, wait out that period.

The server shows no tools

plugin:dbwise:postgres is connected, and no database tool is listed.

the server registers a tool only when an alias admits it. With no aliases there is nothing to offer, and that is not an error. Either config.json does not exist, it holds no aliases, or DBWISE_ALIASES names none of them. A read alias gives the tools of level read only; the diagnose and write tools appear when an alias admits them.

dbwise alias list

and echo $DBWISE_ALIASES (in PowerShell $env:DBWISE_ALIASES) in the environment Claude Code starts from. The names in the variable have to be alias names, and the server warns about one that is not.

add an alias (Add an alias) or correct DBWISE_ALIASES, then reconnect.

The server shows only dbwise_status

The only tool is dbwise_status, and none of list_databases, read_sql and the rest.

the plugin's Python environment is not built yet. Claude Code waits a few tens of seconds for a server to answer, and the first build takes longer, so for the first session after the install (and after an update that changes requirements.txt) the server is a stub with one tool while a build runs in the background. A build that has failed, a platform dbWise refuses and a build in another session produce the same picture.

ask the agent to call dbwise_status and relay its text, or call it yourself. What the text means:

The full build log is bootstrap.log in the dbWise home directory, ~/.dbwise or $DBWISE_HOME (see Files). It holds pip's output. The usual cause of a failed build is no route to PyPI, or to the mirror pip is set up for, because pip installs binary wheels only. See The first start needs access to PyPI.

after the cause is gone, restart Claude Code, or run dbwise doctor in a terminal, which waits for a build and then runs. A refused platform writes nothing to bootstrap.log.

An alias is unreachable

list_databases shows the alias with reachable: false, or a call answers with Access refused by the role check of alias '<alias>': ..., or with the cause the server recorded for the alias, such as Alias '<alias>' has no usable connection at level 'read': ... or Timed out after 5s connecting to alias '<alias>'.

at start-up the server probes each alias with its read credential, and an alias it cannot open stays in the list with no database. The tool's text and the alias's error in list_databases name the cause; a gate refusal names its reasons in both and in the alias's reasons.

dbwise doctor --alias prod

The doctor tells these causes apart: NO HOST and NO USER (the config lacks them; the fix is a dbwise server add or dbwise credential add, or dbwise import --from-vault), NETWORK (the host cannot be reached within 5 seconds; check the VPN, the tunnel, the host and the port), a missing password (dbwise set-password NAME in a terminal), AUTH FAILED (the server refused the user; the password changed or is wrong, so run dbwise set-password NAME), NOT FOUND and NO ACCESS for a database in the list (correct the list with dbwise server add, or have the database owner grant CONNECT), and a role check REFUSED:, in a database of the alias's list or in the server's discovery database.

When the cause was the network, the agent's reconnect tool probes the alias again. After a change to the config or to a password, reconnect plugin:dbwise:postgres in /mcp instead.

The role check refused the alias

The refusal lists every reason it found, separated by ;. Each row below names the reason, the statement that clears it, and what it means. Run the statements as a superuser, in the database the reason was found in (one of the alias's databases or the server's discovery database, dbname, default postgres, which the server and dbwise doctor both check), and replace dbwise_read with the role the alias's credential uses. After the fix, reconnect plugin:dbwise:postgres (or call reconnect), because the gate takes a snapshot when a pool opens.

Where the grants came from is easiest to see in dbwise doctor, whose audit: lines list what the role owns and the write grants that reach it, directly, through PUBLIC or through a role it inherits.

The server is configured with role_check warn

On a server whose entry in config.json has "role_check": "warn", a refused gate is a warning: the alias opens, and list_databases shows role_check: warn with the reasons. This is meant for local and test databases; see Limitations. The setting is edited in config.json by hand: dbwise server add replaces the entry and drops it.

A call is refused for its level

The tool answers Error: Alias '<alias>' is at level '<alias level>', but this tool is at level '<tool level>'. Nothing was sent to the database.

the alias's level is lower than the tool's. diagnose_sql, explain_query, get_top_queries, analyze_db_health, analyze_workload_indexes and analyze_query_indexes are diagnose; write_sql is write.

raising the level is your decision. Replace the alias with a higher level, and give it a credential for each level up to the new one:

dbwise alias add prod prod-db --level diagnose --credential read=prod-reader --credential diagnose=prod-monitor

Create the roles first (Create the database roles for dbWise), because a diagnose login has to pass the gate at diagnose.

A query is refused or times out

read_sql or diagnose_sql answers Error: Error validating query: <the query text>; explain_query answers Error: Error executing explain plan: Error validating query: EXPLAIN (<options>) <the query text>.

the SQL policy of the alias's level refused the statement before it reached the database. The tool's text does not name the reason. A statement kind the level does not admit, a function outside the level's set and a SELECT with a locking clause are refused this way. A statement that PostgreSQL cannot parse answers Error: Failed to parse SQL statement.

compare the statement with What each level's policy admits. EXPLAIN runs only through diagnose_sql or explain_query on an alias at diagnose or write, and a function such as pg_sleep, set_config or a pg_advisory_* function is in no set.

rewrite the query to use admitted statements and functions. If the task needs something that only diagnose admits, raising the alias's level is your decision; see A call is refused for its level. At write there is no policy, and the database role is the only limit.

A call answers Error: Query execution timed out after 30 seconds at level read. The text goes on with Consider simplifying your query or increasing the timeout. At diagnose the level in the text is diagnose.

a call at read or diagnose has 30 seconds, and the limit is fixed.

simplify the query: filter earlier, add a LIMIT, or ask the DBA for an index. No setting raises the limit at read and diagnose. write_sql has no timeout, and using it is your decision.

A diagnose tool reports a permission problem

The Sequence health: part of analyze_db_health ends with <n> sequence(s) could not be read with this role's privileges and were not checked:, followed by names. The role has no SELECT on those sequences. Grant it, never USAGE, which the gate counts as a write grant:

GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO dbwise_diagnose;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON SEQUENCES TO dbwise_diagnose;

or make the role a member of pg_read_all_data. The other health checks ran.

A query on hypopg_list_indexes answers permission denied for view hypopg_list_indexes. hypopg 1.4.3 grants that view to its owner only, and the GRANT SELECT ON ALL TABLES IN SCHEMA public of the role recipe covers it only when the extension already exists in public. In the database with the extension, run GRANT SELECT ON hypopg_list_indexes, hypopg_hidden_indexes TO dbwise_diagnose;. If the extension lives in another schema, qualify both views with that schema and grant USAGE on the schema to every dbWise role (dbwise_read, dbwise_diagnose, dbwise_write): the pool reset after each call runs that schema's hypopg_reset() and hypopg_unhide_all_indexes() on the pools of all levels. The recipe is in Create the database roles for dbWise. The index tools do not use these views.

get_top_queries or the workload index tool finds no pg_stat_statements, or the index tools no hypopg. The doctor prints note: extension ... is not installed in <database>. Ask the database owner to create it, or create it through write_sql on an alias at level write.

An invalid config.json stops the server

plugin:dbwise:postgres failed in /mcp, and no alias is offered, including the valid ones.

once the Python environment is built, the server reads config.json before it opens an alias. A file that cannot be read, is not valid JSON or does not follow the format makes it print the reason and exit with status 1.

dbwise doctor prints config unusable: with the file, what is wrong and, for a format violation, the JSON path of the first problem. The SessionStart hook's lines in the session list the config as unusable as well.

correct the file, or copy config.json.bak over it when one exists, then reconnect. See An invalid config.json stops the server.

The server fails at start on a slow machine

The environment is built and the config is valid, and plugin:dbwise:postgres still fails or times out when a session starts, on a machine that is slow or heavily loaded.

Claude Code closed the server's input when it had waited long enough for the first answer. Observed with Claude Code 2.1.296 under claude -p: 27 seconds. A measurement of the server's start-up with a built environment on a Windows 11 machine took about 2 seconds on the first start after a build and under 1 second afterwards, so this applies to slow machines only.

raise the wait with MCP_TIMEOUT, in milliseconds, set in the environment Claude Code starts from. In a POSIX shell:

export MCP_TIMEOUT=60000

In PowerShell:

$env:MCP_TIMEOUT = "60000"

dbWise cannot set this for you: it belongs to Claude Code's own environment. The first start after an install is covered by the dbwise_status stub and needs no setting.
