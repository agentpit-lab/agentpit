dbWise limitations

What dbWise cannot do or does only in part, grouped by where you meet it. Each entry says what you see, and what still works or what to do. For the config format, the commands and the role gate's refusal reasons, see the reference.

Installation and start-up

Windows on ARM64 is not supported

The compiled package the PostgreSQL server needs, psycopg-binary, publishes no wheel for a native Windows ARM64 Python. With such a Python, the bootstrap stops before it runs pip and says so. An x64 Python 3.12 to 3.14 is the way around it: Windows on ARM runs it by emulation. That the x64 wheels then install and run under emulation is not verified.

the postgres server starts as the stub and offers only dbwise_status, which says dbWise does not run on native Windows ARM64 Python. Nothing is written to bootstrap.log. In a terminal, dbwise prints the same text and exits with status 1.

The first start needs access to PyPI

On the first start after the install, and after an update that changes requirements.txt, dbWise builds a Python environment from the hash-locked requirements. pip downloads binary wheels only (--only-binary :all:), so a machine with no route to PyPI, or to a mirror pip is configured for, cannot finish the build. The build runs once per version of requirements.txt; later starts reuse the environment.

the postgres server offers only dbwise_status and never gets the database tools. The build log is bootstrap.log in the dbWise home directory (see Files).

The first session offers only dbwise_status until the build ends

Claude Code waits a few tens of seconds for an MCP server to answer, and the first build takes longer. So the first session after the install, or after an update that changes requirements.txt, starts a stub server with one tool, dbwise_status, while the environment is built in the background. The database tools appear after you reconnect plugin:dbwise:postgres in /mcp or start a new session.

no tool of list_databases, read_sql and the others; dbwise_status says the dependencies are being installed, or that they are installed and the server must be reconnected.

the SessionStart hook's own check. A dbwise command in a terminal waits for the build to end and then runs.

The server needs Python 3.12 to 3.14

The launchers pick python3.14, python3.13, python3.12, then python3 and python (on Windows py -3.14, py -3.13, py -3.12, then python), and use the first one in the range 3.12 to 3.14. With none, a launcher prints that dbWise needs Python 3.12 to 3.14 and exits with status 1 before the stub can start, so the server cannot start and does not answer at all. Python 3.15 and later is outside the range as well.

plugin:dbwise:postgres failed in /mcp. The same range applies to the dbwise command in a terminal.

The SessionStart hook needs Python on the PATH

The hook runs python3, or python when python3 does not run, from the PATH of the environment Claude Code starts in, in whatever version it is. Without either, the shell cannot find the program and the hook exits with status 127. The hook only adds the offline health check's lines to the session; the server does not depend on it.

the SessionStart hook of dbWise fails with status 127, and the session has no dbWise problem lines. A machine that has only a versioned interpreter such as python3.12, or only the py launcher, is in this case although the server itself starts.

the database tools, and dbwise doctor from a terminal.

Intel Macs get an older cryptography release with open advisories

cryptography 49 and later publish no wheel for macOS on x86_64. The lock therefore pins cryptography 48.0.1 for that platform and a newer release everywhere else. 48.0.1 has three open advisories (GHSA-g6cj-pr64-35w5, GHSA-jwv3-5hgf-82ww, GHSA-m2h6-j472-rp4c). dbWise reaches cryptography only through pyjwt, a dependency of the MCP library, and secretstorage, the Linux keychain backend; it does not call the package itself.

nothing at run time. A dependency scan of the lock file for an Intel Mac lists the three advisories.

The configuration is read once, when the server starts

The server reads config.json in the dbWise home directory ($DBWISE_HOME, default ~/.dbwise) and resolves every password when it starts. A change made with a dbwise command, an edited file or a changed keychain entry takes effect after you reconnect plugin:dbwise:postgres in /mcp or start a new session. The reconnect tool does not reread the file: it probes again, with the connection details the server already holds, the aliases that were unreachable, which helps when the cause was the network.

an alias you just added is missing from list_databases, or an old password is still in use.

An invalid config.json stops the server

Once the Python environment is built, the server reads config.json before it opens any alias. A file that cannot be read, is not valid JSON or does not follow the format makes the server print the reason and exit with status 1, so none of the aliases is offered, including the valid ones. A config that does not exist yet is not an error: the server starts with no aliases.

plugin:dbwise:postgres failed in /mcp. The SessionStart hook's check lists the config as unusable, and dbwise doctor prints config unusable: with the file, what is wrong and, for a format violation, the JSON path of the first problem.

fix the file, or copy config.json.bak over it when one exists, then reconnect plugin:dbwise:postgres in /mcp.

Vault

The Vault address a team file names receives the operator's Vault token

dbwise import --from-vault runs the vault CLI against the addr of the team file's vault section, and the CLI sends the operator's Vault token to that address with every read. dbWise accepts only an https:// address (http:// for localhost, 127.0.0.1 and [::1]), and refuses quotes and control characters in it, but it cannot tell a trusted address from another one. A plain dbwise import of a team file stores the vault section without contacting it, and a later --from-vault import uses the stored address.

read a team file like code before the first import --from-vault, and check its vault.addr against the address your team gives you.

The Vault login method name is limited to a few characters

The login field of the vault section names the method passed to vault login -method=. dbWise accepts only letters, digits, ., _ and - in it, so a method name with another character, a space or a slash for example, makes the import refuse the team file before any call. The refusal leaves the local config unchanged.

$.vault.login: must use only letters, digits, '.', '_' and '-'; nothing was changed.

log in with the vault CLI yourself, then import.

Importing from Vault needs the vault CLI

dbWise reads Vault through the HashiCorp vault CLI, found through an absolute entry of the PATH, and logs in through it. There is no built-in HTTP client. A machine without the CLI cannot run import --from-vault; the command prints how to install it.

dbwise import <team file> without --from-vault, and every other command.

What the access levels guarantee

Only the leading marker is authoritative

Every query text sent at read, diagnose and write carries a comment dbWise puts in front of it, /* dbwise read */, /* dbwise diagnose */ or /* dbwise write */, so a DBA reading pg_stat_activity or pg_stat_statements can see which level sent it. The comment is added once in front of each query text a tool sends. read_sql and write_sql send their whole text as one query, so with several statements pg_stat_activity shows the comment once at the start, while pg_stat_statements splits the text and only the first statement has it. Only the leading /* dbwise <level> */ comment is dbWise's. A query can carry its own comment of the same shape later in its text, and that one says nothing about the level.

read the start of the query text, not a match anywhere in it.

A server with role_check set to warn loses the role layer

With "role_check": "warn" on a server, a refused role gate becomes a warning, so a superuser or an owner of tables can serve a read or diagnose alias. What remains is dbWise's SQL policy and the read-only transaction. A statement the policy does not foresee, or a function it admits, then runs with the privileges of the role. Use warn for local and test databases.

the tool descriptions of those aliases say role check relaxed (warn), and list_databases lists the reasons the gate found.

Statistics views that PostgreSQL grants to every role stay visible at read

What separates read from diagnose is the database role of each level's credential, enforced by the role gate, together with the tool split and the per-level statement and function sets. PostgreSQL grants some statistics views, such as pg_stat_user_tables, to every role. A read alias can query them. Other sessions' query text in pg_stat_activity and pg_stat_statements needs pg_read_all_stats, which the gate refuses at read.

VACUUM fails through write_sql

write_sql runs inside a transaction that it commits, and PostgreSQL refuses VACUUM inside a transaction block. CREATE INDEX CONCURRENTLY and other statements that cannot run in a transaction block fail the same way. Run them with a tool outside dbWise.

VACUUM cannot run inside a transaction block.

Timeouts and resource settings are guards a session can lift

A call at read or diagnose has a statement timeout of 30 seconds, set for the call with SET LOCAL, and the client stops waiting after the same time. Role defaults that a DBA sets with ALTER ROLE ... SET (default_transaction_read_only, statement_timeout and others) are availability guards, not part of the guarantee: a session can lift statement_timeout and default_transaction_read_only itself. On PostgreSQL 17.11 a session of a plain role also set work_mem and idle_in_transaction_session_timeout back and was refused temp_file_limit. dbWise's allowlist, which refuses the statements that change them, is what keeps the model from doing it. write has no statement timeout. The statements that set these defaults are in Create the database roles for dbWise.

EXPLAIN ANALYZE runs the query and loads the server

diagnose_sql and explain_query with analyze execute the explained SELECT on the server, with its full load, inside a transaction that is rolled back. A long SELECT holds its ACCESS SHARE locks until it ends or times out, and other sessions that need a stronger lock on those tables wait for it. See the PostgreSQL documentation on explicit locking.

A hostile view or function already in the database can use resources

A call can only run what the policy admits, but a view or a function that already exists in the database can do a great deal of work inside a call. The statement timeout limits it to 30 seconds per call, and several calls can follow each other.

At read every transaction that gets a transaction id consumes one

PostgreSQL gives a transaction an id when it first needs one and takes it from the server's counter, also when the transaction is rolled back. dbWise refuses pg_current_xact_id, which assigns an id on every call. Other ways to get one assigned are not listed.

A database with dblink installed refuses read and diagnose aliases

dblink_exec can run a write on a remote database that stays after the local rollback, and PostgreSQL leaves EXECUTE on the dblink functions to PUBLIC by default. The role gate refuses a read or diagnose role that can execute them, so the alias is unreachable until you run REVOKE EXECUTE ... FROM PUBLIC on the dblink functions of that database and grant it back only to the roles that need it. The same holds for a role with USAGE on a foreign server.

the alias is unreachable and the reason reads the role can execute functions of the dblink extension.

pg_stat_statements covers the whole server

get_top_queries and analyze_workload_indexes read pg_stat_statements, which keeps one list for the whole PostgreSQL server. Their results include queries from every database on the server, not only the database you named. The extension must be loaded through shared_preload_libraries and created in the database.

The SQL parser accepts PostgreSQL 18 syntax

dbWise parses SQL with the PostgreSQL 18 grammar, so a statement that only PostgreSQL 18 accepts passes the parse and is refused by an older server; a construct the allowlist does not know is refused before the statement reaches any server.

Sequence health check

analyze_db_health at diagnose runs a sequence check. It looks at the sequences that a column owns or takes its default from, and it reports the ones that have used more than 90% of their values. The gaps below are the cases it does not see or measures against another limit.

A sequence the role cannot select is not checked

The check needs SELECT or USAGE on each sequence. A role that has SELECT on tables does not have it on their sequences, and the role gate counts USAGE on a sequence as a write grant. Grant SELECT instead, with GRANT SELECT ON ALL SEQUENCES IN SCHEMA <schema> and ALTER DEFAULT PRIVILEGES IN SCHEMA <schema> GRANT SELECT ON SEQUENCES, or let the role be a member of pg_read_all_data. The statements, with the FOR ROLE clause that default privileges need, are in Create the database roles for dbWise.

the Sequence health: part of the report ends with <n> sequence(s) could not be read with this role's privileges and were not checked:, followed by the sequence names. The rest of the check, and the other health checks, still run.

A default that looks up the sequence by name follows the search path of the diagnose role

A column default such as nextval('orders_seq'::text) leaves no dependency on the sequence, so the check cuts the name out of the default and resolves it with to_regclass, in the session of the diagnose role. An unqualified name is found through the search_path of the diagnose role. If that path differs from the application's, the name resolves to another sequence or to none, and the column is then measured against that one or missed.

A sequence name that contains a single quote is not matched

The name is cut out of the default between single quotes, so a sequence whose name contains a single quote is not found through a default that looks it up by name. A serial or identity column, and a default that names the sequence directly in nextval(...), are not affected.

A default of an unrecognised form is measured against the sequence's own maximum

The maximum is the lesser of the sequence's max_value and the range of the column's type, but only when the column takes the value unchanged: it owns the sequence, or its default is exactly nextval(...) with an optional cast. For a default such as nextval('s') % 1000, the check keeps the sequence's own maximum, so a column narrower than the sequence can overflow before the check warns.

After setval with is_called false the sequence reads as 0% used

PostgreSQL reports last_value as empty for a sequence that has not been read from yet, and for one set with setval('seq', N, false). The check counts an empty value as 0, so such a sequence shows 0% used until nextval runs once, however close N is to the maximum.

Descending sequences are not checked

A sequence with a negative increment is left out of the check.

Inheritance children are reported once each

A table that inherits a column and its default from a parent through INHERITS is a table of its own, and the check reports the sequence once for each such table, so one sequence can appear once for each child. A partition of a partitioned table is reported only through its parent, unless the partition has a sequence of its own.

A domain or numeric column is not capped by its own range

The check caps the maximum by the range of smallint, integer and bigint columns. A column whose type is a domain, even a domain over integer, and a numeric column are measured against the sequence's own maximum, at most the bigint maximum. A domain over smallint or a numeric(5,0) column can run out of values before the check warns.
