dbWise how-to guides

Task guides for dbWise. Each guide says when you need it, the steps, and how to tell it worked. The dbwise command is on the PATH of the agent's Bash tool only, so the agent can run it there, except where a password is typed. To run it yourself in a terminal, use the full command line that dbwise credential add prints (step 3 of the first guide). The reference lists every command and option, and Troubleshooting starts from a symptom.

After every change to the configuration, reconnect plugin:dbwise:postgres in /mcp or start a new session. The server reads config.json once, when it starts.

Add an alias

you want the agent to reach a database.

  1. Describe the server and the databases the agent may use. --dbname is the discovery database and defaults to postgres; --port defaults to 5432 and --sslmode to require:

    dbwise server add main --host db.example.com --databases app

  2. Describe the login. The credential holds the database user and where its password lives, never the password:

    dbwise credential add main-read --user dbwise_read

  3. Type the password in a terminal. dbwise credential add prints the exact command line to run in a terminal on your system, with the path of the plugin's launcher. On Windows, use PowerShell or cmd: Git Bash cannot hide typed input. The command asks for the password with the input hidden and stores it in the OS keychain; a password never goes through the chat. The line it prints runs this command:

    dbwise set-password main-read

    To read the password from an environment variable of the Claude Code process or from a file instead, give the source when you add the credential: --password-env VAR or --password-file PATH.

  4. Create the alias. The level is read unless you say otherwise:

    dbwise alias add main main --level read --credential main-read

  5. Reconnect plugin:dbwise:postgres in /mcp, then run /dbwise:doctor (or dbwise doctor).

dbwise alias list shows the alias with its level and credentials, dbwise doctor ends with VERDICT: ready, and the agent's list_databases call shows the alias with reachable: true. The role of a read login has to pass the role gate; to create one that does, see Create the database roles for dbWise.

Give an agent diagnose on a production database with its own role

the agent should find slow queries, read plans with EXPLAIN ANALYZE and get index advice on a production database, and you want to be able to revoke that access without touching the access to schemas and data.

The diagnose level has its own credential, so a separate database role serves it. The agent's read_sql calls on the alias keep using the read role.

  1. Ask the DBA for two roles, or create them with the recipe in Create the database roles for dbWise: dbwise_read for the read level and dbwise_diagnose for the diagnose level. The diagnose role is a member of pg_monitor, and the read role should not be: the gate refuses a pg_monitor member on an alias at read.

  2. Add a credential for each role and type its password:

    dbwise credential add prod-reader --user dbwise_read
dbwise credential add prod-monitor --user dbwise_diagnose
dbwise set-password prod-reader
dbwise set-password prod-monitor

  3. Add the server if it is not there, and the alias with one credential for each level up to the alias's level. A map that skips a level, or names a level above the alias's, is refused:

    dbwise server add prod-db --host db.example.com --databases app
dbwise alias add prod prod-db --level diagnose --credential read=prod-reader --credential diagnose=prod-monitor

    dbwise alias add replaces an alias of the same name. With a single --credential NAME, one login serves every level up to the alias's level, and then that login has to pass the gate at the alias's level, which for diagnose admits the monitoring roles.

  4. Reconnect plugin:dbwise:postgres in /mcp and run dbwise doctor --alias prod.

for each credential and database of the alias, the doctor prints role check (diagnose, enforce): passed in <n> ms: a diagnose alias applies the diagnose checks to both of its logins. When the alias's list does not name the server's discovery database (dbname), the doctor prints the same line under discovery database <name>: too, for the login that serves read (the only one the server opens there). get_top_queries needs pg_stat_statements in the database, and the index tools need hypopg; the doctor notes a missing extension. Which tools need which extension is in Requirements.

Import credentials from Vault

your team keeps hosts, users and passwords in Vault and shares a team file that maps them.

  1. Read the team file like code before you run it. The vault.addr in it receives your Vault token: the vault CLI sends the token there with every read. Check the address against the one your team gives you.

  2. Run the import. The vault CLI has to be on the PATH:

    dbwise import team.json --from-vault

    With the default oidc login method the command starts the login itself, and you finish the sign-in in the browser. Another method asks for input and needs a terminal.

  3. Reconnect plugin:dbwise:postgres in /mcp and run dbwise doctor.

dbwise credential list shows the imported credentials with their password sources, the keychain among them, and the doctor reports no NO HOST, NO USER or AUTH FAILED. A password from Vault goes to the OS keychain only, never to config.json.

Without --from-vault, dbwise import team.json merges the file and asks for the passwords it lacks. dbwise export --aliases a,b --output team.json writes a team file with no password.

Restrict a project to some aliases

one project should see only some of your aliases, for example the staging database and not production.

  1. Set DBWISE_ALIASES to a comma-separated list in the environment Claude Code starts from. In a POSIX shell:

    export DBWISE_ALIASES=staging,prod-replica

    In PowerShell:

    $env:DBWISE_ALIASES = "staging,prod-replica"

  2. Start Claude Code from that environment, or reconnect plugin:dbwise:postgres in /mcp when Claude Code was already started from it.

list_databases shows only those aliases. A name in the list that is not an alias is ignored, and the server writes a warning that names it. With no variable, the server offers every alias. The variable restricts what the server offers; it does not change the config.

Create the database roles for dbWise

you are the DBA, or you ask one, and dbWise should reach the database with a role that passes the role gate at read and at diagnose. The gate refuses an alias whose role holds more than its level allows; the reference lists the refusal texts.

No example below holds a password. Run the statements as a superuser (or as a role your platform lets do the same), with psql. The examples use the database app and the schema public; repeat the grants for each schema the agent should see and for each database in the alias's list. The read role must also pass the gate in the server's discovery database (--dbname, default postgres), where the server runs the same check at start-up; run step 5 there too when dblink is installed in it. app_owner stands for the role that owns the application's tables.

What a role must and must not have

At read and at diagnose the role has to:

  • be a login role without SUPERUSER, BYPASSRLS, CREATEROLE, CREATEDB and REPLICATION;
  • own nothing in the database: no database, schema, table, view, sequence or function;
  • hold no write grant on any relation outside the system schemas, from any source. That counts INSERT, UPDATE, DELETE and TRUNCATE on tables and views, INSERT and UPDATE on a single column, MAINTAIN on PostgreSQL 17 and later, and USAGE or UPDATE on a sequence. A grant to PUBLIC counts too, because PUBLIC is part of every role;
  • be a member of no role except the predefined pg_* roles, and of none of pg_write_all_data, pg_signal_backend, pg_maintain, pg_read_server_files, pg_write_server_files, pg_execute_server_program, pg_checkpoint and pg_create_subscription. Membership in an application's role lets the member cancel and terminate that role's sessions (verified on PostgreSQL 17.11) and passes on what that role owns and is granted;
  • be unable to execute the functions of the dblink extension and hold no USAGE on a foreign server. On a database with dblink installed and its default grants, this takes the REVOKE in step 5.

At read the role must not be a member of pg_monitor, pg_read_all_stats or pg_stat_scan_tables: they belong to diagnose. The gate takes a snapshot when a pool opens, so a grant made later shows up after a reconnect.

1. Create the logins

CREATE ROLE dbwise_read LOGIN;
CREATE ROLE dbwise_diagnose LOGIN;

CREATE ROLE gives neither role any of the refused attributes. Set each password in psql, which asks for it with the input hidden and sends the server a hash:

\password dbwise_read
\password dbwise_diagnose

Then type the same password for each credential with dbwise set-password.

2. Grant the read role

In each database of the alias:

GRANT CONNECT ON DATABASE app TO dbwise_read;
GRANT USAGE ON SCHEMA public TO dbwise_read;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dbwise_read;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON TABLES TO dbwise_read;

ALL TABLES covers tables, views, materialized views and foreign tables that exist now. The default privileges cover those that app_owner creates later. They apply to objects created by the role named in FOR ROLE; without it, they apply to objects created by the role that runs the statement, which is usually not the application's owner. Name the role that creates the tables, and repeat the statement for each role that does.

A shorter way to the same reach is a membership in a predefined role, which covers every schema and every object created later, sequences included:

GRANT pg_read_all_data TO dbwise_read;

pg_read_all_data passes the gate at read and at diagnose (verified on PostgreSQL 17.11). It spans every schema of the database, so use the explicit grants when the agent should see only some of them.

3. Grant the diagnose role

The diagnose role gets the same reach as read, SELECT on sequences, and pg_monitor:

GRANT CONNECT ON DATABASE app TO dbwise_diagnose;
GRANT USAGE ON SCHEMA public TO dbwise_diagnose;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dbwise_diagnose;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO dbwise_diagnose;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON TABLES TO dbwise_diagnose;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT ON SEQUENCES TO dbwise_diagnose;
GRANT pg_monitor TO dbwise_diagnose;

pg_monitor lets the role see other sessions' queries in pg_stat_activity and pg_stat_statements. It does not let it cancel or terminate other roles' sessions (verified on PostgreSQL 17.11). The slot lag in the replication check needs no grant: any role that can connect reads pg_replication_slots and runs pg_current_wal_lsn and pg_wal_lsn_diff, while pg_monitor additionally fills the sender positions of pg_stat_replication (verified on PostgreSQL 17.11).

Grant SELECT on sequences and never USAGE. analyze_db_health reads each sequence to see how much of its range is used, and without SELECT it lists those sequences as not checked. USAGE would let the role call nextval, and the gate counts USAGE on a sequence as a write grant, so the alias would be refused. pg_read_all_data instead of these grants gives the same SELECT on sequences without USAGE (verified on PostgreSQL 17.11).

hypopg 1.4.3 grants its views of hypothetical indexes to their owner only. The schema grants above cover them when the extension already exists in public. If hypopg is created later, grant them in the database with the extension:

GRANT SELECT ON hypopg_list_indexes, hypopg_hidden_indexes TO dbwise_diagnose;

If hypopg lives in another schema, name the schema, and grant USAGE on it to every dbWise role: after each call the server resets hypothetical indexes through that schema's functions, on the pools of all levels.

GRANT USAGE ON SCHEMA <hypopg_schema> TO dbwise_read, dbwise_diagnose, dbwise_write;
GRANT SELECT ON <hypopg_schema>.hypopg_list_indexes, <hypopg_schema>.hypopg_hidden_indexes TO dbwise_diagnose;

4. Set session defaults for both roles

Run once for the cluster, for each of the two roles. The values are examples; choose your own:

ALTER ROLE dbwise_read SET default_transaction_read_only = on;
ALTER ROLE dbwise_read SET statement_timeout = '30s';
ALTER ROLE dbwise_read SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE dbwise_read SET temp_file_limit = '1GB';
ALTER ROLE dbwise_read SET work_mem = '32MB';
ALTER ROLE dbwise_diagnose SET default_transaction_read_only = on;
ALTER ROLE dbwise_diagnose SET statement_timeout = '30s';
ALTER ROLE dbwise_diagnose SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE dbwise_diagnose SET temp_file_limit = '1GB';
ALTER ROLE dbwise_diagnose SET work_mem = '32MB';

These defaults are guards for availability and for a mistake. They are not part of the guarantee, because a session can change some of them. On PostgreSQL 17.11 a session of a plain role could set default_transaction_read_only, statement_timeout, work_mem and idle_in_transaction_session_timeout back, and was refused temp_file_limit. dbWise refuses the statements that change them, which is what keeps the agent from doing it. The guarantee is the grants above and the role gate.

5. Revoke the functions that PUBLIC may execute

PostgreSQL lets every role execute pg_logical_emit_message, the pg_advisory_* and pg_try_advisory_* functions and, once the extension is installed, the dblink functions. dbWise refuses to call them from read and diagnose, and the REVOKE closes them at the database as well. It is required for dblink: without it the gate refuses the read and diagnose aliases of a database where dblink is installed.

The signatures differ between PostgreSQL versions (17 added an argument to pg_logical_emit_message), so generate the statements from the catalog instead of typing them. In each database, as a superuser:

SELECT format('REVOKE EXECUTE ON FUNCTION %s FROM PUBLIC', p.oid::regprocedure)
FROM pg_proc p
WHERE p.pronamespace = 'pg_catalog'::regnamespace
  AND (p.proname = 'pg_logical_emit_message'
       OR p.proname LIKE 'pg\_advisory\_%'
       OR p.proname LIKE 'pg\_try\_advisory\_%')
UNION ALL
SELECT format('REVOKE EXECUTE ON FUNCTION %s FROM PUBLIC', d.objid::regprocedure)
FROM pg_depend d
JOIN pg_extension e ON e.oid = d.refobjid AND d.refclassid = 'pg_extension'::regclass
WHERE e.extname = 'dblink' AND d.classid = 'pg_proc'::regclass AND d.deptype = 'e'
\gexec

\gexec runs each row as a statement. The dblink part selects the extension's own functions, so it never touches yours. Running the statement again is harmless. dbwise doctor prints the same REVOKE for the PostgreSQL function it finds executable by PUBLIC, as an advice: line.

A database created later from template1 copies its catalog, so running the statement in template1 as well makes new databases start revoked (verified on PostgreSQL 17.11). On a managed service where you are not a superuser, whether you may change the ACLs of pg_catalog functions: not verified.

an application that takes advisory locks, or uses dblink, through PUBLIC loses them until you grant them back to the roles that use them. Grant each function that application needs, for example:

GRANT EXECUTE ON FUNCTION pg_advisory_lock(bigint) TO app_owner;

Check for advisory lock and dblink use before you revoke, for example in the application's code and in pg_stat_statements. If you cannot revoke on a database, read and diagnose aliases still run with the pg_advisory_* and pg_logical_emit_message functions refused by dbWise's SQL policy, except on a database with dblink installed, where the gate refuses them.

6. A role for write

write_sql runs any SQL the login may run, and the gate does not apply. Grant what the agent should be able to change. This example gives data changes on one schema and no schema changes:

CREATE ROLE dbwise_write LOGIN;
GRANT CONNECT ON DATABASE app TO dbwise_write;
GRANT USAGE ON SCHEMA public TO dbwise_write;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO dbwise_write;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO dbwise_write;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO dbwise_write;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO dbwise_write;

Give the password with \password dbwise_write. Add CREATE on the schema, or ownership, only for an alias whose agent is meant to run DDL. Do not reuse the write role for read or diagnose: the gate would refuse it.

7. Point dbWise at the roles and check

Add the credentials and the alias as in Add an alias and Give an agent diagnose on a production database. Then run:

dbwise doctor --alias prod

each database, and the discovery database when the alias's list does not name it, shows role check (<level>, enforce): passed in <n> ms, with the alias's level, once for each login of the alias; the discovery database is checked for the read login only. A refused role shows REFUSED: with every reason, and the troubleshooting page gives the grant or REVOKE that clears each one.
